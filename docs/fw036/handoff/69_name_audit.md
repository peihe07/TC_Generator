## 二、審查判定：**收。§1 為本 feature 至今對排期影響最大之單一發現。**

### 2.1 §1.1 —— **`Bearer Selection` 十六列中只有一列與 bearer 有關**

其餘十五列為 DDF 判讀與**安全／認證**（TLS、HMAC、伺服器認證、埠管理、簽章）。

> **故「該組待 DR-SU2(a)」這個排期理由，自下放包 50 §二 #6 起就只對一列成立。**

**其成因之指認尤須記明**：**該 Test Set 之名稱是我方在 `framework.md` 定的**
（下放包 06 §4.2，`Bearer Selection` 自 `Client Architecture` 析出即由分析層裁），
**而其後我方一直以組名代替組之內容做排期決定。**

**§6.1(丁) 之歸類正確且是本輪最該留下之一句**：

> **本題之答案不是「某包漏了一個推論」，是「某包用組名代替了組之內容」。**
> **其與 B-36（總數對而分佈錯）、B-37（欄位不相稱）同族 ——
> 三者皆為：一個標籤被當成它所標之物。**

### 2.2 §6.1(乙) —— **下放包 54 握有那個資訊而沒有打開它**

該包同輪已列全部候選組之 105 比率（`Bearer Selection` 62%），
**而若當時看的是那 16 列之內容而非組名，就會發現十五列是安全與認證。**

**分析層追認：該包為我方所發，其未打開該資訊者是我。**

### 3.1 ⚠ `R-TM40` 揭露 T70a 之一個缺陷：**節內既有之引文框會被串接誤納**

該條節內於 1489 起有一個 fenced block —— **其內容為 canon §10.7 之逐字引文**，
**不是本條之條文本體**。

**而 T70a 之規則為「全部 fenced block 之串接」** ——
**加框後該引文框會被算進 `body_sha`。**

> **其後果**：**canon §10.7 若被他方改寫，`R-TM40` 之 `body_sha` 會變 ——
> 而本條一字未動。** **那正是 `body_sha` 設計要避免的事。**

**裁定**：

```
`FRAME_STATE.tsv` 增欄 `excluded_frames`：其值為該條節內
**不計入 `body_sha` 之 fenced block 之序號**（1-based，逐條）。
`rulings_hash.py` 之串接依該欄排除。

其判定屬人裁（引文與條文之別，機器不可判），
**於框界裁定時一併裁**，記於同一輪。

**`R-TM40` 之 `excluded_frames` = 其節內既有之引文框**（加框後為第 3 框）。
```

**併令普查**：`pending-frame` 之 25 條中，**節內已有 fenced block 者逐條列出**
（其為同型風險之候選）。

## 四、六項裁定

### #1 `Bearer Selection` —— **三項處置全採**

1. **其阻斷理由改記為「安全與認證之觀測手段」**，其請求**另立**（非 DR-SU2(a)）——
   **新開 `DR-SU7`**：TLS／HMAC／伺服器認證／埠管理／簽章之驗證，
   於系統測層級之觀測手段（是否須網路側錄，其工具與權限為何）
2. **16 列仍於收尾起草**（下放包 68 §三 #3 不變），其可交付性預估 **0／16**
3. **`framework.md` 之組名加註其內容**，**不改組成** ——
   > 改組成會動已交付之 trace；**而組名之誤導，其解是把內容寫在名字旁邊，不是改名字。**

**併記**：`292`（唯一之 bearer 列）仍歸 DR-SU2(a)。

### #2 SOC 門檻衝突 —— **`145` vs `246` 為真衝突，入 DR；`069` 不衝突**

| 列 | 值 | 情境 |
|---|---|---|
| `145` | `$IBS_SOC$ < [80]` → 不允許安裝 | **安裝前** |
| `246` | SOC less than 65% → 阻擋安裝 | **安裝前** |
| `069` | `> [65]` → 允許下載 | **下載前**（情境不同，**不衝突**） |

**`145` 與 `246` 同為安裝前之 SOC 門檻而值不同（80 vs 65）** —— **入 DR-SU4 之 addendum**
（其與 30 分鐘之三起算點同型：**同一量、不同值、來源皆為上游**）。

### #3 `D-9`（`248` 缺受詞）—— **追認，其受詞不得補**

> **補 `SWMC` 與補 `WiFi Update Service` 是二個不同的需求，而 037 沒有說是哪一個。**

**該句應入 `DESCRIPTION_DEFECTS.md` 之 D-9 條目** ——
**它把「為何不補」講得比任何條文都清楚。**

### #4 `D-7` 複發（`242`／`243` 與 `117` 共用同一段誤併之註腳）—— **追認**

**「三列共用同一段註腳 —— 其為同一次編輯之產物，非三次獨立之失誤」** ——
**該判斷改變了 D-7 之性質**：其為**上游之一次編輯事故**，非散發之缺陷。
**故其列數不代表其嚴重度，其「同一段註腳出現幾處」才是。**

### #5 盲測六條 —— **見 §三**

### #6 全 21 組之組名與內容相符度抽查 —— **令做**

**其自陳正確且是本項該做之理由**：

> **若組名誤導不只一處，本 feature 之整個排期史都建立在標籤上。**

**設計**：21 組逐組**依列序抽三列**（不挑），出其 `Requirement Title`；
**判其與組名之相符**（相符／部分／不符）。
**⚠ 判定由執行層出候選、分析層裁** —— **其為對我方分組之檢驗，執行層不宜獨判。**
