## 八、回答 SEC-18 審閱 §三（`match_kind` 全為 `exact` 之疑）

**結論：不是「正規化提前」，而是審閱之前提與 SEC-01 之記載不符 —— `base` 回退從未被實際使用過。**

逐項舉證：

| 來源 | 原文（逐字節錄）|
|---|---|
| `up/20260916_SEC-01.md:274` | 「**`base` 何以一次未用**：六本 SYSAD docx **皆**有「每元素一表」，`_COMP`／`_INTF` 等尾綴之…」|
| `up/20260916_SEC-01.md:279`（§4-1）| 「SAM 19 列共 42 個 SYSAD token（19 個帶 `_COMP`）。**42／42 皆 `exact`，`base` 命中清單為空。**」|
| `up/20260916_SEC-01.md:281` | 「但 Table 11 **不是唯一對應來源** —— `SYSAD_SAM_SYSTEM_COMP` 等在元素表 T14 等自身即為 `SYSAD_ID`。」|
| `features/security/DATA_REQUESTS.md` 之 `DR-SEC-i` | 「`SYSAD_SAM_PACKAGE_INTF` 補 `Mapped SYSRA-ID`（**元件表存在而該列未填**，非 Table 11 漏列）… 不阻。**去尾綴回退基底名為合法對應**。本 feature 實測 70/70 `exact`」|

即：**DR-i 講的是「某列未填 Mapped SYSRA-ID」，而「去尾綴回退」只是被登記為合法備案，不是實際命中路徑。**

程式面複驗（`build_trace_matrix.py`）：
- `sec_of` 之鍵來自 **SYS3 SYSAD docx 之元素表／Table 11**（`read_sysad()`），而 `SYSAD_SAM_SYSTEM_COMP`
  等帶尾綴之 id **在元素表中自身即為 `SYSAD_ID`**，故 `n in sec_of` 直接成立，不進 `strip_base()` 分支。
- 列級 `match_kind` 只有在**每一個** source id 都 `exact` 時才記 `exact`（`all(k == "exact" …)`），
  故「70 列全 exact」等價於「全部 SYSAD token 皆 exact，`base` 分支零次觸發」。
- 實測：SAM 19 列之 `sysad_normalized` 皆含 `…_COMP` 且 `match_kind = exact`（19／19）。
- 旁證：`Mapping detail` 內**查無任何 `SYSAD_SAM*` 字串**（該 sheet 以 SYS-RA-SEC 為鍵），
  故 SAM 之對應本就不經該 sheet 之 id 比對。

**處置**：依審閱 §三所給之二選一，採「附一句說明」，不加 `match_note` 欄
（該欄會使 `trace_matrix.tsv` 全檔重生，且事實已可由 `match_kind` ＋ SEC-01 §4-1 完整回答）。
若分析層仍要該欄，請明示，一支 chore 可加。
