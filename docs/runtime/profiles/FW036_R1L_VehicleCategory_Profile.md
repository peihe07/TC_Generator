## 1. `[OVERRIDE]` —— IN §11 引號例外之啟動

IN §11 之例外其啟動條件為「**when the feature profile says so**」。
本節即該啟動，其範圍**嚴格限定於下列四項**，逐字採 R-VC19 (a)–(d)：

**(a)** **僅 `test_item` 上半之 verbatim 區段**得保留來源記法。
037 `Requirement Title` 之 `'...'` 與 `Requirement Description` 之
`«...»` 皆為來源記法，於該區段內逐字保留，不改寫。

**(b)** **作者之散文一律 `"..."`** —— procedure 之按壓標的、
非引用之 ER 行、括號下半、reasoning，**無例外**。

**(c)** 保留之記法**須對得上所引之來源列** —— 即該 token 確實逐字出現於

「驗證其來源」。**⚠ 現行 lint 無法實作本項，見 §2。**

**(d)** 本例外**不及於**任何其他欄位、不及於 `«...»` 以外之新記法。
若日後出現第三種來源記法，須另裁後始得納入，**不得類推**。

### 1.1 本例外不改動之事

## 5. 標準 setup 片語（常數表）

IN §5.3 要求標準 setup 片語**逐字重用**。本節為本 feature 之常數表。

設立時機：pilot 之 12 筆 Procedure 首步逐字完全相同，但該片語當時
**只存在於 JSON 裡，未進任何常數表**。全量批次時 `Category Structure`／
`Controls`／`Settings List` 等組亦需導覽首步，各自書寫即產生變體
（IN §5.3 所禁之 case／hyphenation／spacing／wording variants）。
**pilot 是建表的最好時機 —— 現在只有一個片語，且已驗證可用。**

### 5.1 常數

```
ENTER_VEHICLE_CATEGORY:
  Open the Vehicle Category screen

ENTER_VC_TAB(<tab>):
  Open the Vehicle Category screen and select the "<tab>" tab
  <tab> 之值域：framework §2 所載之 Test Set 對應頁籤名
                （現為 Controls、Settings；Specialty 諸名待其批次時擴充）
  values(<tab>) = Controls | Settings
```

> 末行 `values(<tab>) = …` 為**機讀行**（下放包 16 §四 T90 增設、
> 下放包 17 §二 **准**）。其上之中文值域說明為裁定之措辭，二者須一致；
> 機讀行存在之理由同 §5.3 —— **值域之擴充須同時改二處，而「須同時」
> 若無承載者就只是規定**。`verify_batch.py` 自機讀行解析。

### 5.1.2 機讀行之格式（固定，下放包 17 §二 T95）

```
values(<參數名>) = 值1 | 值2 | 值3
```

**五項固定**：

1. 前綴逐字為 `values(`，小寫，無空白；
2. 參數名以 `<` `>` 包覆，與其模板中之洞**逐字相同**；
3. 分隔符為 ` = `（等號前後各一空白）；
4. 值以 ` | ` 分隔（豎線前後各一空白），值本身不得含 `|`；
5. **一常數一行**，不換行、不續行。

**理由**：若格式不固定，日後另一個帶參數常數會出現第二種寫法 ——
**分歧從值域移到了格式**，而 §5.2(a) 之「二處不得分歧」是對值域說的，
攔不到格式分歧。

**現行僅 `ENTER_VC_TAB` 一個帶參數常數**（§5.1.1 之「不再擴大參數化」）。
本節之格式即為其唯一實例所定，日後若另有需求須另裁（同 §5.1.1）。

原 `ENTER_CONTROLS_TAB` 成為 `ENTER_VC_TAB(Controls)` 之實例，
**其字串不變** —— 第 1 批已生成之 22 筆不需因此改動。

首次使用：`generated/pilot_glovebox.json`（12 筆，`ENTER_VC_TAB(Controls)`）
與 `generated/batch1_category_structure.json`
（22 筆，含 `ENTER_VEHICLE_CATEGORY` 與 `ENTER_VC_TAB(Settings)`）。

### 5.1.1 帶參數常數之凍結語意（§5.2(c) 之補充，非重寫）

```
帶參數之常數，其**模板**凍結；其**值域**得擴充，但擴充須經裁定並記於 profile。
模板之修改與無參數常數同 —— 須經裁定並回溯既有 TC。
```

**不再擴大參數化**：僅 `ENTER_VC_TAB` 一個常數帶參數，且參數只有一個、
值域為枚舉。**不引入巢狀、不引入條件、不引入預設值** ——
保持其為「一個有洞的字串」，不使本節成為 DSL。
若日後另有常數需參數化，**須另裁**。

### 5.2 擴充規則

**(a)** 新增常數時，須**同時**更新本節與 `verify_batch.py` 之常數表，
**二處不得分歧**。

**(b)** 新片語之加入須先確認既有片語不敷用 ——
**不得為措辭偏好而增設近義常數**。

**(c)** 常數之措辭**一經登記即凍結**；其修改須經裁定並**回溯既有 TC**。

### 5.3 本表之機器化

`verify_batch.py` 第 14 項驗「該批所用之 setup 片語皆取自本表」。
其常數**自本檔解析**（讀 §5.1 之 code fence），非硬編於腳本 ——
故 (a) 之「二處不得分歧」由解析保證，不靠人記得。

**偽陰性**：只驗**首步**是否為表中常數。若某批把導覽寫在第二步，
或把常數拆成兩步，本項看不到。屆時須擴充判準。

## 6. 標準 Pre-Condition 措辭

**與 §5 分立**（下放包 15 §3.3）：§5 之標的為 IN §5.3 之
「Standard Setup **Snippets**」，其例皆為 **Procedure 步驟**；
本節之標的為 **Pre-Condition**，其規制來源為 **IN §4.4** 而非 §5.3。
二者之判準與禁項不同，混為一表會使 §4.4 之三類禁項失去對應。

### 6.1 常數

```
DISPLAY_LANDSCAPE:
  The vehicle is equipped with a landscape display
DISPLAY_PORTRAIT:
  The vehicle is equipped with a portrait display
```

**§4.4 之類別：hardware / peripheral。**
自檢（`requires do / check / confirm` → NOT a Pre-Condition）為**否** ——
測試者不會把螢幕轉成直向，而是換一台配直向螢幕的車。
故其為車輛之硬體配置，非步驟可切換之狀態。

首次使用：第 1 批 `Category Structure` 之 `VC-012-*`／`VC-013-*`
（下放包 15 §5.2 之方向前提）。

### 6.2 擴充規則

**沿用 §5.2 之三項**：(a) 二處同步（本節與 `verify_batch.py`）、
(b) 不為措辭偏好增設近義常數、(c) 一經登記即凍結，修改須經裁定並回溯。

### 6.3 本表之機器化

同 §5.3 —— 常數自本檔解析，非硬編。
**偽陰性**：只驗「Pre-Condition 若涉顯示器方向，是否用表中措辭」；
若某批以其他措辭表達同一前提（`The display is in portrait orientation`），
本項看不到 —— 那正是常數表要防的變體，卻也是它抓不到的。
**故 §4.4 之三類禁項檢查（第 11 項）仍為主防線，本表為輔。**

## 7. `PENDING` 之內嵌書寫（**提案，自第 2 批起適用**）

下放包 16 §三之建議措辭，**採納**，逐字登記：

```
PENDING 之內嵌書寫：
  缺件僅影響某一步驟之某個值時，得內嵌於該步驟，
  但須使其可讀為**標註**而非句子成分 —— 建議以獨立子行或括號標示。
  缺件影響整個欄位時，該欄逕填 PENDING 佔位。
```

### 7.1 適用範圍與不回溯

**自第 2 批（`Settings List`）起適用。**
`pilot_glovebox.json`（`VC-033-01`）與 `batch1_category_structure.json`

### 7.2 現行形態之留痕

```
3. ... and compare it against PENDING: DR-VC9 Dashboard content table
```

內嵌後 `PENDING:` 在語法上成為介詞之受詞，讀來像「與『PENDING:…』比較」。

整欄標 PENDING 過度、內嵌之定位精確度較高。

### 7.2.1 `PENDING` 之**位置**依其所影響之欄位而定（下放包 26 §4.2）

```
`PENDING` 之位置依其所影響之欄位而定：
  缺件影響「怎麼做」→ Procedure；影響「怎麼判」→ ER；
  影響「前提」→ Pre-Condition。
下放包若表列其位置，該表列為預設值；執行層依實際功能判定後
記明理由者，以實際功能為準。
```

**由來**：下放包 25 §三表列「`062-*`／`063-*` 四筆之 **ER** 帶 PENDING」，
執行層改置 **Procedure** 並記明理由 —— 該四筆之驗證標的為**返回落點**，
彈窗文字屬 `062-01`／`063-01`；為帶 PENDING 而另立 ER 斷言文字，
會與其驗證點重複（IN §8.2.1／§527）。**文字在該四筆只用於辨識按的是哪個彈窗。**
下放包 26 §4.2 追認，並自認該表列為「套了一個未經檢視的預設」。

**計數之母體**：`PENDING` 之筆數以 **TC 層**為母體，非 leaf 層 ——
拆分後同一 leaf 之數筆各自計。收斂第 8b 項即以 TC 層計。
（下放包 25 稱「5 筆」為 leaf 層，TC 層為 7 筆。）

**本節未機器化**：無檢查驗「該 PENDING 是否放在正確欄位」——
第 8b 項只驗樣式、DR 存在性與宣告相符，**不驗位置**。

### 7.3 未機器化

本節**無對應之檢查項**。「可讀為標註而非句子成分」需語意判斷，
其可機械化之近似（如「`PENDING:` 前一字元須為 `(` 或行首」）
會把現行三筆判為違規 —— 而它們依 §7.1 不回溯。
**故本節為書寫慣例，靠審閱承擔，不靠檢查器。** 記明以免誤以為已受保護。

```
Procedure 所必然建立之狀態**（即：不解指涉，該 TC 也必須建立它）者，
得以**單句**為上半，指涉由 TC 結構承載。

層次（依序適用，不得跳層）：
  1. 預設 —— 取含先行詞之整段（既有處置）
  2. 整段逾 R-3 之 50 token，**或**先行詞為結構必然狀態 →
     得採 `resolved-by-structure`：單句上半 ＋ CONT 登記
     `resolution`（`PC` 或 `Step-n`）與 `resolution_key`
     （先行詞之關鍵詞，如 `popup`）
  3. 二者皆不合 → 停並回報

登記可驗（第三個檢查點）：`resolution=PC` 者，收斂時檢該 TC 之
pre_conditions 含 `resolution_key`；`Step-n` 者檢該步驟含之。
聲稱「結構會解」而結構裡沒有 —— FAIL。
```

### 9.3 登記欄位（`data/cont_table.tsv`）

| 欄 | 語意 |
|---|---|
| `leaf` | 037 之 SWE requirement ID |
| `kind` | `continuation`／`reference`（§9.1 之二類）|
| `sys1_section` | SYS1 之 Outline Number |
| `sentence_index` | 單句 `3`／範圍 `1-2`／`*`（整段）|
| `resolution` | **§9.2 專用**：`PC` 或 `Step`；不適用者留空 |
| `resolution_key` | **§9.2 專用**：先行詞之關鍵詞，逐字 |
| `note` | 判定理由 |

**`resolution_key` 之逐字要求**：其值須與 TC 內之書寫**逐字相同**
（不做去連字號、不做同義展開）。`pop-up` 與 `popup` 為二字串 ——
若判準容許二者互通，該欄之保護即退回語意判斷，
而**能被語意判斷放過的東西，就是這個檢查原本要攔的東西**。
故本 feature 一律登記 `pop-up`（沿 SYS1 §11.5 之原文記法）。

### 9.4 三個檢查點之分工

| 層 | 標的 | 承載者 |
|---|---|---|
| 第一層 | 候選 leaf 未登記（該進表的沒進表）| `cont_guard.py` `layer1` |
| 第二層 | 登記之節／句指錯（表之內容錯）| `cont_guard.py` `layer2` |
| **第三層** | **`resolution` 之聲稱與 TC 結構不符** | `cont_guard.py` `layer3` |

第三層之**已知盲區**：它只驗 `resolution_key` 出現於所指之欄位，
**不驗該欄位所述之狀態是否真為先行詞**。
即「PC 裡有 `pop-up` 這個詞」不等於「PC 建立的正是該彈窗」——
後者仍為人工判讀。記明以免誤以為 §9.2 之層次 2 已全機器化。

### 9.4.1 第一層之已知偽陰性 —— 三型、六實例（下放包 25 §2.2）

第一層之特徵為**二個**：`continuation`（去條號後小寫起首）與
`reference`（句首代名詞 `It|They|This|These|That|Those`）。
**下列三型結構上不命中**：

| 型 | 實例 | 逐字 |
|---|---|---|
| **標點層改寫** | `013-02` | 037 於句中補句號並刪 `and` —— 首字大寫，非片段外觀 |
| **非代名詞之時序承接** | `038-04` | `The user is **then** taken back…` —— `then` 承接前句，首字大寫 |
| **定冠詞回指** | `058-03` | `**Closing the pop-up** with ‘X’ or ‘OK’ returns…` |
| **非句首代名詞** | `062-02`／`063-02` | `If **they** press ‘OK’ or ‘X’…` —— 句首為 `If` |
| **無冠詞名詞回指** | `064-03` | `…while **pop-up** is on screen…` |

**六個實例，形態穩定。**

**本 feature 不擴充第一層**（下放包 25 §2.2 裁定），理由：
擴充之收益在**未來 feature**，本 feature 剩餘僅 6 leaf（第 6／7 批 3 ＋ b 段 3），
人工對照足堪；且擴充需偽陽性調校 ＋ 全表回歸，其成本此刻高於收益。

```
現行補網 —— 勘查 (d) 之 SYS1 人工對照。六個實例**皆由它發現**，
非由第一層發現。補網有效，不是靠運氣。

**若未來 feature 沿用本機制而其批次規模較大，應優先擴充第一層。**
屆時三型之樣式為：定冠詞回指、非句首代名詞、無冠詞名詞回指。
```

**不擴充是本 feature 之取捨，不是判定該三型不重要。**
記明使接手者不需重新發現。

## 10. R-3 之 `token` 工作定義（下放包 23 §2.3）

canon（IN／PLAYBOOK）**未定義 R-3 之 50 token 上限如何 token 化**。

```
本 feature 之工作定義：**以空白切分計詞**。
canon 若日後定義 token 化方式，以 canon 為準，屆時 CONT 全表重算。
```

**此定義使既有量測自近似值升為正式值**：上繳包 22 §4.2 之

CONT 表現有 6 條之取材範圍皆由人工計數。
記明以免誤以為 R-3 於本 feature 已受檢查。

## 11. `split_flag`／`split_reason` 於本 feature 不使用（下放包 24 §1.4，裁甲）

```
本 feature 之 `split_flag` 恆 `False`、`split_reason` 恆空。
拆分之權威紀錄為：JSON 頂層之 `split_delta` ＋ `tcs` 中同一 req_id 之重複。
```

**三項理由（下放包 24 §1.4）**：

1. **拆分資訊已有承載者且受檢** —— `split_delta` 由收斂第 15 項驗
   「宣告值 vs 自 `tcs` 實際數得之增量」，同 req_id 之重複為工作簿之處置對象。
   二欄再填即第二來源，**而二來源必分歧**。
2. **canon 對 `split_flag` 之語意無判準** —— 標什麼？拆分之產物？
   被拆之母體？填 `True` 是在無定義下造語意。
3. 回溯改既有四筆屬既交付者之改動（R-TM13），其收益為零（見 1）。

**現況實測**：截至第 4 批，全 99 筆 TC 之 `split_flag` 皆 `False`、
`split_reason` 皆空，**其中 8 筆為拆分之產物**
（`046-05`／`048-02`／`038-03`／`038-05` 四個 leaf 各 2 筆，
即 `split_delta` 合計 4）。
本節即為該現況之明文，非新規。

**未機器化**：現無檢查項驗「`split_flag` 恆 `False`」。
其違反不會被攔，只會使該欄成為第二個拆分來源 —— 記明以免誤以為已受保護。
