1. 標準流程 — 產生一份完整的 TC

最常用的操作路徑。從拖檔到匯出共五步。

成本分布：Generate 階段為主要 LLM 成本來源。實際金額依 row 數、prompt cache 命中率與模型選擇而定。

Task-level 模型分層：
  • Test Set 分類（Configure → Grouping，以及 Export 時補分類）固定用 gpt-5-mini，純歸類不需重度推理。Configure 內的 Fill Blank 只補空白 Test Set；Regroup All 會把既有 Test Set 當 hint 重新分類全部 row，按 Apply 前不會改寫 row。
  • 需求解讀 / 拆分判斷（decompose）與 TC 正文生成（generate / regenerate / rerun）用使用者在 Configure → Options 選的 model（預設 gpt-5，另可選 gpt-5.4）。
Review 操作分兩種：
  • Regenerate：使用者先填 regenerateReason，AI 以該原因作為主要修正目標並重新判斷是否需要拆分。若不拆，只回 primary row.regenerated；若需要拆，先回 req.split.insertPlan（新增幾列、插入錨點、是否重排），再用 row.added 補 sub-TCs。Primary 仍走 diff-preview，新增列直接插在 parent 後方。
  • Re-run：重走完整 pipeline（含 decompose），不依賴 reviewer reason。一筆 row 可能產生多筆 TC：先回 req.split.insertPlan，primary 覆蓋原列，sub-TCs 插在下方。適合對 AI 首輪拆分不滿意或要補缺漏情境的場景。

2. 快速路徑 — Quick Generate

只想試一筆需求、不用整個 workbook 的情境。不需 upload、不需 review，直接貼需求看結果。統一走 auto-split：AI 依 ASPICE SWE.6 §6.1（Test Item）、§9（False Pass 拆分）、§10.2（延伸情境）自動判斷拆成幾筆 TC。

何時用這條路徑？：臨時驗證、內部會議示範、寫 prompt 時試個 case。產生的 TC 會進入 Job History 但不寫進 workbook。

3. 單一 Test Case 的狀態流轉

每一筆 TC 從解析開始，到最後被匯出，會經過幾個明確的狀態。Review 階段的決策是核心。若 AI 判斷一筆 requirement 應拆成多個 scenario，generating 期間會先觸發 req.split.insertPlan 說明新增列數與插入錨點，再產生額外 sub-TC rows。

Accepted Only 只匯出 accepted；All Generated Cases 則匯出目前 review 清單中的所有 generated rows。
實作細節：frontend status 欄位實際有 8 種 — pending / generating / success / fail / reviewing / accepted / rejected / flagged。success 與 fail 是 generating 結束的瞬間狀態（成功即進入 reviewing，失敗會保留供重跑）；flagged 是 reviewing 下的子狀態，表示 validator 有警告需人工留意。req.split.insertPlan 是結構變更計畫，AI 只回新增數量與插入位置，實際 row 插入與 ID/順序調整由前端 store 和 export writer 處理。

4. 桌面上的視窗如何互動

每個步驟對應一個視窗。透過 advanceWindow 前進下一步時，前一個 module 視窗會自動關閉；若使用者從桌面圖示或 Taskbar 直接開窗，仍可同時開多個 module。CostMeter、Workspace、Job History 與 Agent 則維持常駐。

重點：
  • 主流程前進或返回時，advanceWindow(from, to) 會關閉來源視窗、開啟目標視窗，因此使用者通常一次只沿著一條主流程操作。
  • 若從桌面圖示或 Taskbar 直接開窗，仍可同時打開多個 module；這不是主流程預設，但實作上是允許的。
  • Taskbar 常駐看得到累積花費（CostMeter）、Workspace、Job History，這些不受 advanceWindow 影響。
  • 關閉 module 視窗不會遺失資料。所有 rows、設定、成本記錄都存在 Zustand store（localStorage）和後端 SQLite，回到原步驟會恢復上次狀態。

6. 雙軌並用 — GUI + Agent

GUI 流程與 Agent 視窗可並用，兩者共用同一份 backend tools 與 job store。

核心原則：兩種模式共用同一份資料與 tool；使用者可在同一個 job 裡來回切換。GUI 做正式交付、Agent 做模糊查詢與批次，各司其職。
