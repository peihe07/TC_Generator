1運作原則

固定流程走 GUI 與 API；只有需要語意判斷或生成的地方才使用 AI。這樣使用者看得到狀態，也不會把 token 花在可以用按鈕完成的動作。

2GUI 與 API 並行 / 切換

GUI 是操作層，API 是執行層。使用者不需要知道每個 backend endpoint，但每個按鈕背後都對應明確 API；當流程需要 AI 時，API 再把必要上下文交給模型。

GUI
固定操作
把流程變成可見狀態
Upload、Configure、Review、Export 都是高重複、需要確認狀態的工作。做成 GUI 可以看到 rows、preview、validation、usage 與輸出範圍，不必在 chat 裡反覆描述要刪哪幾筆或匯出哪個版本。
API

parse、match、group、generate stream、export 都由對應的 API endpoint 執行；job 狀態則是這些流程的副作用，由 job_manager 持久化。每一步有固定輸入輸出，錯誤可重試，也能被測試覆蓋。
AI
語意判斷
只在需要理解時切入
AI 不負責操作整個系統，只負責 requirement 解讀、test case 生成、必要的分類或修正建議。GUI 決定何時呼叫 API，API 決定是否需要模型。
User Action使用者在 GUI 選檔、按 Group、Refresh Match、Generate、Delete 或 Export。
API Contract前端送出明確 payload，backend 回傳 preview、job state、SSE event 或 Excel file。
AI Boundary只有語意不足以用規則處理時，backend 才組 prompt 並呼叫模型。
GUI State結果回到畫面，使用者可審查、覆寫、刪除、重跑或匯出。
可追蹤：每一步都有狀態 可測試：API 行為固定 可省成本：AI 只處理必要內容 可人工覆寫：不被模型結果綁死

3Token 成本：GUI vs Agent

核心差異不是「有沒有用 AI」，而是 AI 只拿生成需要的上下文，或是讓 agent 在每一步都讀取工具結果、重看歷史並做下一個決策。基準：一份 Excel 約 50 條需求 → 約 150 條 test case。

GUI / API 路徑：成本集中在 Generate parse、match、group、export 由程式碼完成；LLM 只處理 requirement → test case 的語意生成。
Agent 路徑：Generate 之外還有決策成本 tool schema、tool result、規劃文字與多輪歷史 replay 都會進 context，任務越長越容易放大。

5Configure 決策圖

這裡是目前最容易誤會的區塊：載入頁面只顯示現有資料，真正分類要按 Group；Spec Matching 則有明確的 exact → fuzzy → semantic 順序。

Grouping：使用者決定何時分類

Load rows讀取 workbook rows 與原 H 欄 testSetHint。只呈現既有資料，不自動產生 group。
Run Group使用者按 Group 後，才用 requirement、hint 與現有 Test Set 重新分類全部 rows。
Check preview結果先留在 preview。若分類不對，可在 Manual Override 逐 row 改成正確 Test Set。
Apply to job確認後寫回 job rows，並把 test set label 縮短成可讀名稱。

Spec Matching：由確定到模糊

Exact code先找 C1、C6.1、CR、ICE、LS、PDM code。命中時 confidence 最高。
Fuzzy text沒有明確 code 時，用 H/I/L/M 欄、requirement text 與 hint 做文字比對。
Semantic match只有 spec cache 有 embedding 且環境可用時才跑，用來補足文字相近但 code 不明的情況。
Review preview結果進 preview。使用者可 refresh，並優先檢查 unmatched 與 low confidence rows。

6Generate / Review 邏輯

生成階段負責結構化產出；Review 階段負責把不該交付的 rows 排除，並維持後續 export 的資料一致性。

GEN
AI pipeline
Decompose → Generate → Validate
同一 Requirement ID 的 sibling rows 會被放進 prompt context。模型需判斷 duplicate 或差異軸，validation 失敗時走 retry / escalation。
REV
Local state
Delete 後立即整理
刪除 row 後會重算 split sibling metadata、清掉指向已刪除 row 的 duplicate note，並依 group bucket 重排 TC ID。
