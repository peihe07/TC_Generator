## 2. §4.2 —— lint 腳本

落點：`features/privacy/scripts/lint_tcs.py`。**未沿用 AMFM 版。**

### 2.1 為何不能沿用

AMFM 之 gate 以 `data/stla_to_cfts.json` 解析每一個 `specification_reference`。
Privacy 沒有這種對映檔，**也不應該為了沿用而造一個** —— R30-1 已確立
id 是查得的不是算出來的。本腳本改為**每次執行時自 CFTS022 docx 重讀
artifact 全集**（336 個）作為 `spec-reference` 之權威。

若 artifact 表頭樣式改變而解析出 0 個 id，腳本**中止並要求修 parser**，
不降級為通過 —— 這是 B1-GATE-1 那次 0/10 誤報的教訓寫進程式。

### 2.2 gate 清單（12 項）

| gate | 依據 |
|---|---|
| `design-method` | profile §3.3；權威為 `下拉選單!A1:A9` 九詞條（讀工作簿，非硬編）|

### 2.3 ⚠️ B1 回跑先報 3 findings —— 是 gate 缺陷，不是 TC 缺陷

首次回跑：

```

[er-modal] -004 TC1: Expected Result contains the modal 'CAN'
[er-modal] -005 TC2: Expected Result contains the modal 'CAN'
```

命中的是 **`Interior CAN`（匯流排名）**，被大小寫不敏感之 `\bcan\b` 當成

**修正方式為修 gate，不是放寬 gate**（停手條件 1 之界線）：
modal 命中若其字面為全大寫，判為縮寫／訊號名而非 modal 動詞。

`er-modal` —— 一個對正確輸入誤報的 gate，與一個永不觸發的 gate 一樣壞。

## 3. §4.3 —— B2 生成之 JSON 與 digest

### 3.1 digest

**4 leaves → 4 TC**（-008 停手未產）。§2.5 預估為 5 葉 5–8 TC。

| leaf | artifact | TC | design_method | priority | 一句話 |
|---|---|---|---|---|---|

| -007 | 4915172 | 1 | 等價劃分 | P1 | AMP 存在 → HU 不改變 level |
| -009 | 4915174 | 1 | 等價劃分 | P1 | 無 amp + 使用者改 level → 改顯示／改 level／存記憶體 |

**四葉皆一條 TC**：-009 / -010 之條文各有多個 outcome（改顯示＋改 level＋
存記憶體／改顯示＋送訊號），依 §5.7「一個觸發之連帶結果為一條 TC 配多行 ER」
不拆為多條。

### 3.2 為什麼四葉同一個 design_method

四葉是**同一個劃分（amplifier presence）之四個格**：
-006/-007 為自動調整側之 not present / present，
-009/-010 為使用者調整側之 not present / present。
每葉覆蓋一個等價類，正是 `等價劃分` 之定義
（`Reference` 分頁：「將行為相同的輸入分組，每組取代表值」）。

**未引用 AMFM 之 R10-1 config-gate 規則** —— 該條在 SXM profile 內，
Privacy profile §7 明定不由類比繼承。此處之 EP 判定自 §12 與劃分事實本身導出。

### 3.3 兩對之間不互相補齊（§2.5 逐葉指示）

| 對 | 觸發 | outcome |
|---|---|---|
| -006 / -007（自動側）| 車速變化 | 調整／不調整輸出音量 |
| -009 / -010（使用者側）| 使用者選擇改 level | 改顯示＋改 level＋存記憶體／改顯示＋送訊號 |

- **-010 之 outcome 無「改變 level」亦無「存入記憶體」** —— 照條文原樣寫，
  未自 -009 反向補入。這與 -007（AMP 存在時 HU 不改變 level）一致。
- -006 之 outcome 無「存入記憶體」，未自 -009 補入。
- 各葉之 `reasoning` 皆明寫此點。

### 3.4 AMP present/not present 之建立 —— 未填 PROXI 參數值

VF651_V6_R2（HDCC28 版）之 `PROXI Parameters` 節列有
`Acustic_Configuration` 與 `Audio_System_Type` 兩個參數名，
但同節明文：

> The characteristics of the "PROXI" Parameters and their related values are
> defined in the "PROXI requirements" specific for the vehicle project.

**值不在該文件內**，且該 PROXI requirements 不在 `inputs/`。
依 §8.4.1 **不自行填任何參數值**；Pre-Condition 以條文自身之措辭
（`An external amplifier is present / is not present on the vehicle`）表述
—— 此為 profile §3.2 明列之合法 spec-trigger。
已列為 `DATA_REQUESTS.md` **#11**。

## 4. §4.4 —— -008 之 ECU 判定（單獨成節）

**判定：可觀察面全在 AMP 側 → 依停手條件 3 停止該葉之生成。**

### 4.1 條文

```
4915173  [ECU: ETM, AMP, RRM, LTM]
When the AMP wakes up on the Interior CAN, the AMP shall recall the state of
the speed controlled volume.
```

### 4.2 依 R33-1(d) 之判準逐項

| 項 | -008（4915173）| 本批其餘四葉 |
|---|---|---|
| trigger 主詞 | **AMP** | HU（-006/-007 為條件式，-009/-010 為使用者操作經 HU）|
| outcome 主詞 | **AMP** | **HU** |
| 條文是否提及 HU | **否** | 是 |
| ECU tag 是否含 `AMP` | **是** | 否 |

**-008 是本批唯一 outcome 主詞為 AMP、且條文完全未提及 HU 的一條**，
也是唯一 ECU tag 列有 `AMP` 的一條。

037 之 Verification Criteria 同向：五條判準全部以 AMP 為主體，
包含「The AMP performs speed-dependent volume adjustments according to the
restored SCV setting」。

### 4.3 一項反向指標，照實回報

**該條之 ECU tag 仍列有 `LTM`**（`ETM, AMP, RRM, LTM`）。
若僅看 ECU tag，本交付件之 ECU 在列，會得出「本葉屬本交付件」之結論。

執行層**不以此推翻判定**，理由是 R33-1(d) 之判準寫的是**注入點／觀察點**
是否落在本 ECU，而非 ECU tag 是否列名 —— 條文之 trigger 與 outcome 皆為 AMP，
HU 側無任何可觀察之行為。但這兩者不一致本身值得裁定：
**ECU tag 列名與行為主詞不一致時以何者為準**，目前無條文。

### 4.4 與 -005 之異同

| | -005 | -008 |
|---|---|---|
| outcome 主詞 | AMP | AMP |
| 本 ECU 是否有可觀察行為 | **有** —— HU 為 $VolumeSCV$ 之發送端，輸出集合可觀察 | **無** |
| 處置 | 維持讀法 (i)，改寫 TC2 為輸出集合封閉性 | **停手** |

-005 之所以能留在本交付件，是因為 HU 在該訊號鏈上有可觀察的一端；
-008 沒有。這正是 R33-1(d) 判準在兩個相似情境下給出不同結果。

## 8. §4.8 —— 本包是否仍有該驗而未驗者（獨立判斷）

**有，六項。**

### 8.1 lint 的 12 個 gate 涵蓋的是形式，不是內容

`spec-reference` 只驗「id 查得於 CFTS022」，**不驗該 id 之條文是否真的對應
該葉**。B1-GATE-1 那次抓到的錯（-002 指向 splash screen 條款）
**這個 lint 抓不到** —— 那次靠的是人工語意比對。
若日後有葉子引用了存在但不相干的 artifact，lint 會放行。

### 8.2 `step-actions` 之動詞表是我列的

`STEP_VERBS` 十八個動詞出自我對現有 TC 的歸納，不是任何條文。
表外的動詞（例如 `verify`、`observe`）不會被計為動作，
故「一步兩動作」在使用表外動詞時可能漏抓。

### 8.3 -006 / -007 之「速度變化」步驟未回溯規格

`Increase the vehicle speed` 是我寫的激勵方式。CFTS022 之條文只說
「according to the speed controlled level」，**未規定如何改變車速、
也未給任何速度值**。我沒填任何數值（§8.4.1），但「以改變車速為激勵」
這個測試設計本身未經規格確認 —— 且其可執行性與 A-PV16（CAN trace）同類，
需要車速模擬能力。

### 8.4 -009 之「存入記憶體」以睡眠喚醒驗證，與 -003 部分重疊

-009 之 outcome 含「store the new value in memory for the next Interior CAN
bus wakeup」，我以睡眠→喚醒→重讀驗證。**該觀察面與 -003（喚醒後召回 SCV
狀態）重疊**。兩者條文不同（-009 是使用者改值後的儲存，-003 是喚醒時的召回），
故未標 `duplicate_of`；但 review 若認為重疊過多，-009 之步驟 4–6 可考慮移除
並改以其他方式驗證儲存。

### 8.5 Pre-Condition 措辭回溯原文仍未辦

N5 / 上繳包 04 §6.3 / 上繳包 09 §6.4 已連續三次列出，本包仍未辦。
B2 四葉新增之 PC（`An external amplifier is present on the vehicle` 等）
同樣未逐句回到 CFTS022 核對。**P6 寫回前必須完成**，且範圍現已擴至十葉。

### 8.6 ECU tag 與行為主詞不一致時的判準尚無條文

-008 之判定依賴「行為主詞」而非「ECU tag 列名」，兩者在該葉衝突（§4.3）。
本次以 R33-1(d) 之觀察點判準處理，但該條寫的是注入點／觀察點，
**未直接規範 ECU tag 列名之效力**。若日後再遇同型衝突，
目前沒有可引用的條文，會重新爭論一次。
