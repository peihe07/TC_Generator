**實則兩條無人負責，而該事實被一個量詞掩蓋。**


## 2. §3.3 C-5 抓到 0 個訊號 —— 綠向強度須收緊

診斷正確且修正得當。但真正的一般化在這句：

> self-test 之 C-5 綠向只檢查鍵存在，不檢查內容非空 —— 與 `05R` 之
> `lint_required_fields` 只檢查鍵存在同型。

**同一形態在本 feature 已出現三次**：`lint_required_fields`（鍵存在 vs
值非空）、C-5 綠向（鍵存在 vs 內容非空）、以及更早的
`check_other_sheets`（member 名稱 vs 內容位元組）。

三者皆為**以結構之存在代替內容之正確**。

```
R-TM52（分析層自裁，2026-08-21）—— 綠向須驗內容非退化，不得只驗鍵存在

self-test 之綠向判準不得以「鍵存在」「欄位有值」「集合非空」為滿足條件，
須驗**內容非退化**：

- 集合型 → 元素數 > 0 **且**其值域非單一退化值
- 文字型 → 非空 **且**不等於樣板／佔位字串
- 對映型 → 至少一項之值來自實際來源，非預設值

判準寫成後自問：「若該項之產生邏輯完全失效而只回傳空結構，本綠向會不會
通過？」會 → 判準無效。

依據（同型三例）：
1. lint_required_fields 檢查鍵存在不檢查值非空（05R §4.3）
2. C-5 綠向檢查 `"signals" in leaf` 而全 22 片皆 0（06 §3.3）
3. check_other_sheets 比對 member 名稱而非內容位元組（A-TM21(b)）

本條為 R-TM21（判準須可能失敗）之內容面：前者問「會不會失敗」，
本條問「失敗時會不會被抓到」。
```

`load_spec_objects()` 之守衛（body 全空即 raise）為正解 ——
**它把一個綠向抓不到的錯誤移到執行期必然 raise**，比收緊綠向更可靠
（R-TM39：不觸碰優於主動保護之同一精神，此處為「必然 raise 優於可能檢出」）。
