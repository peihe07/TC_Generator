### 1.1 逐筆對差（00R §2 要求公布，不得只回報計數）

```
新有舊無（首版漏抓）： 030  031  032      ← 全部 3 筆
舊有新無（首版誤抓）： （無）              ← 0 筆
```

**首版為純漏抓、零誤抓**，三筆皆為 `Functional Requirement`，故缺口
51 → 48。78 筆與 48 筆之完整 id 清單已落於 `ANOMALIES.md` A-TM09 §B。

### 1.2 根因（執行層自查，00R 未要求但屬該交代者）

三筆全數漏在 `SWE-RA-TIME&DATE-009` 一列，其原始字串為：

```
SYS-RA-TIME&DATE-029–033, 046, 047, 080, 081
```

首版之範圍 regex 為 `(?<![\w-])(\d{2,3})\s*[–-]\s*(\d{2,3})`。負向後查
`(?<![\w-])` 本意是防止把 id 尾碼誤認為範圍起點，**但範圍起點 `029` 前面
正是 id 之連字號，故該防護把全表唯一一個真範圍擋掉，範圍展開完全未觸發。**
其後 `029` 由完整 id regex 撿回、`033` 由裸數字 regex 撿回（其前為 U+2013，
不在字元類 `[\w&-]` 內），中間 `030`–`032` 遂無任何規則命中而蒸發。

即：**防護規則與其欲防護之對象在字面上同形**，且失敗形態為靜默。
全表僅此一列使用「範圍 + en-dash」寫法，故只錯一列 —— 這也是首版逐列
檢查時未察覺之原因：22 列中 21 列正確。

### 1.3 兩項推論之缺陷 —— 接受，且認為 00R 之定性正確

**(a) 方向性搞反** —— 接受。「全部命中 FR」證明的是零偽陽性；零偽陽性
與低估完全相容，本例即是。零偽陽性只支持「引用集 ⊆ 真集」，推出的是
**下界**而非上界。首版寫「上界」，被自身證據推翻（真值 61.9% > 59.5%）。

**(b) 恆等式充作檢查** —— 接受。`126 − 命中數 = 未覆蓋數` 為定義，
相加必為 126，與引用集對錯無關。`78 + 48 = 126` 同樣成立。鑑別力為零。

首版將此二者當作「解析正確性之驗證」，實際上**當時完全沒有做任何正確性
驗證**，只是把兩個必然成立的性質誤讀為證據。這比數字錯 3 筆嚴重 ——
數字錯是可更正的單點失誤，把恆等式當檢查是**方法上的失效**，會使同類
錯誤在未來不被攔截。

已完整登記於 A-TM09 §D，並立為往後之作業要求：**凡以解析結果立論者，
須公布展開後之完整 id 清單供反驗，不得只給計數。**
