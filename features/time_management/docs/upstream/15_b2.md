## 3. T3 —— 兩閘與構造複驗（R-TM67 首次適用）

### 3.1 構造複驗之輸出

```
[構造複驗] r_ok 之 DR 序 [5, 11] 已升冪 = True；r_bad 之 DR 序 [11, 5] 已升冪 = False
[構造複驗] r_bad 之字串序若以字典序排 = True（若為 True，則字串比較會放行此壞值 —— 本閘須用數值）
[構造複驗] itd_dup 之 input_test_data 確實出現於 procedure = True；itd_ok 則為 False
```

**第二行是 R-TM67 之價值所在**：它不只證明壞值確實壞，還證明了
**本閘之判準（數值比較）是必要的** —— 若用字串比較，這個壞值會被放行，
而紅向仍會顯示 PASS（因為別的原因報了），看不出判準選錯。

### 3.2 兩閘之射程刻意寫窄，理由已入 docstring

**`lint_data_placement`（R-TM66）**：只驗**重複**，不驗歸屬是否正確。
一筆真正的獨立資料集寫在 `input_test_data` 而 Procedure 未提，本閘不報 ——
該判斷需讀懂資料性質，非本層所能。**射程窄是為了不誤攔合法之資料欄。**

**`lint_remarks_order`（R-TM68）**：驗升冪與一佔位一行，不驗佔位是否
齊全（該 leaf 該有的 DR 都有沒有）—— **後者正是 §5.2 所揭之缺口。**

### 3.3 七案例

```
PASS 綠向 R-TM68 (DR-5 在 DR-11 之前 → 不報)
PASS 紅向 R-TM68 (DR-11 在 DR-5 之前 → 報)
PASS 紅向 R-TM68 (兩佔位擠一行 → 報)
PASS 綠向 R-TM68 (Remarks 為空 → 不判)
PASS 紅向 R-TM66 (input_test_data 與 procedure 逐字重複 → 報)
PASS 綠向 R-TM66 (獨立資料集，procedure 未提 → 不報)
PASS 綠向 R-TM66 (input_test_data 為 NA → 不判)
                                              自驗：49 / 49
```

### 5.2 **但另有一條同樣漏了，而 lint 沒報 —— B3 閘之假陰性**

以獨立量測（不經 lint）檢查 002 三條：

```
TC#1: DR 號=['5','11','11']   含 DR-5=True
TC#2: DR 號=['11']            含 DR-5=**False**   ← lint 未報
TC#3: DR 號=[]                含 DR-5=False       ← lint 報了
```

**TC#2 同樣缺 DR-5，卻因 Remarks 內有 DR-11 佔位而通過 B3 閘。**

**成因**：B3（`lint_spec_gap`）之判準為「Remarks 含 `PENDING: DR-`」。
該判準在 R-TM64 之前是有效的 —— 當時 Remarks 只承載 DR-5。
**R-TM64 使 Remarks 成為全部佔位之單一落點後，「Remarks 非空」不再等於
「該 leaf 之缺口已宣告」**，而 B3 未隨之調整。

**一個規則變更使另一個既有閘門靜默失效，且 lint 全綠。**
這正是本 feature 一路在防的形態，這次出現在條文之間而非程式之間。

**未修**（T5 明令不預先修正 B2 之 lint 發現；且修閘門會改變本次實測之
條件 —— 若先修再跑，就看不到「現行 lint 抓到什麼」）。

**修法明確**：B3 之判準由「含任一 `PENDING: DR-`」改為「含
`PENDING: DR-{SPEC_GAP_DR}`」（該 leaf 之特定 DR 號）。
**提請裁定**，並請一併考慮：R-TM68 之 `lint_remarks_order` 同樣只驗排列
不驗齊全，**「該有的佔位有沒有」目前無任何閘門負責**。

### 5.3 **B-2 界線 —— 人工確認成立，但有一項但書**

下放包 T5 第 4 項要求人工確認「014 之 TC 不得涵蓋 SNA 送出規則」。

**驗證內容欄（test_item / pre / itd / procedure / ER）後，兩條 TC 之
procedure 與 ER 皆未測 SNA。** 但：

```
TC#8 / TC#9 之 test_item 上半：
  'The software shall transmit GPS-based date/time signals or SNA if unavailable'
                                                          ^^^^^^^^^^^^^^^^^^^^^^
```

**leaf 描述本身含 `or SNA if unavailable`**，而 canon §4.3.1 要求 test_item
上半逐字取自 `leaf_descriptions.txt`，不得改寫。

**故此處是 canon §4.3.1（verbatim）與 §8.2.1（B-2 界線）之張力**：
014 之需求描述本身就跨越了界線，而我方不得改寫需求。

**執行層之處置**：procedure 與 ER 只驗 GPS 值之送出，不驗 SNA；
並於兩條之 reasoning 明寫「**本條不涵蓋 SNA 送出規則** —— 該規則屬 022
（B-2 界線）」。**上半之 SNA 字樣保留，因 verbatim 不得改。**

**提請裁定是否足夠**，或需另加措施（如 Remarks 註記）。

**一項自我更正**：我首次以「TC 全文含 SNA」判定，得「**含 SNA**」；

**兩次都是判準過粗**（與 `14` §4.2 同族），但這次在報出結論前就發現。
