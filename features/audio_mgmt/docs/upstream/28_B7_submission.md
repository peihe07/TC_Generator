## 五、新增防線：生成後葉集核對（`scripts/leafset_check.py`）

**缺口**：既有差集核對於**下放前**執行，問「318 列是否皆有歸屬」。
它看不見「已裁入本批、生成時卻消失」之葉——那時批次已不在規劃階段。

**首版之缺陷（記錄，因其正是本案之教訓）**：初版以
「B{n}.json 之 req_id 集合 vs 該批 context」比對。**該比對對本案無效**
——221 是連 context 一併被移除的，兩邊一致，檢查綠燈。
**拿衍生檔比對衍生檔，證明不了任何事。**

**改版設計**：context **恆保完整裁定葉集**；不得交付之葉留在其中並帶
`held` 欄與理由，**不得刪除**。檢查斷言：

```
{req_id in B{n}.json} == {ruled leaves} - {leaves held with a reason}
```

且「標 held 卻無理由」與「標 held 卻有 TC」皆為 FAIL。如此，靜默丟葉
在結構上不可能——要丟就得寫下理由，而理由會出現在上繳包裡。

（曾試以剖析下放包散文取得裁定葉集，因 SYS-RA 號與他批葉之提及造成
大量誤報而放棄；`held` 欄之設計不依賴文件剖析，且對人為疏漏同樣有效。）
