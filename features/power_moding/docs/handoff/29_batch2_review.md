## 二、batch 2 之人讀覆核 —— **兩項實質、兩項輕微**

lint 32/32 只證明其合於已編碼之規則（R-PMH52）。以下為逐條人讀。

### 2.1 【實質】`-015` 之 Pre-Condition 含動作，且未依 §5.6 建立 baseline

`-015` PC2 逐字：`The current entertainment sounds volume has been recorded`

**canon §4.4 之自測**：「requires *do / check / **record*** → NOT a Pre-Condition」。
**`has been recorded` 是一個動作之完成，不是狀態。**

**且本條正是 canon §5.6 之典型情形**（before／after 比較）——
其要求「記錄步驟在 procedure、比較在 final ER」。現行：

| | 現行 | 應為 |
|---|---|---|
| 記錄 entertainment 音量 | **PC2**（違 §4.4） | **procedure 之一步**（`Read the current entertainment sounds volume and record it`） |
| 比較 | ER4 ✅ | 維持 |

**處置**：PC2 移為 procedure 之首個實質步驟；PC 只留
`Start-up sounds are supported and the setting is Always`。

### 2.2 【實質】`-014` 之 design_method 應為 EP，非 NEG

`Always`／`Once a Day`／`Never` 為**同一設定之三個等價類**，
`-012`／`-013` 皆標 **EP**，而 `-014` 標 **NEG**。

**canon §12 之 first-match**：`Negative / Invalid` 之條件為
**「Invalid input / illegal op」**。**`Never` 是一個合法之設定值，
不是無效輸入亦非非法操作** —— 其 first-match 落在
`Input partitioned valid / invalid` → **Equivalence Partitioning**。

**「其標的為不播放」不使其成為負向測試** —— 等價類之預期結果本就可為
「不發生」。

**同軸三值而其一異技術，與 R-PMH59 之精神（批內依據互不矛盾）相違。**

**處置**：`-014` 之 `design_method` 改 **`等價劃分 (Equivalence Partitioning, EP)`**；
其 `reasoning` 記明「本條為 §7 所要求之**負向配對**（enumerated supported items
須配至少一條 unsupported／否定情形），**惟其技術為 EP 之第三類**，
二者不同層 —— §7 講的是覆蓋，§12 講的是技術」。

### 2.3 【輕】`-009`／`-010` 之 PC2 未具名其來源與必要性

二者之 PC2 為 `The start-up sound setting is Always`／`goodbye sound setting is Always`。

**`SSND 1)` 未提及該設定** —— 其來源為 `SSND 2.1)`／`SSND 2.3)`（他 leaf）。
其為使本條之 ER 成立所必需（設定為 `Never` 時不播放），
**故該限定正當**，惟依 §8.5 與 R-PMH55(c) 之精神，
**其來源與必要性須於 `reasoning` 具名** —— 現行未具名。

**處置**：`reasoning` 補一句，記其來源 leaf 與「不加則 ER 於 `Never` 下不成立」。

### 2.4 【輕】`-014` 步驟 5 之檢查範圍與 ER5 不對稱

步驟 5：`Trigger the shut-down animation and check that no sound was played`
—— 其 `no sound was played` 讀來涵蓋**三次觸發**；
而 ER5 只斷言第三次（`No goodbye sound is played when the shut-down animation
is triggered`）。

**處置**：二擇一 —— 步驟 5 之檢查限於本步（`and check that no goodbye sound
is played`），或 ER5 擴為三次之總結。**分析層傾向前者**（ER3／ER4 已各自
承載前兩次）。

### 2.5 其餘逐項通過

`test_item` 上半皆為 `source_clause` 之逐字子句；括號下半各異；
`tc_title` 10～12 字；PC 除 §2.1 外皆為狀態；
`-011` 只驗選項存在而不驗行為（§8.2.1 不擴入 siblings）；
`-012` 之「兩次」為最小充分次數且不斷言上限；
`-013` 之「一日」未定義而以措詞繞過並具名；
priority P1×6／P2×1 且 `-015` 之 P2 依據與其餘不矛盾（R-PMH59）。

## 三、apparatus 凍結之範圍 —— **我立 R-PMH104 時漏寫了一件事**

28a §5 第 3 項指出：凍結後，`animation` 掃描
**「只可能因『已經出錯』而被排程」**。
28 §10 第 5 項另指出：R-PMH99(c) 之字串檢查**不及於 batch 2 之十二項限定**，
而擴及之即為新增檢查項，**故不做**。

**這兩項合起來，會使凍結產生一個我沒有預期之後果**：
**每一個新批次都會帶進其自身之新斷言與新限定，而依現行讀法，
它們永遠不能被掃描、不能被保護。**

**凍結若如此運作，等於「第一批之後不再驗任何東西」** —— 那不是我立條之意。

### 3.1 界定

| 類 | 例 | 是否為 R-PMH104 所凍結 |
|---|---|---|
| **檢查邏輯之增長** | 新增一支程式、新增一個 lint 項、新增一種判準 | **是，凍結** |
| **既有檢查對新資料之適用** | 既有 `spec_assertion_scan` 對一個新斷言（`animation`）跑一次、既有 lint 之限定字串檢查讀該批之限定清單 | **否，不凍結 —— 且為義務** |
| 既有檢查之一般化（28 §5.2） | 期望值由寫死改為讀該批宣告 | **否**（執行層已如此處置，正確） |

**判別法**：該動作**是否增加了「檢查什麼種類的錯誤」**。
增加者為凍結之標的；只是把既有種類套到新資料上者，不是。

→ R-PMH107。**`animation` 掃描與 batch 2 十二項限定之字串檢查，二者皆應做。**

## 四、裁決條文（逐條抄入 `RULINGS.md`）

```
R-PMH107（apparatus 凍結之範圍界定）
R-PMH104 所凍結者為**檢查邏輯之增長**，非**既有檢查對新資料之適用**。

判別法：該動作是否增加了「**檢查什麼種類的錯誤**」——
  增加種類者（新程式、新 lint 項、新判準）→ **凍結**；
  只是把既有種類套用到新資料者（既有斷言掃描跑一個新斷言、
  既有限定檢查讀該批之限定清單、既有檢查之期望值由寫死改為讀宣告）
  → **不凍結，且為義務**。

**理由**：每一新批次必帶進其自身之新斷言與新限定。
若其適用亦被凍結，則凍結等同「第一批之後不再驗任何東西」——
**非立 R-PMH104 之意**。

現行應為之二項（28 包 §10 第 1、5 項所指者）：
(a) `animation` 斷言之掃描（`-009`／`-010` 之 ER 含之）—— **應做**；
(b) R-PMH99(c) 之限定字串檢查**擴及 batch 2 之十二項** —— **應做**，
    其作法比照 28 §5.2 之一般化（讀該批之限定清單，非寫死 tc_id）。

依據：28a 上繳 §5 第 3 項 —— 執行層指出凍結後該掃描
「已不可能因『謹慎』而被排程，只可能因『已經出錯』而被排程」。
**該後果為分析層立 R-PMH104 時未寫明者。**
```

```
R-PMH108（`-013` 與 `-011` 之未定義項開 DR-PMH8）
下列二項為規格未定義而以措詞繞過者，**開 `DR-PMH8`**：

(a) `SSND 2.2)` 之「一日」**未定義其起算點**（午夜／點火週期／其他）——
    `-013` 現以「今日尚未播放過」與 `on the same day` 繞過；
(b) `SSND 2)` 之設定**未給其所在路徑** ——
    `-011` 現以「設定選單可達」繞過。

**DR 不在 R-PMH104 之凍結範圍內** —— 凍結者為檢查裝置，非對外詢問。

**其形態與 A-PMH22（`Else: Mute Active`）相同**：
以措詞繞過而不判讀，**繞過不使該未定義消失**，故仍須詢問。
執行層 28 §10 第 2 項自陳「未開 DR，因判其已由措詞繞過，
**惟該判斷未經裁定**」—— 本條即其裁定：**繞過與詢問並行，不互相取代。**

`DR-PMH8` 不阻斷 batch 2；若上游另有定義，`-013` 之步驟與
`-011` 之 pre-condition 須重寫。
```

```
R-PMH109（`-009` 之跨螢幕同步維持併入）
`Sounds will sync amongst all supported vehicle displays.` **維持併入 `-009`
之 ER4，不另立第三條**。

依據二項：
(a) canon §5.7 —— 其為同一觸發（駕駛門關閉引發之啟動音播放）之必然後果，
    **非另一觸發**；
(b) 該句**無其自身之觸發** —— 其主語為 `Sounds`，
    描述已在播放之聲音如何分佈，不描述何時開始播放。

**執行層 28 §10 第 4 項所提之另一讀法（其為獨立能力，則 leaf 012 應拆三條）
不採**，其理由：若視為獨立能力，則該 TC 之觸發仍須借用 `-009` 之門關閉，
**兩條將共用同一觸發而只在 ER 上不同** —— 正是 §5.7 所禁之拆法。

**惟其限度須具名**：本條只涵蓋**啟動音**之跨螢幕同步；
**告別音之跨螢幕同步（`-010`）未被任何 ER 斷言** ——
`-010` 之 ER 只驗其與關機動畫之同步。**登記為覆蓋缺口，不另立 TC**
（其屬同一 `Sounds will sync` 句，若上游確認該句涵蓋二者，
則 `-010` 之 ER 須增一條）。**併入 `DR-PMH8` 詢問。**
```
