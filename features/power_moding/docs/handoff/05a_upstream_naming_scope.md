## 二、裁決條文（抄入 `RULINGS.md`）

```
R-PMH26（上游 037 報告命名之範圍界定）
上游 037 報告之檔名一致性**不在本 feature 之驗證與處理範圍內**。

具體拘束四項：
(a) 不得就 037 檔名之形態差異開立 DR，不得產生要求上游改名之建議或
    回報；
(b) 不得以「上游命名將趨於一致」為前提設計任何欄位、判準或腳本；
(c) 037 檔名之差異不得登記為 anomaly —— 它不是缺陷，是本 feature
    無權處置之外部事實；
(d) 若某判準之正確性取決於上游命名一致，該判準即不成立，須改用不依賴
    命名之判準（例如以檔案 SHA256 或其在 `inputs/` 之台帳編號指稱）。

依據：Pei 於 2026-08-24 之裁定（逐字見 05a §一）。

適用範圍為上游之**命名**。本 feature 自身欄位（如 D5）要不要引用該檔名，
屬 Q3，與本條無涉。
```

## 三、對 Q3 之影響 —— 我要先講清楚一件事，免得你據誤解而裁

**案（乙）不需要上游改任何東西。** 它只是把上游現有的檔名逐字抄進 D5，
抄什麼是什麼。所以「不能要求他們改」本身**不構成排除案乙之理由**。

但你這句話指出的方向，在語料上確實有兩個硬的支撐：

**一、`V0.1` 是版號，會過期。**
本 feature 之 037 逐字為
`FM-WI-FSM-037-A03-N1L-SWE1-PowerModing-HMI-V0.1 STLA 報告.xlsx`。
上游只要出 V0.2，我們寫進 D5 的字串就變成錯的，而**沒有任何機制會通知我們**
——這正是 R-PMH26(d) 所講的「判準取決於上游命名」之情形。
Popup 已經是 **V0.2**（`…-SWE1-Popup-HMI-V0.2 STLA 報告.xlsx`），
證明版號確實會動。

**二、有些 feature 根本沒有「單一份 037」可寫。**
實測 `ASW-R2` 全樹之 037 檔（唯讀掃描，`**/*037*.xlsx`）：

| feature | 037 份數 |
|---|---|
| **VF230** | **11** |
| **CFTS044** | **4** |
| Vehicle Settings（根層，VF665／BedLowering／VehicleCategory） | 4 |
| 其餘各 feature | 1 |

VF230 之 036 只有一格 D5，卻對應 11 份 037 —— 它填的
`FM-WI-FSM-037-A03_SWE1_VF230_STLA 報告_SWRA_STLA`
是把 11 份共同的前綴截斷後充數，**不是任何一份真實檔名**。

**這解釋了為什麼這欄從未穩定**：案乙在「一個 feature 一份 037」時才良定義，
而全案並非如此。本 feature 恰好是一份，但據此立的規則無法外推。

**故 Q3 之兩案，其真實差別為**：

| 案 | 代價 |
|---|---|
| （甲）留空 | 交付件少一項資訊；與母體最大群一致（9/16） |
| （乙）填 037 報告全名 | 需承擔版號過期之風險，且該值無機制維護 |

**請你裁一個字。** 我仍不提案 —— 上面兩點是把代價講清楚，不是替你選。

## 四、附帶：一項連帶收緊

R-PMH26(d) 對本 feature 已有一處適用：`inputs/MANIFEST.sha256` 之四份素材
目前以**檔名**列示。依 (d)，其指稱應以 SHA256 為主、檔名為輔 ——
台帳本來就記了 SHA256，故本項**已滿足，不需改動**，僅記明其滿足之理由，
以免日後有人把台帳改成只記檔名。
