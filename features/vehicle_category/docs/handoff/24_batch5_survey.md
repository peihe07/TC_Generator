### 1.3 `038-03` 之不拆:**推翻——判拆,理由是覆蓋洞,非「二觸發」形式論**

你們的壓測(「同一規則之二個邊界」)在規則層面成立。
但逐 ER 檢視後,**不拆的實質後果是一條路徑無 TC 可抓**:

| 離開路徑 | 何處被驗 |
|---|---|
| 使用者按 X → 彈窗消失 | `038-03` 之 ER 3 ✅ |
| **系統完成 → 彈窗消失** | **無** —— `038-03` 之 Procedure 只走 X;`038-05` 未完成支第 3 步等到完成後,記錄的是**語言清單**非彈窗 |

§8.2.2 壓測換個問法:「**完成時彈窗不消失**」這個失效,
現有 16 筆哪一筆會 FAIL?——**沒有。**

且該洞有連帶:`038-05` 未完成支第 3 步等完成後驗「選項不再灰」——
**若彈窗該消失而未消失,它可能正擋著清單**,該步之 FAIL 會發生
但原因混淆(灰化未解 vs 彈窗未關)。補拆後,「完成 → 彈窗消失」
成為該步之明確前置。

**裁:`038-03` 拆 2**(X 路徑/完成路徑),同 req_id,
括號下半以離開條件區分。第 4 批 16 → **17 TC**,`split_delta: 2`。
你們把判讀記在 reasoning 而非埋掉,使本裁定成為可能——
**這正是「記明」的用途:不是免責,是讓下一雙眼睛有東西可推翻。**

### 1.4 `split_flag`:**裁甲**(維持全 `False`,明文不用)

理由三:
1. 拆分資訊**已有承載者**且受檢:`split_delta`(第 15 項驗宣告 vs 實際)
   + 同 req_id 之重複(工作簿處置)。二欄再填是第二來源,二來源必分歧。
2. canon 對 `split_flag` 之語意無判準(標什麼?拆分產物?被拆母體?),
   填 `True` 是在無定義下造語意。
3. 回溯改四筆屬既交付之改動,其收益為零(見 1)。

**記入 profile**(新條):本 feature 之 `split_flag` 恆 `False`、
`split_reason` 恆空;拆分之權威紀錄為 `split_delta` 與 req_id 重複。
