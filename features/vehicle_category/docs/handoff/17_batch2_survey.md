## 二、profile 機讀行：**准**

執行層自行增設 `values(<tab>) = Controls | Settings`，報備並自陳可推翻。

**准。** 其論證成立且與既有慣例一致：值域若只有中文說明，
verifier 須另存一份或解析中文 —— **二處分歧即無承載者**，
而「須同時更新」若無承載者只是規定。

正當性之根源是**單一來源**：值域寫兩處必然分歧，寫一處則不會。
profile §5 之常數表本就兼具人讀與機讀性質（`ENTER_VC_TAB(<tab>)`
之模板已是機讀形式），機讀行不是新增性質，是把已有的性質寫完整。

**惟加一項拘束**（T95）：機讀行之**格式**須於 profile 內明文固定
（前綴 `values(`、參數名、`=`、`|` 分隔），否則日後另一個帶參數常數
會出現第二種寫法，分歧從值域移到了格式。

## 三、R-VC19 之擴充 —— 第 2 批出現二種新來源記法

### 3.1 事實（分析層粗查，待執行層重測）

第 2 批 30 leaf 之 `Description` 中，出現 R-VC19 未涵蓋之記法：

| 記法 | leaf | 逐字 |
|---|---|---|
| **彎引號 `“…”`**（U+201C／U+201D）| `VC-042-01`、`VC-043` | `replaced with an arrow (“>”)` |
| **方括號 `[…]`** | `VC-043` | `[Example: Language (English) >]` |

方括號尤須注意：IN §11 明文
「Square brackets `[...]` … MUST NOT appear in TC output fields」，
其保留給本文件之 placeholder 語法與 sibling row 標記。
**但此處之方括號是來源原文**，落在 `test_item` 上半之 verbatim 區段內。

R-VC19(d) 明文：「本例外不及於 `«...»` 以外之新記法。
若日後出現第三種來源記法，**須另裁後始得納入，不得類推**。」
**本節即該另裁。**

### 3.2 裁定：改為通則，機器保護移至來源驗證

逐一列舉記法之代價是**每遇一種新記法即需一輪往返**，
而其所買到的保護（「新記法須經人檢視」）**已由 R-VC19(c) 承擔** ——
(c) 要求保留之記法須對得上所引之來源列。

```
R-VC23（R-VC19 之擴充：來源記法之通則化）

R-VC19(a) 之「037 `Title` 之 `'...'` 與 `Description` 之 `«...»`」
之列舉式範圍，**擴充為通則**：

  `test_item` 上半之 verbatim 區段內，**凡逐字出現於所引來源列
  （037 `Title`／`Description`，或 R-VC7 所定之 SYS1 權威複本）
  之記法，一律逐字保留**，不改寫、不正規化、不轉為 `"..."`。
  含但不限於：`'...'`、`«...»`、彎引號 `“...”`、方括號 `[...]`、
  角括號 `<...>`。

R-VC19(b)(c)(d) 之其餘拘束**不變且更形吃重**：

(b) **作者之散文一律 `"..."`**，無例外。本條擴充之範圍
    **僅及於 verbatim 上半**；procedure 之按壓標的、非引用之 ER 行、
    括號下半、reasoning，一律 `"..."`。
(c) **每一個保留 token 須對得上所引之來源列** ——
    即該 token 逐字出現於該 leaf 之 `Title`／`Description`／SYS1 對應句。
    **本條為通則化後之唯一實質保護，其驗證須逐 token 為之，
    不得抽樣。**
(d) 原「新記法須另裁」之要求**作廢** —— 其保護已由 (c) 承擔，
    且逐一列舉之往返成本高於其邊際保護。

**IN §11 之方括號禁令於本例外之範圍內讓位** ——
該禁令之立意為「禁止作者使用方括號」，非「禁止引用含方括號之原文」。
作者自書之方括號仍禁（(b) 所轄）。

即時適用：`VC-042-01`／`VC-043` 之彎引號與方括號，
於其 `test_item` 上半逐字保留。
```

### 3.3 lint／verifier 之配套

第 7b 項（保留記法對得上來源）於第 1 批報「保留 token 0 個」——
其 PASS 讀作「本批無保留記法」而非「保留記法皆已驗證」（上繳包 16 §9 已揭露）。

## 四、第 2 批 `Settings List` 之勘查（30 leaf）

> 以下為**分析層粗查**，量自 037（SHA256 `cb80a77e…d877ed`）之
> `Requirement Description`。依 R-VC15，本節之判讀不得沿用，
> 須由執行層重測；列出以使勘查聚焦。

### 4.1 五項風險

**(1) 二筆之 Description 疑似被截斷**

```
VC-046-05  … If user picks list item by pressing the knob, the system switches to next lev
VC-051-03  … the user will be taken back to the settings screen t
```

二者皆止於半個詞。須確認係 037 儲存格自身截斷，
或分析層讀取時之長度限制所致 —— **前者為異常須登記，後者為我的量測問題**。
以 SYS1 對照（R-VC7）取其完整句。

**(2) `VC-048-02` —— 本批第一個拆分候選**

```
Confirmation tone shall be played whenever a settings value is modified,
with the exception these settings: Clock Hours / Minutes, Audio Settings,
Phone/Bluetooth Settings.
```

IN §7 明文：**列舉之支援項須配對至少一個不支援之負向 TC**。
本 leaf 同時載正向規則與三類例外 —— 依 IN §8.2.2
（RD sub-id ≠ TC count），其**二個獨立之部分失效**
（一般設定無確認音／例外設定卻有確認音）在單一 TC 下皆判 fail，
**判準不明**，應拆。

第 1 批預估「無需拆分」且事後成立；**本批不得沿用該預期**。
勘查須逐筆施用 §8.3 之壓力測試，回報拆分候選。

> 本筆即 FROP = `Audio Management` 之唯一一筆（下放包 02 §4.4）。
> 表 A 之揭露須標其落於第 2 批。

**(3) 具體數值可用，且為 boundary 材料**

```
VC-049  press & hold > 500 ms → 1 step each 200 ms（Clock／equalizer／
        Balance-Fade／Engine Off Idle Timer／Fleet Vehicle Settings）
VC-050  press & hold > 500 ms → 1 step each 500 ms（Brightness Settings）
```

二者皆 spec-sourced，可用。**二筆為 sibling** —— 觸發門檻相同（500 ms）、
速率不同（200 vs 500 ms）、適用對象不同。括號下半須以**適用對象**區分，
不得僅以速率區分（速率是後果不是情境）。

500 ms 為 §8.3 之 boundary 軸材料 —— 是否拆為
「< 500 ms 不連續增減／≥ 500 ms 連續」由勘查判定。

**(4) `VC-040`／`VC-041`／`VC-044` 依賴 `HMI Settings List`**

該素材**已在手**（`inputs/`，R-VC10）。但須勘查確認其**確實載有**：
- `VC-040`／`VC-041`：category 之層級結構
- `VC-044`：list items 之**順序**

> 與第 1 批 `VC-011` 之 `the table` 不同 —— 該筆未具名故 PENDING；
> 本三筆**明確指名** `HMI Settings List`。若該素材確載其內容，
> **不需 PENDING**；若查無，則為新缺件須登記。

**(5) 三筆帶 `(image: imageNN.png)`**

`VC-040`（image13）／`VC-041`（image14）／`VC-053`（image15）。

依 R-VC7 與 R-VC12 二：圖內內容**不得以視覺判讀充當實測值**。
