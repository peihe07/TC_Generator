## 三、`owner` 正則缺陷：**修**，且修前修後須並列

### 3.1 裁定

**修。** 成本為一個正則，而其噪音**正落在 9 個之中的二個**（`2`／`4`）——
單位數 section 最易被「下放包 29 §3.3」「包 2」「第 4 項」這類截段污染。

**但修完須重跑，並出修前修後之差異表**：

```
比較 107／61／18／9 四個數字之修前修後值，
並逐一列出：因修正而**消失**之標的、因修正而**新增**之標的。
```

消失者即噪音之具體證據；**新增者須特別注意** ——
若修正使某標的首次進入高優先，那是原本被噪音**淹沒**的真候選。

### 3.2 修正之範圍限定

**只修 `owner` 之偵測（擁有者在數字之前者），不動其他任何判準。**
不得順手調整 `NEG`／`POS` 語彙表、不得調整第一層之剔除類別 ——
一次只動一個變數，否則差異表歸因不明。

**self-test 前置**：
- (b) 已知標的 = `A-VC21` 正文之「下放包 29 §3.3」→ **須被判為 owner，剔除**
- (a) 反向 = 一個真正的規格節引用（如 tableB 之「§3.3」若存在）→ **須保留**
- 若二者在文字上無法區分，**停並回報** —— 那意味著本修正不可行

## 四、同檔內牴觸：**不做第三判準**，補網移至加註紀律

### 4.1 為何不做

同檔內之多次提及**絕大多數為正常**（一條裁決會多次提到同一節）；
拿掉跨檔要求即爆量，而其新增之真陽性率無從預估。

**且 R-VC12 之形態更深一層**：二(a) 與其餘各款**同屬一個條目**，
即使做到「同檔跨條目」也抓不到 —— 要抓它須把條文切成款、款間比對，
**成本高而收益不確定**。

### 4.2 補網：R-TM13 之加註本身就是機會，只是沒被用上

R-VC12 二(a) 之錯**存活 24 個包**，其根本原因不是沒有工具，
而是**它從未被加註過** —— 直到 R-VC27 才第一次有人動它。

**加註是唯一一個「必然要讀原文」的時刻。**

**PLAYBOOK 增一則（建議位階，T161）**：

```
條文之某款被作廢、修訂或加註時，須讀**該條全文**，
並確認其餘各款不因該款之變動而失據、不與該款之新處置牴觸。
於加註中記明「其餘各款已複核」或列出受牽連者。

由來：R-VC12 二(a) 之錯存活 24 個包 —— 它從未被加註過。
加註是唯一一個必然要讀原文的時刻，該時刻不做內款複核，
同條目內之牴觸即無任何機會被發現（`ledger_xref` 與其粗篩皆為跨檔，全盲）。
```

### 4.3 盲區逐字記入

`ledger_xref` 之說明與 profile 之相關節，須記：

```
本工具與其粗篩之偵測範圍為**跨檔**。
同一檔內、尤其同一條目內之牴觸，**全盲**。
R-VC12 二(a) 之所以被發現，是因其恰好跨檔（DR-VC6 記對、RULINGS 記錯）；
同型而不跨檔者不會被發現。其補網為 PLAYBOOK 之加註內款複核（紀律，無承載者）。
```
