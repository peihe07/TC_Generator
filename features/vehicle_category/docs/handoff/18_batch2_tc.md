## 二、第 7b 項之強化提案 —— 消除樣式表之限制

### 2.1 上繳包 §6 之揭露指出一個真缺口

> R-VC23 通則化後，**掃不到即等於未受保護** —— 第 7b 項只驗它認得的 token。
> 這是通則化之代價：條文不再限制記法，但檢查器仍受其樣式表所限。

**該揭露正確，且其代價比表面更大**：R-VC23(c) 是通則化後之
**唯一實質保護**（我在該條文裡自己寫的），而它現在建立在一張
會漏的樣式表上。`「…」`、`｢…｣`、以及任何未來出現之記法皆在其外。

### 2.2 提案：由 token 比對改為**整段子串比對**

`test_item` 上半依 R-S4 為「需求／規格原句 verbatim」，
依 R-3 得摘句（token ≤ 50），依 R-4 得將句首字母轉大寫。

**故其應為某個來源字串之逐字子串**（首字母正規化後）：

```
判準：test_item 上半（去首尾空白、首字母大小寫正規化）
      ∈ substring( 037 Title ∪ 037 Description ∪ SYS1 對應句 )
```

**此判準之性質**：
- **不需樣式表** —— 任何記法自動受驗，因為整個字串都要對得上
- **強於 token 比對** —— token 對得上而其間之文字被竄改者，token 比對抓不到，子串比對抓得到
- **零閾值、可機械化、無語意判斷**

其與第 16 項（續行型 leaf 上半與 SYS1 完整句逐字相符）之關係：
**第 16 項是本判準之特例**（該 4 筆之來源限定為 SYS1 且要求全句相符）。
二者不衝突，第 16 項更嚴，保留。

### 2.3 但須先回歸，不得逕行取代

**本提案為更強之判準，可能使既有 34 筆（pilot 12 ＋ 第 1 批 22）FAIL。**

執行順序（T99）：

1. 先**只跑不判** —— 對既有 34 筆計算其上半是否為三來源之子串，
   **逐筆回報結果**，不改變其收斂狀態
2. 若 34/34 通過 → 第 7b 項改為本判準，token 比對降為輔助（或移除）
3. 若有不通過者 → **停並回報其 leaf 與不符之處**，不自行調整判準亦不改 TC

**第 3 種情形不預設處置** —— 不通過可能意味著：
(a) 該筆之上半確實有問題（則為真陽性，須修 TC）；
(b) 摘句規則允許之形態超出「單一來源之子串」（則判準過嚴，須修判準）。
**二者之處置相反，須看實例才能裁**，不得預先擇一。

| leaf | `Description` | `Title` |
