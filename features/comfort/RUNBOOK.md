## 判準 vs 用詞禁令（22 §4，2026-08-15 記入）

> rev1 是 `is readable`，rev2 是 `is recorded`，兩者都把主詞放在觀察者身上。
> rev2 改的時候，以為問題是「readable 這個字」，實際問題是「ER 的主詞是誰」
> —— 換字沒有換主詞，所以錯誤原樣搬了家。
> **用詞禁令我可以繞過而不自知，判準不行。**

與 **R-C13**（零命中須換路徑而非下結論）、**R-C18**（截斷欄位不得用於判讀）
同源：**以表徵為判準者，其失敗形態是靜默的。**

實務上之兩條推論：

1. **寫 gate 時，先問它檢查的是表徵還是判準。** 檢查表徵者（禁某字、
   數某數）能擋住重複同一個字面錯誤，擋不住同一個判斷錯誤換個寫法。
2. **改動點不等於審視點。** rev2 親手改過的那幾行 ER 仍帶 `is recorded`；
   TC-014 之 PC 區塊因 rev2／rev3 皆未改動而三輪未被重讀。
   前者是「改過所以以為看過」，後者是「沒改過所以沒看」——
   兩者都不是「看過而判斷錯」。

## anomaly 編號之例示寫法 —— 用 `A-CF-XX`，不用真數字

`anomaly-id-registered` gate（26 §4.2）掃 `features/comfort/docs/` 全部
`*.md` 之 `A-CF\d+`，凡未見於 `ANOMALIES.md` 者即 FAIL。**上繳包與下放包
都在 `docs/` 內**，所以在文件裡舉例一個不存在的編號會把自己抓出來。

上繳 17 就是這樣撞的：反向驗證那段逐字寫了測試用的編號，lint 隨即 FAIL
並指名該上繳包本身。

**gate 沒有錯** —— 它的規則是「docs/ 內引用之編號須已登記」，而上繳包確實
在 docs/ 內。代價是反向驗證之過程無法逐字記載。

**約定（29 §5.3）**：例示一律寫 **`A-CF-XX`**，編號位改為非數字，
不匹配 `A-CF\d+`，故不觸發 gate。

**不要做的事**：不要為了寫文件而放寬 gate 的 pattern，也不要把例示用的
編號真的登記進 `ANOMALIES.md`。前者讓真正的孤兒編號溜過去，後者在
anomaly 台帳裡塞一筆不存在的異常 —— 兩者都是為了文件方便而弄髒機制。


## 拆與不拆 —— 「測試設計上的重複，不是需求上的區別」

同一節、同一 parent、外觀相近的兩個 leaf，**拆與不拆的方向可以相反**。
批次 2 之 `024-02` 與 `024-07` 即一組對照：

| | `024-02`（七項連動）| `024-07`（四個破壞源）|
|---|---|---|
| 結構 | **一個 trigger → 七個 outcome** | **四個 trigger → 同一個 outcome** |
| 判準 | §5.7：同一 trigger 之必然後果屬同一 TC | §8.2.2：不同控制實體 → 拆 |
| 處置 | **一條**，七行編號 ER | **四條**，同溯該 leaf |

**不拆 `024-02` 的理由**：拆成七條會產生 spec 不存在的區別，而每條都要
重按一次 MAX DEF —— 那是**測試設計上的重複，不是需求上的區別**。

**拆 `024-07` 的理由**（我第一次判錯，30 §1 推翻）：

- **§8.2.2 之控制實體判準是「條件」，不是「許可」。** 我讀成「允許不等於
  要求」，漏了同條後半：different control entities → **split**。
- **locatability 不是 §8.3 的判準。** 我以「編號 ER 可定位到第 4 行」
  為不拆理由，但 §8.3 問的是 **pass/fail verdict 是否明確**。編號 ER 解決
  的是**失敗報告的粒度**，不是**判定的粒度** —— 四個獨立行為共用一個
  verdict，fail 只有一個意思：「其中某項壞了」。
- **最直接的證據是同批的不一致**：A/C、AUTO、MAX A/C 三個破壞源各自成條
  （因為 037 各給一個 leaf），而溫度／RECIRC／mode／再按 MAX DEF 性質完全
  相同，只因 037 併在一個 leaf 就變一條。**TC 的切分因此取決於上游的分節
  習慣，而非行為的獨立性。**

§8.2.2 前半（不得再分解、合併 RD）管**溯源**，後半（TC 數不受 RD 數拘束）
管**驗證粒度**，**兩者不互相決定**。

**進度以 leaf 計，工作量以 TC 計。** 自 `024-07` 起兩者不再可互換。

不回報的逾越，與沒有授權機制是同一回事。

改 gate 時的兩條路也記下來：**放寬**（重覆即通過）會讓該 gate 原本擋住的
錯誤一併通過；**改判**（重覆合法但每列須宣告拆分）使裁定的條件本身成為
機械要求。判別方式在 R-C32：改判後的 gate，於該裁定**不成立**之情形仍須 FAIL。

### 放寬幅度必須可量（2026-08-17）

R-C32 管**該不該放寬**；本則管**放寬了多少要看得見**。

`spec-ref-sr25` 原式為 `if "SR25" in ref` —— 對整串 `specification_reference`
搜 `SR25`。89 §3 核可引用一份自身版本即為 SR25 之外部文件（HMI Settings
List），該 gate 立刻 FAIL。

**那道 gate 沒有錯，是它的範圍寫得比它的理由大**：R-C1 禁的是
**Comfort spec 之基線為 SR25**，不是「任何文件的名字裡不得出現 SR25」。
改為逐段檢查 ＋ 以身分豁免已認可之外部出處。

**關鍵在反向驗證的第二案**：

```
已認可清單中帶 SR25 者恰為一件 → 豁免之窄度可量
```

**一道被放寬的 gate，其放寬幅度必須可量** —— 否則下次沒人記得它寬到哪裡。
第一案（Comfort stem 之 SR25 仍會被抓）證明它還擋著該擋的；
第二案證明**它讓過去的只有那一件**。**只有前者，是一半的證明。**

## gate 的詞表：canon 以外的項須具名授權，手查習慣不算

`forbidden-verb` 上線時我在 §5.1 的九詞之外自行加了 `locate`——因為
批次 2 初稿用過它、我手查時覺得不妥。

**它與 canon 抵觸**：§5.6 的**正面示例**就是
`Locate the phone and record its A2DP and HFP status shown in the list`。
`locate` 是定位動作，不把判斷推給測試員。**那個 gate 以機械形式固化了一個
canon 明文推薦的寫法之禁令**，撐了一批才被抓掉（32 §2）。

**通則**：gate 之詞表若含 canon 以外之項，須於該 gate 之註解**具名其來源
與授權依據**；無授權依據者不得入表。

**手查時的個人習慣不是授權依據** —— 它在手查階段只影響一次判斷，
入 gate 後影響全部後續批次。這跟 R-C26（豁免不可自取）是同一件事的另一面：
**禁令同樣不可自取。**


## 「On vehicles with X」判別 —— 候選產生器，不是判準

批次 3 我立了一個判別：**條文有無「On vehicles with X」型選擇子**，
用它判定 2.2 之 8 條無需配置類 PC。我在上繳包裡自陳「這是本包最需要被
檢驗的一句話」——**風險在同一批內就實現了**（33 §4）。

**它是詞彙型代理判準**：

| 用途 | 可否 |
|---|---|
| 有選擇子 → 需要軸 | **可** —— 產生候選 |
| 無選擇子 → 不需要軸 | **不可** —— 陰性結果只是索引層事實（R-C13）|

**本案之實質答案**：2.14 明文 `no HVAC screens` —— 3 旋鈕 ICS 的車輛
根本沒有氣候觸控畫面，2.2 的 8 條在那種車上**沒有一條可以執行**。
判別產生的候選是空的，而實質答案不是。

**同源**：§5a（代理不得凌駕實質）、R-C13（零命中須換路徑）、
R-C18（截斷欄位不得用於判讀）、22 §4（用詞禁令可繞過而判準不行）。
**以表徵為判準者，其失敗形態是靜默的** —— 而這次它甚至通過了 37 個 gate。

## 037 與 spec 衝突：單位歸 037，內容歸 spec

2.1 的條文說 `up to 4 tabs` 含 Massage，037 的 leaf 說 3 tabs 不含 Massage。
我判「現行條文未涵蓋」，那句對 §8.6 而言正確（它管的是 spec 與其索引，
不是 spec 與上游分析），但 **§8.1 有「Conflict → Req wins; flag RD」**，
與 §8.2 併讀即得分工。已立為 **R-C33**。

記憶點：**037 決定的是「這份 spec 被切成幾個要求」，不是「這份 spec 寫了
什麼」。** 把後者也讓給 037，等於讓一份分析報告改寫它所分析的對象。

**委派的是行為，不是存在**：2.1 說 `Refer to separate HMI Logic and Flow
documentation for Massage Seats logic` —— Massage tab **是否顯示**由 2.1
擁有，Massage tab **按下去做什麼**不由 2.1 擁有。


## 沒有任何機械檢查會問「這條在哪種車上跑不起來」

批次 3 之 §4.1 判別失效時，我在上繳包裡寫下的自述，逐字留在這裡（34 §6）：

> **判別產生的候選是空的，而實質答案不是。**
>
> 我在上繳 21 §10.1 自陳「這是本包最需要被檢驗的一句話」，並把它寫成
> 可反駁的形式。**風險在同一批內就實現了** —— 而且它通過了全部 37 個
> gate、通過了我自己的 §9 十七項自評。
> **沒有任何機械檢查會問「這 8 條在哪種車上跑不起來」。**

**這句話定義了一整類 gate 抓不到的缺陷**：gate 檢查的是 TC 寫得對不對
（欄位、格式、溯源、1:1、主詞），**不是 TC 在哪種車上有沒有東西可以操作**。
後者要靠一個實質問句：

```
在哪一種車輛配置下，這條 TC 沒有可操作的對象？
```

**不是問**「該節條文有沒有選擇子」（代理判準，已限縮為候選產生器）。
**不是問**「lint 有沒有報」（R-C23）。

回溯複查（34 §1）即以此問句對既有 31 條施行，補出 18 行 PC。
**那 18 條在被問之前，全部是綠的。**


## 「答了」不等於「答對了」—— interface-axis-answered 的界線

`interface-axis-answered`（36 §6）驗的是**R-C34 之義務有沒有被履行**，
不是**答案對不對**。這條界線有一個現成的實例，記在這裡：

> 我在上繳 24 對 `3.1` 之 `emea_ics` 答過「mirrored」，
> **那個答案是錯的，而任何 gate 都不會知道。**

逐節建 `ch16_mirror_map.tsv` 之後才看清 `16.12.1` 對應的是 `2.12.2`，
不是 `3.1` —— 兩者皆述 Mode hard control 而所屬體系不同。
那一欄從頭到尾是綠的。

**推論**：凡「記錄一個判斷」型的 gate，其綠燈只證明欄位被填了。
要驗答案本身，需要的是**另一份獨立導出的資料**（此處即鏡射表），
而不是更嚴的欄位檢查。

同源：R-C23（自評不得以 gate 通過充數）、35 §4 之
`axis-value-count`（驗登記而非驗判斷）。


## 比對之前，先確認比對的兩側都真的存在

驗證基礎設施自己壞掉、產生假結果，本 feature 已發生**兩次**：

| 次 | 現象 | 假結果之方向 |
|---|---|---|
| 1 | zsh 之 `${PIPESTATUS[0]}` 取到空字串（zsh 用 `pipestatus`，且 1-indexed）| 假 **FAIL** —— R-C9 驗證項 3 被誤報為失敗 |
| 2 | `/tmp/base` 是既存**檔案**而非目錄，`mkdir` 失敗、`cp` 未成，`cmp` 遂與不存在的檔案比對 | 假 **FAIL** —— 19 檔全報 DIFF，而基準根本沒被建立 |

**兩次都是假 FAIL，方向安全 —— 但下一次未必。** 一個假 PASS 長得跟真 PASS
一模一樣。

**通則**：凡以比對為驗證手段者，**先確認比對之兩側皆實際存在**
（目錄非空、檔數相符、基準確實被寫出），再讀其結果。

作法上：比對前印出兩側之檔數並斷言相等，比印出「PASS」有用得多 ——
`cmp` 對不存在的檔案不會沉默，但迴圈裡的 `||` 會把它變成一行 DIFF，
和真正的內容差異長得一樣。

**與「一個失敗的比對，其失敗原因可能在比對本身」同一件事**：
看到全部都 DIFF 時，先懷疑比對，不要先懷疑被比對的東西。


## 節級看開頭，TC 級看那一句

`ch16_mirror_map.tsv` 把 `16.14 ↔ 2.14` 記為 `mirrored`，依據是「首二句逐字
相同」。**而 ICE13 全文就只有那兩句** —— C15 的 3 旋鈕 ICS 整段在 ch16
根本不存在。`16.17 ↔ 2.16` 同理：首句一樣，而 16.17 只有一句。

> **節級 `mirrored` 之依據是「開頭一樣」，TC 級要問的是「這條所驗的那一句
> 在不在」。**

這是 R-C36-1 存在理由的最短表述。節級強度只給預設答案與證據出處；
**預設不等於免答**。逐條補答 45 條時，這句話值 6 條過嚴的排除式 PC。

## gate 的紅綠，對應「違規」而非「待裁」

`emea-per-tc-answered` 對 verdict 非 `yes` 者**不變紅**，改以具名回報行輸出。

> gate 之紅綠應對應「**是否違反已定之規則**」，不對應「**是否有待裁決之事**」。
> 待裁事項以具名回報行呈現。

理由：**紅燈會製造壓力，而壓力會催生未經授權的處置。** 若 gate 因「否」
而變紅，執行層會被推著自行移除那 6 條 —— 而移除是裁定，不是 lint 能逼出
來的東西。

同源：R-C24（豁免須為具名回報行而非靜默跳過）—— 兩者都是「讓機制說話而
不讓機制代替判斷」。

## 橡皮圖章 —— 清旗之前先問「有沒有新東西可看」

42 §1 立 `provisional` 旗標時，觸發條件寫成「**任一側**之 Test Set 全數生成
之日」。實測 632 列到期，而**其中兩側皆已生成者為 0**。

> `provisional` 的**成因**是「某一側沒有 TC」。
> 會觸發的那一側，正是**已經有 TC** 的那一側。缺的那一側仍然缺。

所以那 632 列的「重新確認」，可用證據與當初判定時**完全相同**。
再看一次不會看到新東西，能寫下的**只有一個橡皮圖章**。

**執行層當時未自行改觸發條件，而是如實留下紅燈** —— 改觸發條件是改裁定，
不是落實裁定。43 §1 據此改邊：觸發改為「該列中**原本未生成的那一側**補上
之日」，改後 632 → 0。

**通則**：一個要求「再確認一次」的機制，其觸發點必須落在**證據改變的時刻**，
不是落在任何一個看起來相關的時刻。兩者之差別在紅燈亮起時看不出來 ——
紅燈只說「有事沒做」，不說「做了會不會有用」。

**自查一句**：清掉這個旗標之前，我看得到什麼是當初看不到的？
答不出來就不要清，回報。

## 未見過紅燈的 gate，等於沒被驗過

`verify_provisional_gate.py`／`verify_axis_gate.py` 之存在理由：

> **條件接錯與條件被滿足，印出來的綠色是同一種綠色。**

故驗證須**雙向**斷言：該響時響、不該響時不響。只驗「該響時響」會漏掉
一個永遠會響的 gate；只驗「不該響時不響」會漏掉一個永遠不響的 gate。

兩項寫法上的要求：

1. **import 出貨的那份判準，不要重寫一份。** 重寫一份判準去驗另一份，
   驗到的是「兩份判準是否一致」，不是「判準是否正確」。
2. **案例要包含「舊版會答錯的那一個」。** 42 §1 之舊觸發條件通過了它自己
   全部五個案例 —— 因為那五個案例都在斷言 predicate 做了什麼，
   沒有一個在斷言那面旗子**是什麼意思**。43 §1 改邊後補的第五案
   （「已生成側之組完成、但對造仍缺 → 不該響」）就是舊版會答錯的那一個。

同源：R-C37（樣本須含陰性側）。**一個只驗陽性側的 gate 驗證，
與一個只取陽性樣本的歸納，是同一個錯誤換了層。**

## 數字對不上，是唯一的線索

43 §1 改完觸發條件之後，`provisional-sibling` 之 FAIL 數應為 26
（批次 6 使 `16.2`／`16.14`／`16.16` 首次生成，對造補上者 26 列）。
實際印出 **10**。

那 16 列的差額，是重建自己把 `provisional` 由 `true` 改成了 `false` ——
**在 gate 要問問題的那一刻，機器搶先蓋了橡皮圖章**。若沒有那個「26」，
lint 會是綠的，清旗會不曾發生，而沒有任何一個檢查會出聲。

> **量測不是為了報告，是為了讓後續的異常有參照物。**
> 先量後改，那個「先」是它全部的價值所在。

三項可操作的推論：

1. **改機制之前，先把它現在的輸出記下來**，哪怕看起來無趣。
   改完之後第一件事是比對，不是看綠燈。
2. **預期值要寫下來再跑**，不要跑完才回想「大概是這個數吧」。
   事後回想會自動遷就看到的數字。
3. **差額本身要追到底。** 26 → 10 之差是 16，而 16 恰好等於
   `16.2`／`16.14`／`16.16` 之對造中已判定者 —— 差額能被解釋，
   才算追完；「大概是哪裡少算了」不算。

同源：R-C30（陰性結果須載明搜尋範圍）。**兩者都是在說：
一個沒有參照物的觀察，不構成證據。**

## 一個檢查沒問的問題，不會因為別的檢查通過而變成已答

A-CF26 之成因，逐字記下來：

pilot 寫回（ENTRY 002）之 assertion 有九項，**沒有一項檢查資料驗證（DV）
之涵蓋範圍**。而 profile §0.1 之 Excel 四項確認，其第 2 項問的是
「**R 欄下拉可用且為九項**」—— 而 `R10` 恰好在 DV 範圍內，於是那一項通過了。

於是**程式端九項全綠、人端四項全過**，而 `P10:Q11` 這個只涵蓋兩列的
priority 下拉，就這樣安然通過了兩道獨立的檢查，並隨 privacy 交付出去。

> **兩道檢查各自都對，合起來仍然什麼都沒問。**
> 綠燈之總數與涵蓋範圍無關 —— 十項綠燈可以全部避開同一個問題。

三項可操作的推論：

1. **加檢查時，寫下它「不問什麼」。** `assertion 13` 之註解即載明它只驗
   R 與 P 兩欄之 DV，`T–Z`／`AF` 因留白而未列 —— 那句話就是下一個缺口的地圖。
2. **人工確認項與程式 assertion 之間的縫隙，要當成一個東西來看。**
   四項確認問「可不可用」，九項 assertion 問「值對不對」，
   **沒有人問「這個約束蓋到第幾列」**。
3. **抽樣式的確認項（「R 欄下拉可用」）會被第一列滿足。**
   凡措辭為「某欄可用」者，須改為「**每一寫入列**之該欄可用」。

同源：R-C37（樣本須含陰性側）、上繳 33 §9.3。
**三者是同一個錯誤在三個層次上：檢查了容易的那一個，就以為問過了全部。**

## 類項之標題須隨成員擴充而更新

`DATA_REQUESTS` 有兩個**類項** —— 同一形態之發現合為一項，因為它們之**處置
完全相同**（照錄、`reasoning` 具名、開 DR、不阻塞、不自造內容）：

| 類項 | 成員 |
|---|---|
| #34 條文以名詞指稱而未定義其**入口或操作方式** | `controls screen`／`Voice Recognition session`／widget 畫面切換手勢 |
| #32 條文要求一組**對照關係**而未定義之 | 座椅 off icon／recirc icon／`most closely matches` 之模式對照 |

**兩者原本都以其首個成員為名**（#34 曾是「`controls screen` 指何畫面」、
#32 曾是「座椅 off icon 由哪一種 configuration 決定」）。

> **以首個成員為名的類，會使後來者看不出自己屬於它。**
> 第二個成員出現時，第一個反應會是「這是新的一項」——
> 於是同一形態被開成兩個 DR，而它們的處置一模一樣。

作業規則：

1. **新增成員時，先問標題還罩不罩得住它。** 罩不住就改標題，
   不是另開一項。
2. **標題描述形態，不描述首例。** 「條文要求一組對照關係而未定義之」
   罩得住 icon、模式對照、以及任何日後出現的對照。
3. **成員逐項列其節次與所缺之物**，使「為什麼它屬於這一類」看得見。

同源：50 §3 之「**處置相同者不分類**」。兩者是同一原則的兩個方向 ——
處置相同就不該分成兩項，而合成一項之後，名字得跟著涵蓋範圍走。

## 類項之成員清單須隨成員更新

36 §2 記了「**標題**須隨成員更新」。本節記其另一半：**清單**也是。

上繳 37 把批次 11 之六個未定義入口寫進各條之 `reasoning`，
而 `DATA_REQUESTS` #34 之成員清單仍只列三例。

> **具名於 `reasoning` 與列入類項清單，是兩件事。**
> 前者使**該條 TC 之讀者**知道缺什麼；
> 後者使**該類之讀者**知道這一類有多大。

上游收到 DR #34 時，看到三例與看到九例，其優先度判斷不同 ——
而兩次的實情是同一個。

三件一起做，缺一即不算登記：

1. **標題**罩得住新成員（36 §2）
2. **成員清單**列出新成員，逐例具名節次、所缺之物、子類
3. **影響欄**之計數隨之更新（「影響 7 條 TC」→「影響 17 條」）

第 3 項最容易漏，而它正是上游用來排優先度的那個數字。

**同源**：50 §3「處置相同者不分類」。三者合起來是同一件事的三面 ——
處置相同就併成一項；併了之後，名字、清單、計數都得跟著涵蓋範圍走。

## 調參數不是中性的動作 —— 它同時移動兩側

> （`— and the rear zone is enabled`，違反 §8.4.1）**當場消失**。

故：**凡以「清單」控制敏感度之檢查，加一項就要問一次「這一項會吃掉什麼」。**
把誤報調到零之最快方法，是讓它什麼都不報。

## 子字串比對使詞形變化在單一方向上被隱藏

同一組探針之副產物：節內有 `landscaped`，句寫 `landscape` → **命中**
（因 `landscape` 是 `landscaped` 之子字串）；反過來，節內有 `landscape`
而句寫 `landscaped` → **不命中**。

> **同一個詞形差異，換個方向就換個結果。**
> 這是實作之性質（子字串），不是判準之意圖（同詞）。

故：讀任何以子字串為基礎之比對結果時，**「命中」不等於「相同」** ——
它只保證一側包含另一側。日後若把該類量測升為 gate，此不對稱須先處理，
否則其嚴格性會依詞序而異。

## 以「當下規模」寫下的數字，兩個方向都會壞

`verify_b_gates.py` 之 `check(len(withheld) >= 20, …)` 寫於 25 個 leaf 停下之時。
R-C45 解封六條後，停下者剩 19 —— **該檢查開始 FAIL，而語料是變好了。**

R-C43 講的是語料**增加**時範圍式界定會失效。這一則是它的另一面：
**語料改善時同樣失效。** 兩者之成因是同一個 —— 那個數字記的是「寫下它的那一天」。

判別法不變：**若明天多了一筆（或少了一筆），這個界定還對嗎？**
`>= 20` 之本意是「不要掃到空集合」，那句話寫成 `>= 1` 就好；
`20` 是把當日之規模誤當成了性質。

**第三例（2026-08-17）**：`write_back.py` 之前置 gate 寫
`BASELINE.sha256 8 檔全數 OK`，而 `inputs/` 自 5 檔增為 8 檔（Pei 補入三份
外部文件）之後，該式立即失效 —— **素材變多了而檢查壞了**。
改為 `FAILED == 0 且 OK > 0`。

**三例並列**（`len(withheld) >= 20`／`len(LEAF_UNIVERSE) == 403`／本例）
**之共同形狀**：`gate 要證的是「每一列都驗過且都對」，
而那句話裡本來就不該有一個數字。**數字進到一個 gate 裡，
通常是因為寫的時候剛好數了一下。**

## 以形態辨識身分，形態會撞

`withheld-not-generated` gate 以 `("SWE1-HVAC-…"` 之**字面形態**辨識 WITHHELD

## 形態式 pattern 找得到的，比清單式多一種東西

盤點 129 節之外部參照時，第一版 pattern 混了具體文件名

**是兩個 0 命中變成了資訊**：`PROXI`／`$…$` 與 `defined in` 句式
於 129 節皆 0。即**本 spec 從不以參數名指涉配置**（那是 CFTS043 的寫法），

## 計數不是身分 —— `len(LEAF_UNIVERSE) == 403` 一例

`verify_no_tcid_gate.py` 曾以

```python
check(len(L.LEAF_UNIVERSE) == 403, "the leaf universe is 037's 403 leaves ...")
```

宣稱「這個 universe 就是 037 的 leaf 集合」。**該式只保證「有 403 個」。**
037 若換掉 3 個 leaf 而總數不變，**原式靜靜通過**——它從未看過任何一個 leaf
的身分，只數過個數。已改為與 `data/recon.json` 之集合逐一比對。

這是 R-C43 之標準說明（77 §3）：**計數在界定當下為真，而其為真之條件是
「內容不換」**——而內容會換，且換的時候它不出聲。

同族之判別法：`nums == list(range(1, len(nums) + 1))` **不是**範圍式，
因為右式自左式之長度導出，**不含任何凍結之常數**。
分界在於「這個數字是我寫死的，還是它自己算出來的」。

## 標題數字是 169，可信的數字是 8

覆蓋審計（73）對 373 個 leaf 逐條問七問，機器判出 **169 格缺口**。
人工複核了其中 **38 格**：**假陽性 30、真缺口 8**。

> **把 169 交出去而不附 22.5% 之複核率，就是把待複核清單當成缺口清單用。**

其後續（74 §2）更尖銳：Q7 之判準本身是錯的 —— 我把 §8.2.2 讀成
「多個獨立可觀察量落在同一 fail」，而 canon §5.7 之判準是**觸發**：
**一次按壓造成七件事，是七個要檢查的事實，不是七條 TC。**
據該錯判準得出之 106 格「應拆」全部作廢。

故：**任何以機器產出之清單，其標題數字須與其複核率一同交出**；
未複核之部分要說出它未複核，而不是說出它有多少。

**自查一句**：我要交出去的這個數字，**是量出來的，還是判出來的**？
量出來的可以直接說；判出來的要說「判準是什麼、複核了多少」。
