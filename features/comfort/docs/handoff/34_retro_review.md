## 1. §10.1 —— **授權回溯複查**，且這是本輪最重要的一項

執行層自陳：§3 之複查只做了一個方向（2.2 是否須排除某種車輛），
**未問「其他已生成之批次是否也須排除某種車輛」**，並判此為
「本包最可能重演同一錯誤之處」。

**該判斷正確。** §4.1 之判別在批次 3 失效，而 pilot 與批次 2 **是在該判別
仍被當作判準時生成的** —— 它們沒有被那個判別漏掉，是因為當時根本沒人問
這個問題。

### 1.1 複查之問題須為實質形式

```
對每一條既有 TC 問：
  「在哪一種車輛配置下，這條 TC 沒有可操作的對象？」

不是問「該節條文有沒有選擇子」（代理，已限縮為候選產生器）。
不是問「lint 有沒有報」（R-C23）。

答案為「存在該配置且未以 PC 排除」者 → 補一行 PC，出處依 R-C29 具名，
`specification_reference` 併入該出處節，**內容不重寫**。
答案為「不存在」者 → 於上繳包具名其實質理由。
```

### 1.2 範圍與已知風險點

全部 31 條既有 TC（pilot 14 ＋ 批次 2 之 17）。已知須特別檢視者：

- **`Seat Control Tab`（13.x）** —— 13.1（`assumption`，037 未引用）述及
  `lower comfort screen` 之有無影響座椅／腰靠控制之可及性；
  6.3 述及 `non-foldable secondary lower screen`。**第九軸已存在**，
  而 pilot 之 14 條是否用到它，須實測
- **`Tri-Mode Climate`（3.x）** —— 已有 tri-mode／MAX DEF／MAX A/C 三軸之
  PC，但未問第十三軸（3 旋鈕 ICS 車上是否有 climate screen 可操作）

**複查得出之補行，不重跑內容、不改 tc_id。** 若某條之結論為「該 TC 在某
配置下完全無法執行且無 PC 可排除」，回報停下，不自行處置。

## 2. DR #19（`-045` 之例外情形）—— **拆條**

2.14 之 `020-04` 條文含主情形與例外：

- 主：3 旋鈕 ICS → 不顯示任何 HVAC icon／screen／pop up
- 例外：`For one zone MTC with push button TEMPERATURE … this exception
  does not apply` → 顯示

**兩者為不同輸入（不同配置）之不同結果，且各自獨立可失效**：主情形正確
而例外錯誤（或反之）皆可能發生，兩者共用一個 verdict 即為 bundling。
§8.3「different inputs」與 §8.2.2「independent partial failures under one
sub-id → split and record」同時成立。

另有 §7 之獨立理由：**列舉之支援項須配至少一個未支援之負向 TC** ——
例外正是該負向對照。目前 `-045` 只寫主情形，該負向不存在。

處置：拆為二條，**同溯 `SWE1-HVAC-020-04`**，`split_flag` 為真、
`split_reason` 具名 §8.2.2 與 §7。tc_id 續編，後續順移並列新舊對照表。

**PC 之第十三軸值須具名**：例外條之 PC 不得用否定式，須明寫
`one zone MTC with push button TEMPERATURE`（見 §4）。

## 3. §10.3（`-044` 之 ER 改寫）—— **成立**

037 之 `-03` 寫 `no mismatch occurs`，而條文為
`… in order to prevent a mismatch` —— **目的子句**。目的不是可觀察量。

執行層改以條文之機制句（螢幕不提供與 3 旋鈕重複之互動）為 ER，
**正確**，且與 **R-C22**（ER 以條文自身命名之可觀察量表述，不可量化
≠ 不可觀察）一致。

另有一項使其更強：**在 3 旋鈕 ICS 之車上沒有螢幕，`mismatch` 在該配置下
本就無從觀察** —— 以它為 ER 會產生一個永遠無法判定的 TC。

`reasoning` 須補一句：`no mismatch` 為目的子句，被驗證者為其機制。

## 4. 第十三軸之否定式表述 —— 限縮其適用

執行層 §10.2 自陳：PC 寫 `does not have 3 knob HVAC controls with ICS`，
把三值軸壓成二值；對 2.2 正確（後兩值皆顯示 HVAC UI），但若某節需區分
後兩者即不敷使用。

**裁示**：

- 否定式**僅得用於「只需排除某一值」之情形**，且該 PC 須註明其為排除式
- **凡 TC 之行為隨軸值而異者，PC 一律具名該值**，不得用否定式
- profile 第十三軸增一段記此限制，並以 §2 之例外條為首個具名值之案例

理由：否定式之涵蓋範圍取決於軸現有幾個值，**而軸會增值** ——
今日正確之否定式，會在增值當日靜默地變成錯誤，且無任何 gate 會報。
