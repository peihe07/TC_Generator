## 1. A-CF21 —— 037 leaf 與 spec 條文衝突：立條文

2.1 之條文為 `up to 4 tabs`、順序含 `Massage`；037 之 `-01` 為 `up to 3 tabs`、
`-02` 之順序無 `Massage`。**037 系統性地少了 Massage tab。**

執行層判「現行條文未涵蓋」—— §8.6 管 spec 與其索引導出，不管 spec 與上游
分析。**該判斷正確，但 canon 另有一條涵蓋此形態**：§8.1

> Traces to Req or SWRA. **Conflict → Req wins; flag RD.**

與 §8.2 併讀即得完整分工，本包將其寫成條文以免每次重推：

```
R-C33  單位歸 037，內容歸 spec

037（SWRA）與 spec 條文衝突時，依衝突之性質分別處理：

一、**何者算一個需求單位**（leaf 之切分、數量、id）—— 037 為權威（§8.2）。
    TC 作者不得再分解、合併或發明 leaf。

二、**該需求說了什麼**（數值、列舉、順序、條件）—— **spec 條文勝**
    （§8.1「Conflict → Req wins」），並列 RD-1 呈報該落差。

三、內容依 spec 而 leaf 依 037 時，該 leaf 之 TC 依 spec 內容撰寫，
    `req_id` 仍為該 leaf；`reasoning` 須具名此落差與其 RD-1 編號。

理由：037 決定的是「這份 spec 被切成幾個要求」，不是「這份 spec 寫了什麼」。
把後者也讓給 037，等於讓一份分析報告改寫它所分析的對象。
```

**適用於 2.1**：leaf 維持 `-01`／`-02`／`-03` 三個（037 之切分），
內容依條文之 4 tabs 含 Massage。

**Massage 之委派範圍須分辨**（執行層已判，正確且採納）：
`Refer to separate HMI Logic and Flow documentation for Massage Seats logic`
—— **委派的是行為，不是存在**。Massage tab **是否顯示**由 2.1 擁有，
Massage tab **按下去做什麼**不由 2.1 擁有（§8.2.1）。

登 RD-1 候選：037 之 `-01`／`-02` 與 2.1 條文於 tab 數與順序不一致。

## 2. 2.1 之第一層問題 —— 內容不足，非軸之問題

條文寫 `up to 4 tabs depending on vehicle configuration`，**未述何種配置
產生何種 tab**。故即使 A-CF21 依 §1 解決，`-01`／`-02` 仍無法寫出一個
已知的 tab 集合作為 PC —— 依 R-C28 第一問，任何具體配置皆為造值。

執行層之分層（第一層是內容問題、第二層才是軸）**正確且重要**：
若只當成軸的問題，增軸之後會以為可以開工，而實際上仍缺條文。

處置：`-01`／`-02` **暫不生成**，登為 RD-1 待答項（與 §1 之落差同一問句）。
`-03`（`only Front climate is available` → 不顯示 tabs）之條件為條文明文，
依 §3 增軸後即可生成。

## 3. 增第十二、十三軸

```
第十二軸  僅前排氣候（Front-only climate）
  來源節：2.1（明文 "If only Front climate is available in a specific vehicle"）
  值：僅前排 ／ 含其他氣候區

第十三軸  HVAC 實體控制型式
  來源節：2.14
  值：3 旋鈕 ICS（"3 knob HVAC controls"）
    ／ 單區 MTC 附 push button TEMPERATURE（"one zone MTC with push button
      TEMPERATURE"）
    ／ 其他
  說明：本軸為**控制型式**，與第一軸（ATC／MTC）、第二軸（區數）正交，
  三者於 2.14 同時出現且各自獨立。

  **與市場／變體軸之 `EMEA ICS` 不同，不得混用**：後者之範圍寫明 ch16 全章，
  指 EMEA 市場之整套 ICS 氣候介面；本軸指 ch2 所述之實體旋鈕配置，
  其後果為 HVAC 觸控 UI 不顯示。兩者外觀皆含「ICS」而所指不同 ——
  此正是 R-C18 之同型風險：**措辭正確地屬於別處**。
```

執行層 §12 第 2 問（`MTC has a Climate screen` 是否為第十二軸）**不另立軸**：
「有無 climate screen」是第十三軸之**後果**，不是獨立的配置變數。
把後果立成軸，會使同一事實有兩個來源而無人維護其一致性。

增軸後 `2.1-03` 與 `2.14` 之 4 leaf 可續生成。

## 4. §4.1 之「On vehicles with X」判別 —— 限縮為候選產生器

執行層自陳：該判別由四個正例歸納，未對 129 節全掃，且「這是本包最需要被
檢驗的一句話」。**該自陳正確，且其風險已在本批內實現。**

**該判別是詞彙型代理判準。** §5a：代理判準不得凌駕實質判準；R-C13：
陰性結果只是索引層事實。故：

- **可用於產生候選**（有選擇子 → 幾乎必然需要軸）
- **不得用於認定不需要**（無選擇子 → 不得推出無需軸）

### 4.1 批次 3 之 8 條須補一項實質複查（不退回重做）

`2.2` 全篇無選擇子，故本批 8 條皆無配置類 PC。但 **2.2 之行為預設車輛
同時具備氣候觸控畫面與實體控制鍵**，而該前提是變數：

- `2.14`：3 旋鈕 ICS 之車輛 **no HVAC screens** —— 觸控畫面不存在
- `11.11`（`configured with hard buttons for comfort controls`）——
  實體鍵之有無為配置項

**複查之問題（實質，非詞彙）**：2.2 之 8 條是否須以第十三軸（或其
「其他」值）為 PC，以排除「無 HVAC 觸控畫面」之車輛？

- **須**：8 條各補一行 PC，`(2.14)` 為出處（R-C29 跨節取據），
  `2.14` 併入 `specification_reference`。**內容不重寫，只補 PC。**
- **不須**：於上繳包具名其實質理由（非「2.2 沒有選擇子」）

### 4.2 §4.1 之判別本身

保留，但改寫其定位：於 `RUNBOOK.md` 與 profile §3.2 記為
**候選產生器（proxy）**，並附上「不得用於認定不需要」之限制與本案例。
