## 1. `duplicate_of` 之粒度 —— **不擴充 schema**，改記於 sibling 表

§10.6 為**工具側之輸出契約**（digits-only row-number，對應注入之
`## Sibling Rows`），其設計對象是同一次注入內之列。跨節、跨 Test Set 之
等價不在其射程內。

**執行層未硬填正確**：於節級欄位填入條級之等價，會宣稱整節重複，而那是假的。
其自陳「一次嘗試把 token 放進 doc builder 會靜默丟棄之 per-TC 欄位 ——
死碼而通過全部 gate」尤其值得記：**通過全部 gate 之欄位，可能根本沒被寫出去。**

處置：

1. **`duplicate_of` 維持不填**
2. 條級等價記於 `pending_sibling.tsv`：增 `equivalent_tc_pairs` 欄，
   內容為 tc_id 對，並記其判定依據（§10.6 四項逐項）
3. 兩條 TC 皆**保留**，各溯其 leaf —— §8.2.2 禁 TC 作者合併 leaf
4. **開 DR**：037 將同一行為分解為 `2.6.1` 與 `2.11` 兩個 leaf，
   致本交付件產生兩對嚴格等價之 TC。**此為 RD 層之分解問題**，
   非 TC 層可解（§8.2）

**不改工具契約之理由**：§10.6 是與 generator 之介面，改它會影響
`duplicate-of-format` gate 與 sibling 注入之語意，
而本案之需求以另一份表即可滿足。

## 3. 第十六軸之類別 —— 改為**常設複檢**，不用旗標

執行層指出其類別判定依賴「實測 124 條無一條之可觀察量在 widget 第二頁」，
而該陳述於 ch11／ch12 生成時可能失效，**且無機制會在那時重問**。

**不比照 `provisional` 立旗標** —— 旗標需人手清除，而本案之反面檢驗
**本身就是可機械重跑的**：

```
常設檢查 `axis-type-reverse-test`（每次 lint 執行）：

對每一個判為**功能型**之軸，重跑其判定時所用之反面檢驗：
  是否存在任一條 TC，其功能為該軸所轄，而其可觀察量位於該軸之某值
  所移除之介面上？

存在 → FAIL，訊息指名該 TC 與該軸，要求重新判定類別。
不存在 → PASS，並於具名回報行載明「本次以 N 條 TC 重驗」。

判定當時之 N 一併記於 profile，使「以多少條驗過」可查。
```

**旗標記錄的是「有人看過」，常設檢查記錄的是「現在仍成立」。**
本案要的是後者。

反面檢驗之具體判準（功能關鍵詞、介面之識別）須自 profile 讀入，
不寫死於腳本。

## 4. 通過、無須處置者

- **第十六軸判功能型，且以三個既有介面型軸之共同形態為對照** ——
  「功能還在，只是換了地方看或看不到」。該歸納使判定不依賴直覺
- **反面檢驗為決定性依據**：介面型軸之價值在於「功能仍在而別條 TC 之
  可觀察量消失」，實測無此情形
- **DR #37 自行實測而不待上游**，且查出 `14.12` 之前提與條文其餘部分
  **相矛盾** —— **「這已不是缺一個軸，是該句無法適用」**，
  且明言「即使逐控制登記三個軸，那句仍寫著 the hard controls，仍指不到
  任何一個」。**增軸不能解此問，該判斷正確且省下一次無效的軸登記**
- **FAN 僅見一種形態而不升為「固定」**（R-C13）
- **privacy 唯讀實測**（`ad595ed0…`，11 列，`P10:Q11`），A-CF26 由轉述
  改為實測，且未寫入該 feature 任何檔案
- **R-C36-1 於本批 6/26 得「否」，其中兩條非「ch16 沈默」而是
  「ch16 說相反」** —— 兩者如實分記，不併為一類
