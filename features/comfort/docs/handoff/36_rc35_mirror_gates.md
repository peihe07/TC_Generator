## 1. §3.3 —— 執行層之違反正確，我的規則寫錯了

下放包 35 §2 之判定規則：「若存在獨立於畫面之 LED 指示，則
`-016`／`-017` 之排除式 PC 過嚴，須移除。」

執行層依證據應移除而未移除，理由：獨立 LED 存在於 **recirculation 硬鍵**
與**座椅／方向盤控制**，**沒有任何一節提到 MODE 硬鍵有 LED**；移除該 PC
等於宣稱「MODE 硬鍵有指示可讀」，**那是把一個造值從畫面搬到 LED 上，
方向相反而性質相同**。

**該理由成立，處置維持。錯在我。**

我的規則之前件是「**存在**獨立於畫面之 LED」——一個關於語料的一般事實；
而所欲判定者是「**這條 TC 的可觀察量**是否有第二個承載位置」——一個關於
特定觀察量的問題。**前件與所判之事不同一**，故該規則可以在證據為真時
導出錯誤結論。

```
R-C35  判定規則之前件，須與其所欲判定之事同一

寫給執行層之判定規則，其前件必須是關於**該次判定之對象**的命題，
不得是關於語料、章節或某類事物之一般命題。

前件為一般命題者，規則會在證據為真時導出錯誤結論，且執行層若照字面執行
即無從察覺 —— 錯誤已被編碼進規則本身。

自查：把規則之前件與結論並排，問「前件為真而結論為假，是否可能？」
可能者，該規則不得下放。

同源：§5a（代理判準不得凌駕實質判準）、R-C13（零命中換路徑）、
34 §4（否定式之涵蓋隨軸值而變）。本條之對象是**規則的寫法**，
前三者之對象是判準的用法。
```

執行層之另一項自陳一併記錄：**「若我當時掃了全語料，我會發現『LED 一律
反映畫面』這個前提是假的 —— 我的結論建立在一個我沒驗過而且是錯的前提上。」**
結論維持而理由重寫，兩者須分開記，已照辦。

## 2. §2.4 —— 13.x 之 Seats tab **不補**，且非裁量而是規則所迫

2.1 之 `tabs` 是否涵蓋下螢幕之 Seats tab，條文未定。

**無明文對應即不得寫入 pre_conditions** —— 補 PC 會把一個對未定義詞語之
解讀編碼成事實。

執行層未補、未推測、列待裁 —— 正確。

與 DR #17 同源（皆為 2.1 之內容不足），**併同發函**。

**風險須明記**：若答案為「涵蓋」，則 `Seat Control Tab` 之 14 條在僅前排

## 4. §5.4 —— `duplicate_of` 回填之機制

`2.6.1` 之 sibling（`2.11`，屬 `Climate Modes`）尚未生成，故 `duplicate_of`
暫空。**暫空正確，無機制則否。**

新 gate `pending-sibling`：

- 生成器維護一張 `pending_sibling` 表：`{待判之 tc_id: 其 sibling 之節次}`
- gate 檢查：表中之 sibling 節次，**若其所屬 Test Set 已全數生成**，
  而該 tc_id 之 `duplicate_of`／`distinguishing_axis` 仍為暫空 → **FAIL**
- 反向驗證：偽造 `Climate Modes` 已完成之狀態 → 對 `2.6.1` 之 tc_id 報 FAIL

**這使「等對造節生成後再回填」由記憶轉為條件** —— 對造節生成之日，
lint 會自己要求回填。

現時登記：`2.6.1` 之 tc_id ↔ `2.11`。日後凡跨 Test Set 之 sibling 皆入此表。

31 條之排除式 PC 現繫於「ch16 鏡射 ch2／ch3」此一結論，而該結論之依據為
**三節首句 ＋ framework.md 之鏡射表**。31 條之正確性繫於一個三樣本歸納。

指示：建 `data/ch16_mirror_map.tsv`，欄位
`ch16_outline`｜`ch2_or_ch3_outline`｜`對應強度`｜`依據`。

- 對應強度三值：`mirrored`（首句實質相同）／`partial`（涵蓋部分行為）／
  `no-counterpart`（ch16 有而 ch2／ch3 無，或反之）
- ch16 全 18 節與 ch2／ch3 全 26 節**雙向**列出，不得只列有對應者
  —— **`no-counterpart` 正是本表要找的東西**

若出現 ch2／ch3 之節在 ch16 **無對應**，其 TC 之 EMEA ICS 排除式 PC
即過嚴，須移除；回報清單，不自行移除。

## 6. §9.5 —— R-C34 之生成時義務：**加 gate**

執行層自陳「R-C34 目前仍是紀律，不是機制；`axis-value-count` 只驗否定式
使用者之登記，不驗『該補而未補』」。**正確，補之。**

無法機械驗證「答案對不對」，但可機械驗證「問了沒有」：

- 每條 TC 之 JSON 增一欄 `interface_axis_review`（doc 層或 TC 層皆可，
  須同步入 `json-key-coverage` 之白名單），內容為：
  `{observable_interface: "...", axis_9: "...", axis_12: "...",
    axis_13: "...", emea_ics: "..."}`
- gate `interface-axis-answered`：四個鍵皆存在且非空 → PASS；
  任一缺或為空 → FAIL 並指名 tc_id 與缺漏之軸
- 既有 64 條**須回填**（回填即為一次複查，不是形式作業）
- 反向驗證：抽一條清空某鍵 → FAIL

**該欄不入工作簿**（列入 `NOT_IN_WORKBOOK` 白名單）。
