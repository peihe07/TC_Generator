### 1.1 bytes 相符不等於位元組相符

分析層之工具只能量檔案大小，**不能算雜湊**。170,047 與 6,470 為強證據
而非完整證明 —— 兩份大小相同而內容不同之檔案，於本層之量測下無從分辨。

**逐位元組之驗證須由執行層以 `shasum` 實測**，對 ENTRY 026 之
`0366315926ed9eef…` 與 `docs/` 之交付說明 hash 比對。

### 1.2 一項時戳異常，**以 hash 判定不以時戳判定**

工作簿之 `created` 為 23:33:24、`modified` 為 23:33:54，**相差 30 秒**。
單純複製通常兩者相同。

可能為複製過程使然，亦可能該檔落地後曾被開啟並存檔（**ENTRY 023 即此形態**）。

**時戳可變而位元組是判準** —— 本項不由時戳結論，
由 §1.1 之 `shasum` 結果判定。若 hash 不符，依 82 §1 處置：
驗其內容、不改 ENTRY 026、另登新 ENTRY、**並以交付夾內之該份為交付物之對象**。

## 2. 交付說明第 5 行 —— `<date>` 佔位符未替換

```
**Workbook**: `FM-WI-FSM-036-A01 … _SWQT_Comfort_<date>.xlsx`
```

該欄之用途為「本說明對應哪一份工作簿」，**而佔位符使其不指向任何檔案**。
評閱方同時看到工作簿之實際檔名（含 `20260816_extdocs`）與說明中之 `<date>`，
無從確認兩者是否為同一份。

**其餘各行皆已填實**（Feature／Requirement／Analysis document／Date／
Baseline／Version），**唯此一行漏替換** —— 其形態與 lint 所抓之
「範本殘留」同族，而交付說明不在 lint 之涵蓋範圍內。

### 2.1 處置

1. 改為實際檔名 `FM-WI-FSM-036-A01 … _SWQT_Comfort_20260816_extdocs.xlsx`
2. **重新複製至交付夾**（複製屬 Pei）
3. 登其新 hash

### 2.2 連帶 —— 交付說明應納入檢查

交付說明為交付件之一部分而不受任何 gate 檢查。加一道
`delivery-note-placeholders`：掃該檔之 `<…>`／`TBD`／`XXX`／`__` 形態，
命中即 FAIL。

**其判準為形態而非清單** —— 佔位符之寫法不只一種，
列舉會漏（R-C37：以樣本支持全稱結論者，樣本須含陰性側）。
