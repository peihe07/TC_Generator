## 3. R-C29 —— PC 之節次標註指向出處，非所屬

執行層 §3.5 第 3 問為 pilot 未遇之新問題：3.3 之 PC 需 REAR DEF 存在，
而該事實之明文在 3.4。標 `(3.3)` 則 R-C28 第一問失敗；標 `(3.4)` 則標註
與 TC 所屬節不同。

```
R-C29  pre_conditions 之節次標註指向事實之出處，非 TC 之所屬節

PC 每一行括號內之節次，係該事實之**明文出處**，不是該 TC 所屬之節。
兩者不同時，以出處為準。

連帶三項義務：
一、該出處節須一併列入 specification_reference —— §10.7 明定該欄涵蓋
    「TC 直接驗證或**賴以作為 setup**」之節，跨節取據之 PC 即屬後者。
二、reasoning 須說明何以跨節取據，並確認**未擴張驗證範圍**（§8.2.1）：
    引用 3.4 之裝備事實，不等於驗證 3.4 之行為。
三、coverage 分母以 leaf（req_id）計，不以 specification_reference 計；
    跨節引用不改變任何 leaf 之歸屬。

至今所有 PC 之出處節與所屬節同一，係語料使然，非規則使然。
本條使該巧合不再被誤認為規則。
```

## 4. R-C30 —— 搜尋之涵蓋範圍須隨其結論一併陳述

17 §3.5 據實更正 A-CF02 原記之「交付樹不可達」：該次 `find` 之起點在
`TC_Generator/` 之內，而交付樹在 repo 之外。**零命中被當成「不存在」，
而它其實只是「不在我搜的地方」。**

執行層自陳此與 A-CF16 為同一件事之兩面（引用不存在者／宣告存在者不存在），
且**後者目前無機制**。本條為該缺口之部分補救。

```
R-C30  以搜尋為依據之陳述，須載明其涵蓋範圍

凡結論之依據為「搜尋未命中」者，該陳述須同時載明搜尋之**根目錄**與
**pattern**；未載明者，其陰性結果不得作為任何結論之依據。

此為 R-C13 之補充：R-C13 要求零命中須換路徑，本條要求**已走過的路徑
留下痕跡**。無痕跡者，第二人無從判斷該換哪條路。

適用於 anomaly、上繳包、下放包之一切陰性陳述。
```

## 5. 17 §5 之待裁三項

### 5.1 `json-key-coverage` 擴及 doc 層 —— **是**

執行層限縮於 TC 層並回報，處置正確（未自行增列白名單）。

**擴及 doc 層。** 白名單增列六項結構性 key：
`assumptions`、`batch`、`outline`、`parent`、`source_clause`、`tcs`。
連同既有八項共十四項，**增列仍須經裁定**。

理由：`reasoning`／`keywords`／`duplicate_of`／`distinguishing_axis` 實際
位於 doc 層；gate 只覆蓋 TC 層時，那四項之「具名」是名義上的 —— 它們根本
不在被掃描的層。

### 5.2 交付夾台帳 —— **於 `DELIVERY.sha256` 增一類 ENTRY，不另立台帳**

單一台帳使「誰在維護這個檔」只有一個答案（同 R-C21 之理）。

ENTRY 增 `type` 欄，二值：
- `produced` —— `output/` 之產出物（ENTRY 001、002）
- `folder-attachment` —— 置入交付夾之附件

台帳頭部加一句說明二者之別。本次放入之 SR24 兩檔補記為 **ENTRY 003**
（`folder-attachment`），含來源路徑、bytes、SHA256、放入日期與依據
（下放包 27）。

### 5.3 `anomaly-id-registered` 之副作用 —— 採納，並定例示寫法

該 gate 使上繳包無法逐字記載未登記之編號。**gate 沒有錯**，代價可接受。

**例示一律用 `A-CF-XX` 形式**（編號位改為非數字），不匹配 `A-CF\d+`，
故不觸發 gate。此寫法寫入 `RUNBOOK.md`，免得下一個人再撞一次並誤以為
gate 有誤。
