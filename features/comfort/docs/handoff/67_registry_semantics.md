## 1. §4.2 `AMBIGUITY_REMARKS` —— **保留其機制，改其性質：登錄簿，非許可證**

執行層自行加入該白名單並請裁。**機制保留，但其語意須改**。

66 §3 所立者為**一般義務**：凡條文歧義會使測試員在執行時無法判定者，
該歧義須出現於 Remarks。**以白名單作為許可證，會把一般義務變成逐案審批**
—— 而對一項義務加審批，其淨效果是那件事不再發生。

```
性質改為登錄簿（本包裁定）：

一、**列名不是授權**。凡符合 66 §3 之條件者，其 Remarks **應**承載該歧義；
    作者逕行寫入並同時登錄，**不需個案裁定**。
二、**登錄簿之作用為身分對帳**，gate 雙向檢查：
      Remarks 含歧義文字而未登錄 → FAIL
      已登錄而其 Remarks 無該文字 → FAIL
    （後者即 §7.3 所指之缺口，一併補上，同 `moved-leaf-identity`）
三、**內容之限制仍在且為硬性**：無內部 id、無 DR 編號、
    以執行者可用之語句陳述該歧義。此三項由 gate 檢查，不由登錄簿把關。
```

**分辨**：marker 白名單（R-C26）之所以須裁定，是因為它**豁免了 lint**；
本登錄簿不豁免任何檢查，只記錄「誰承載了歧義」。
**兩者形狀相似而性質相反 —— 一個放寬，一個對帳。**

## 2. §7.4 `126-02` 之 PC —— **改寫，其成本不存在**

執行層不改寫之理由為「改寫 PC 會動到已寫回之列」。

**該理由不成立**：45 §4 已裁寫回為**全量重寫而非追加**，
理由即「既有 TC 會因後續批次之發現而修改」。**每一次寫回都在重寫那一列。**

且其自身之發現指出問題所在：

> **不命中之因是 PC 沒有引到帶限定語的那一段，不是條文沒有限定語。**

而 R-C42 一之文字為「PC 得以該條文**逐字**表述並標 `spec-verbatim`」——
`The vehicle shows the 50% Comfort widget` 是改述，不是逐字。
**該條之 PC 本就未完全滿足 R-C42 一。**

處置：`126-02` 之首行 PC 改為逐字引 `On the 50% widget,`（含其後必要之
片段以成句），標 `spec-verbatim`，出處 `17.3`。改後 gate 直接命中，
**其 disposition 區塊撤除**。

`125-08` 同理檢視：其 PC 若亦為改述，一併改寫。

## 3. §7.2 客戶端之聲明 —— **不加**

BLOCKED row 之 Remarks 陳述者為「**該內容由某文件擁有**」，
而該委派**逐字寫在 Comfort 之條文裡**（`Refer to HMI Settings List for …`）。
**該陳述之依據是 Comfort spec，不是那份外部文件** ——
故「本層未讀該文件」不是該陳述之限制。

「零餘留」之判讀亦然：其對象是**本 spec 之句子**，
問的是「扣除委派後本節還剩什麼可驗」，答案不因外部文件之內容而變。

**不加客戶端聲明。** `reasoning` 之記載（66 §1.2 已裁為如實表達）足矣。

**惟一件須確認**：兩列之 Remarks 是否已使客戶讀出「**Auto Comfort Settings
之選項不由本交付件涵蓋**」。若現行措辭僅止於 `Owner: …`，
補一短句使其明白 —— 客戶要知道的是「這件事沒有被我們測」，
而非只是「這件事屬於誰」。
