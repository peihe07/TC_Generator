## 2. DR #37 —— 未增軸正確，問句須收窄

執行層之發現決定性：**同一車輛同時具旋鈕型風速控制、按鍵型溫度控制與
多向 MODE 控制** —— 故「硬控型態」是**逐控制**之性質，不是逐車輛之配置。
逐車輛之配置才構成軸。

**未增軸正確。** 但 DR #37 現行問句仍以車輛為單位，答了也用不上。收窄為：

```
ch14 所引用之各硬控，其**物理型態於各車型間是否固定**？

  固定 → 該型態由「操作哪一個控制」決定，落 test_procedure，非配置軸
  可變 → 該控制之型態即為一個軸，須逐控制登記

須逐控制回答，不得以整章一句話代之。
```

**此問句可於 `Climate Popups` 開工前自行實測**（掃 ch14 各控制之描述，
看是否出現「某些車輛此控制為旋鈕、某些為按鍵」之形態），
不必全然等待上游。實測若顯示全數固定，則 `Climate Popups` 無此阻塞。

## 3. §9.3 「操作方式未定義」—— **併入同一類，不另立**

執行層之區分（操作*方式* vs *入口*）為實，但**兩者之處置完全相同**：
照錄、`reasoning` 具名、開 DR、不阻塞。

**處置相同者不分類** —— 分類之目的是導出不同處置；不導出者只是多一個
要記的名字。

DR #34 之類名改為「**條文以名詞指稱而未定義其入口或操作方式**」，
`-115` 之畫面切換手勢併入，於該項內以子類標記區別（`entry` / `gesture`）。

## 4. §9.2 `17.1` 三條之重疊 —— **非 §4.5，是 §4.6**

§4.5 管的是**一條 TC 之內**資料屬於哪個欄位；`-115`／`-116`／`-117` 為
三條 TC，各溯不同 leaf，**不在該條射程內**。

其真正性質為 **sibling 重疊**（§4.6）。處置：

- 三條之 `distinguishing_axis` 須逐條具名其區別 token
- 依 §10.6 檢查是否構成 `duplicate_of`（嚴格等價：同 trigger ＋ outcome ＋
  input ＋ verification target）—— 三者之 verification target 不同
  （畫面數／Comfort 內容／Seats 內容），**預期不構成**，但須明寫其判定
- 依 R-C33，037 之單位不動

**風險由「§4.5 未消除」改記為「sibling 重疊已依 §4.6 處置」** ——
前者暗示有一個未修的違規，後者才是實情。

## 5. §9.6 A-CF26 之 privacy 側 —— **授權唯讀量測**

我 46 §2 寫「不改 privacy 之任何檔案」，執行層讀為「零讀寫」。
**過度保守，但其保守方向正確，不責。**

**釐清**：R-C21 禁的是**代他 feature 建檔與修改其既有檔案**；
**唯讀量測不在其列**。一份未經實測之 anomaly 陳述，正是本 pipeline 反覆
指出的問題。

授權：唯讀量測 privacy 之已交付件（依其 `DELIVERY.sha256` 所記路徑），
回報其 P 欄 DV 之 `sqref` 與受影響列數。**不得寫入該 feature 任何檔案。**
量測結果更新 A-CF26 之陳述，由「轉述」改為「實測」。

## 6. 通過、無須處置者

- **A-CF26 §1.2 之定性**：「內容正確而約束缺失」，且明寫
  「**不是已交付之內容有誤，是已交付之防呆缺一段**」—— 該區分決定其緊急度
- **§1.4 之成因**：pilot 之九項 assertion 未檢查 DV 涵蓋，而 Excel 四項確認
  問的是「R 欄下拉可用」而 `R10` 恰在範圍內 ——
  **「一個檢查沒問的問題，不會因為別的檢查通過而變成已答」**，
  逐字寫入 `RUNBOOK.md`
- **產出檔位元組不動、狀態寫在 `output/STATUS.md`** ——
  「改檔即改 hash，台帳就指不到它了」，正確
- **`18.1` 與 `17.1` 逐字相同，僅**章標題**不同，而章標題不是條文** ——
  故螢幕尺寸之 PC 無來源。此判斷精確且是 R-C28 第一問之正確適用
- **修掉一條「看起來有來源而其實沒有」之 PC**（`17.1` 從未說 widget 在
  首頁上）—— 該類最難自查
- **台帳 gate 因 ENTRY 004 內文提及「ENTRY 005」而卡住自己**，
  改為比對 entry 標頭而非任意子字串
