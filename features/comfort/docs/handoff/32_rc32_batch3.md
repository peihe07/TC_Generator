## 1. `req-id-unique` 之改判 —— **批准**，並立為通則

執行層自陳「逾越了本包之授權範圍」。**逾越屬實，處置正確，予以追認。**

拆分使重覆 `req_id` 成為合法，既有 gate 必然失敗。它可選之兩路：
**放寬**（重覆即通過）或**改判**（重覆合法但須每列宣告拆分）。它選了後者。

```
R-C32  裁定使既有 gate 失敗時，改判而非放寬

某項裁定使既有 gate 產生 FAIL 者，該 gate 須**改判為編碼該裁定之條件**，
不得放寬為不檢查。

放寬使該 gate 原本擋住的錯誤一併通過；改判則使裁定之條件本身成為機械要求。

判別：改判後之 gate，於**該裁定不成立之情形**仍須 FAIL。
（`req-id-unique`：重覆 `req_id` 而未宣告 `split_flag`／`split_reason` →
仍 FAIL。若改為「重覆即通過」，§8.2.2 所禁之合併就沒有任何機制擋得住。）

前例：17 §2.3 之 gate 2（`--verify-only` 而非放寬台帳檢查）為同一形態，
當時未立條文。
```

**逾越授權而回報，優於不逾越而停擺** —— 但回報是其成立之條件，
非附帶。此點併記於 `RUNBOOK.md`。

## 2. `forbidden-verb` 之 `locate` —— **否決，須移除**

執行層自陳 `locate` 非 canon 所列，係其手查時自行加入，「若分析層認為不妥，
移除即可」。

**不只是不妥 —— 它與 canon 抵觸。** §5.6 之**正面示例**即使用該詞：

> ✓ Recording step: `Locate the phone and record its A2DP and HFP status
> shown in the list`

`locate` 是定位動作，不把判斷推給測試員，故不屬 §5.1 所禁之類。
**該 gate 目前以機械形式固化了一個 canon 明文推薦的寫法之禁令。**

處置：自詞表移除 `locate`，gate 回到 §5.1 之九詞。

**併記一則通則於 `RUNBOOK.md`**：gate 之詞表若含 canon 以外之項，
須於該 gate 之註解具名其來源與授權依據；無授權依據者不得入表。
**手查時之個人習慣不是授權依據** —— 它在手查階段只影響一次判斷，
入 gate 後影響全部後續批次。

本批無任何步驟使用該詞，移除不影響現有 31 條。
