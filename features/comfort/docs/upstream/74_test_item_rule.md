## 2. profile 之訂正

### 2.1 §3.1 —— 「濃縮」為誤

原文 `Test Item = 以 spec 語言**濃縮**之需求陳述` **已標為誤並劃線**，
改記：**上半為條文原文，原封不動** —— 不改寫、不濃縮、不加主詞、不換句型。

**誤實作之成因逐字記入**（95 §3.1）：

> G-1 量了 `home` 之 Test Item 欄，得「143/144 含 modal、中位 273 字元」，
> 據以認定本節之 override 有據。**該量測量了「有沒有 modal」與「多長」，
> 未量「是原文還是改寫」。**
> **量對了指標，答錯了問題。**

並記 `home` 之 modal **本來就來自條文原文**（RD 語言用 `shall`／`will`），
不是作者加上去的 —— 這一句是那個誤讀能成立的關鍵。

### 2.2 §3.1.1 —— 下半之定義改為「測項定義」

原記為「該條之情境」，改為 95 §2 之定義：**作者所理解之測項定義**
（在什麼條件下、做了什麼、預期看到什麼），並明記其**不是**條款編號、
不是節次、不是文件名 —— **出處另有其欄，不由此欄承擔**。

另記其功能為**拆分之區分**：一 leaf 拆多條時上半完全相同，
**下半是那幾條在 test_item 欄上唯一可分辨之處**。

### 2.3 §3.2 —— J 欄格式（94 §2.1）

已改記：**J 欄只寫條件本文與其節次括號**，並附範例格式；
source class 標籤為 JSON 之內部欄位，不入工作簿。

**這正是該 gate 存在的理由，且它證明了 95 §5 之判斷**：
那 51 條拆分列自生成起就沒有任何檢查問過「這兩條在 test_item 欄上分得開嗎」。

華氏／攝氏兩列、`040-01` 之三個狀態值），合成之結果就會一模一樣。
**合成器取了 procedure 之最後一步，而那一步在這幾對裡不是它們的差別所在。**
