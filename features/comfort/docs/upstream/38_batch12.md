## 2. 「另一個 popup」—— 併入為成員 (h)，風險記於條目內

**處置與其餘成員相同**（照錄、`reasoning` 具名、開本 DR、不阻塞），
故依 50 §3 併入而**不另開項**。

**但其後果不同，已於該成員條目內明記**：

> 其餘成員之風險為「測試員不知從何進入」；
> **本項之風險為「不同測試員挑到不同 popup，三節四條之結果不可比」** ——
> 同一條 TC 在兩次執行間可能踩到不同的下層 popup，
> 其「非可選區域」與「可選項」之版面各異。

**風險之記載屬該成員，不需為它另開一項** —— 56 §2 之這句話值得記，
因為「處置相同者不分類」與「後果不同須記下」看起來衝突，實則不衝突：
**分類看處置，記載看後果。**

## 4. `declared-at-tc-count` —— 改以 `content-sha` 為門檻

### 4.1 機制

每個 `function-axis-reverse-test` 區塊增 `content-sha`（12 碼），
其雜湊來源**逐一具名於 profile**：

```
axis / function-keywords / removed-interface-keywords /
axis-pc-keywords / judged-at-tc-count / judged-at-provenance
```

**不參與雜湊者**：`declared-at-tc-count` 自身、`judged-at`、註解行 ——
**它們記的是「何時」，不是「什麼」**。

`lint_tcs.py` 之 `axis-type-reverse-test` 增一項檢查：重算雜湊並與記錄比對，
不符即 FAIL，訊息指名「改了內容而 `declared-at-tc-count` 沒跟著動」。

### 4.2 反向驗證

```
recorded : 38a2ea8458ec
computed : 38a2ea8458ec            -> 相符
改 function-keywords 後: 6b9862b0e87f -> 會 FAIL
只改 declared-at-tc-count: 雜湊不變   -> 正確地不在雜湊內
```

第三項是關鍵：**若 `declared-at-tc-count` 也參與雜湊，這個機制會自我循環** ——
更新時點會改變雜湊，改變雜湊又要求更新時點。已排除，並實測確認。

### 4.3 通則已寫入 `RUNBOOK.md`

> **一個記錄「何時」的欄位，若隨每輪重寫，記的就不再是那個「何時」。**

並記其為**第二次**（前次為 `provisional` 之重建自行重算，32 §1.5），
以及兩者之修法相同：**以內容為判準，不以輪次為判準**。

自查兩問亦已記：(1) 這個欄位記的是**內容之屬性**還是**流程之屬性**？
(2) 若我什麼都沒改而重跑一次，它會不會變？**會變就是錯的。**

### 6.2 一處不對稱，本批不停而具名待裁

批次 9 曾停下 `2.11` 之 `015-04`／`015-05`（SYNC 之前後排作用），理由是
「車輛是否配備後排氣候不在既有軸內」。

**本批之 `16.11` 有逐字相同之句子，而 037 對 ch16 側產出了 leaf**
（`116-03`／`116-04`），故本批**產出了 `-224`／`-225`**。

> **同一行為，ch2 側停下而 ch16 側生成。**

理由是 037 之分解不同：ch2 側該二 leaf 之可觀察量須另有後排氣候之配置條件，
而 ch16 側之 `16.11` 自身即承載該句。**但這個理由不完全站得住** ——
兩節的句子逐字相同，配置需求理應相同。

**本批不回頭改批次 9，也不停本批**，而是具名此不對稱待裁（§9.2）：
要嘛 `2.11` 之二 leaf 應解封，要嘛 `16.11` 之二條應停下。**兩者不該並存。**
