## 1. 覆核結論：**核可。停手正確。**

**連續兩輪之停手皆為正確之判斷**，且二者非同一理由：
V25 停於「新形態未經 pilot」，本輪停於「四種形態中三種之範例未查」。
**後者為前者之細化 —— 執行層未以「已在做 pilot」為由略過範例查證。**

具名嘉許四處：

1. **§2 之形態實測推翻本層之列舉。** R-VF72 二列四種形態，
   實測為 **六種**：本層漏列 `訊號上行型`（124 條）與
   `設定顯示與修改型`（6 條），而所列之 `狀態轉換型`／`值域切換型`
   **實為 0**（已依令具名「不存在」，未以他條充數）。
2. **訊號送出型 vs 訊號上行型之區辨。** 前者以顧客操作為刺激、斷言訊號；
   後者以 HW 訊號為刺激、斷言畫面。**「二者之測試形狀相反」** ——
   此區辨若未做，124 條會被當作 318 條之同類而共用書寫式。
3. **§2.1 第 2 項之修正理由：「取得之來源先於值之個數」。**
   ENUM 判準搶在 PROXI 之前，致雙參數 PROXI 條文因方括號 ≥3 而誤歸值域切換型。
   **其修正非個案補丁，而是判準之排序原則。**
4. **已扣 pilot #1 之十條**，並具名首版曾命中 `PowerLiftgate/TailgateAlert-016`。
   其理由正確：**同一 leaf 於二 pilot 重複，其第二次之通過不構成新形態之證據。**

**§1 之斷言範例查證充分**：`MESSAGE.Signal = <raw> (<Label>) is transmitted／is sent`
與 SWC 0708／R-VS52 一致，**無須回退、無須自創**。

## 2. 分析層之錯 —— R-VF72 三之範圍過窄

R-VF72 三令「訊號斷言型之書寫形式須窮盡既有範例」，
**其只涵蓋本層當時所知之一種形態**。而 pilot #2 之十條橫跨四種，
其中三種之範例查證**未被任何條文要求**。

**本層之列舉一旦被寫成條文之適用範圍，該範圍即成為上限。**
執行層未以「條文只要求這一種」為由書寫其餘三種，而是停手回報 ——
**其做法較條文所令者為嚴，且為正確。**

**R-VF74 為其更正**（§3）。

## 3. R-VF74 —— 範例查證之義務及於每一種將被書寫之形態

```
R-VF74（範例查證之範圍，分析層裁定 2026-08-24）

**R-VF72 三更正為**：

  **凡一批之產出將涉及某書寫形態，而該形態於本 feature 尚未定形者，
  生成前須先實測 Part 1（或其他已交付線）之既有範例並逐字回報。**

  **其範圍由該批之實際形態決定，非由下放包之列舉決定。**
  下放包所列之形態為**已知者**，非全集（R-VF71 三之同一性質）。

  逐形態之處置：
    有範例      → 依之，逐字回報二至三個實例
    無範例      → 回退至最近之同族既有式，**具名其為回退**
    二者皆無    → **停手回報，不自創**

  **一批含 N 種形態者，須完成 N 次查證方得生成**，
  不得以其中一種已查而書寫其餘。

**成因**：R-VF72 三只令查訊號斷言型，而 pilot #2 實有四種形態。
**若執行層照條文之字面行事，其中三種即為自創。**

**附帶認定**：上繳 §5 所列之三項未查者，本條認其為必查：
  1. `propId = X and value = [Y]` 式與 Part 1 之 `MESSAGE.Signal` 式
     **不同層**（Android 屬性 vs 匯流排訊號），其對應關係
  2. `訊號上行型` 之**畫面斷言**實例（Part 1 之實例其斷言仍為訊號）
  3. `設定顯示與修改型` 之實例
```

**掃條文正文中之委派語**（`managed in`／`handled by`／`not HMI`／
