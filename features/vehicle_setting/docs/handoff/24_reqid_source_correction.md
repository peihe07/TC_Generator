## 0. 分析層之錯誤

23 包判定「237 個 Functional leaf 中僅 4 個可取得 reqid」，
並據此開 DR-16（High，阻塞 N 欄）。**該判定為誤，DR-16 撤銷。**

**成因**：分析層把「CFTS044 reqid」預設為文件內出現之
`CFTS044-NNNN` 字面形態（如 `CFTS044-1520`），
**未先確認 reqid 之定義為何**，即以該形態去掃素材。
掃出 4/237 之後，把「我方假設之形態找不到」記成「素材缺對照」。

**同一錯誤類型第三次**（A-VS12：正則沒設計到 `SYS-RA-CFTS100`；
00B §0：只掃 `$var$` 形態而漏訊號路徑記法；本次）。
共同形態：**以自己假設的形態去掃，掃不到就宣告資料缺**。

```
R-VS34（分析層裁定 2026-08-20）
以某識別碼／記法為判準進行掃描前，須先確認**該識別碼之定義**
（其在來源中之實際承載欄位與形態），並於報告具名該確認之依據。

未確認定義即掃描，且以「掃不到」為結論者 ——
該結論記為「**假設所致，非資料所致**」，不得據以開 DATA_REQUEST。

理由：本 feature 已三次以此形態誤判（A-VS12／00B §0／DR-16），
其中兩次導致對上游開出不必要之請求或錯誤之缺口記載。
```

## 1. 正確之取值來源（Pei 2026-08-20）

```
R-VS33′（取代 23 包 §1 之 R-VS33 實作段；意旨不變）
`specification_reference`（036 N 欄）之值為 CFTS044 之 requirement id。

**該 id 即 SYS2 `Basic Report` 之
`SYS2 來源需求項目ID  Source Requirement items` 欄所載之值**
（7 位數物件 id），亦即 CFTS044 docx 內條文區塊之自身標頭
（`4858298: [Artifact Type:…]`）與章節標題之大括號標記（`{4857897}`）。

取值路徑（即 R-VS2 之錨鏈，末段改取 id 而非章節號）：
    037 leaf → `SYS-RA-CFTS044-N`
             → SYS2 `Basic Report` 第 N 筆資料列
             → 該列 `Source Requirement items`
             → **即為 reqid**

書寫形式：`CFTS044-<7 位數>`，例 `CFTS044-4858298`。

多值者依 R-VS14 逐一列出，**依 7 位數之數值由小至大排序**。

`CFTS044-NNNN`（如 `CFTS044-1520`）為文件內之交叉引用與修訂敘述所用之
舊編號，**不是 reqid**，不得填入 N 欄。
```
