## 2. 甲 —— 67 條之 AH 補記，逐字，於實寫前完成

```
R-VF-甲（`not clear` 轉錄之補記，分析層裁定 2026-08-24）
【落檔取實測最大 +1，回報實得之號】

**補記。** 67 條之 `remarks` 補入 `R-VF15` 所令之轉錄。

**取「逐字」，不取定型句。**

  **理由**：定型句使 67 條同文，其所載之資訊等同於一個旗標；
  **而旗標已存在於 `writability.tsv` 之 `vcvm_not_clear`，
  交付物中再放一次同文之句不增任何資訊。**
  **逐字則使審查者得見上游究竟寫了什麼** —— 其為 R-VF15 之立法目的
  （「上游自述 `not clear` 者逐字轉錄」，**條名即「逐字轉錄」**）。

  **形式**：`Upstream Verification Criteria: <037 之 vc 欄逐字>`；
  `vm` 欄亦含 `not clear` 者，另起一行 `Upstream Verification Method: <逐字>`。
  **不截斷、不改寫、不正規化。**
  **逾 500 字元者具名回報待裁**（截斷規則不得由本層預先自創）。

**時機**：**須於實寫之前完成。** 此非偏好而是合規要件 ——
`R-VF26` 二令其於 TC 書寫時履行；工作簿現為全空（§三-3 實測 0 列），
**故現在補即為「書寫時」；一旦寫入，補記即成回溯編輯，為 R-VF26 二所禁。**

**其改動 67 條已 commit 之 TC 之 `remarks` 欄** —— **不受 R-VF14 拘束**，
因 R-VF14 之「已交付」依 `R-VF24` 為判準 (a)（已寫回並 tag），
而**現無任何 TC 已交付**。

**補記後須重跑 dry-run**，AH 非空數應為 **2 + 67 = 69**。
```
