## 2. 假陰性 —— 立為通則

§2.1：`\bseat\b` 於 `seats` 不匹配，v1 得 30、少 13，全為複數形。

執行層之自陳值得逐字保留：

> 若止於 v1 而回報「詞界重測得 30，00D 高估 13」，那會是一個錯誤的更正 ——
> 且因為方向看起來「更嚴謹」而不易被質疑。

```
R-VS29（更嚴格判準之驗收，待 Pei 裁）
以更嚴格之判準（加詞界、加大小寫、加必要條件）重測而**命中數下降**者，
不得逕行接受該下降。須：

(1) 逐筆列出「舊判準命中而新判準未命中」之差集
(2) 逐筆判定其為**真偽陽性**（舊判準過寬）或**假陰性**（新判準過窄）
(3) 差集非空而未逐筆判定者，該次重測**不得作為更正之依據**

理由：更嚴格之判準使數字下降時，其方向與「修正高估」一致，
因而不易被質疑；但同一個下降也可能來自新判準本身之缺陷。
**兩者在計數上不可分辨，只能逐筆分辨。**

實例：`\bseat\b` 於 `seats` 不匹配，使 43 降為 30；
13 筆差集全為複數形，屬假陰性，非偽陽性。
```

## 3. §6-2 之方向性缺陷 —— 分析層設計錯誤，須補反向表

上繳指出：本表為 **Comfort → 本 feature** 之單向，
而 R-VS7(a) 之委派句**由本 feature 側發起**：
TC 撰寫時的問題是「**我這個 leaf 該不該委派**」，不是「這個 Comfort leaf
對應到誰」。

**本表目前不支援其真正被使用的方向。** 該缺陷源自 19 包 §2 之 W-9 規格 ——
分析層以 Comfort 側之關鍵詞命中為起點設計，而使用端在另一側。

**不能以機械反轉解決**：本表之 43 條係由 Comfort 側之關鍵詞命中選出；
本 feature 之某個 leaf 若其 Comfort 對應物未命中那五組關鍵詞，
反轉後仍看不見它。**反向須自本 feature 側重新掃。**

```
W-29（反向委派表）
產出 `docs/reports/delegation_lookup.tsv`，以**本 feature 之 237 個
Functional leaf 為列**，每列回答：

  leaf_id / layer3 / delegate（yes|no|blocked） /
  comfort_leaf_ids（逗號分隔，得為空） / basis（具名依據） /
  blocked_ref（若 delegate=blocked，記其 TLM HMI Document 條文 id）

判定順序：
 1. 該 leaf 屬 R-VS7(b) 之 16 個 BLOCKED leaf → delegate=blocked
    （其畫面層仍屬本 feature，依 R-VS17 標 BLOCKED，不走委派）
 2. 該 leaf 之 Layer 3 於 06 輪之表中有對應 Comfort leaf → delegate=yes
 3. 自本 feature 側重掃：以該 leaf 之 `Requirement Description` 抽出
    功能詞（座椅加熱／通風／方向盤加熱／頭枕／Stop-Start 等），
    回查 Comfort 037 之 498 leaf **全集**（不限 06 輪之 43 條）
    —— 有對應者 delegate=yes 並註明「反向新增」
 4. 皆無 → delegate=no

**須列出「反向新增」之筆數**：其為 0 才證明 06 輪之 43 條已窮盡；
非 0 則 06 輪之單向表有漏，須於上繳具名。
```

```
W-30（BLOCKED 16 leaf 之具名與交叉）
列出 R-VS7(b) 之 16 個 leaf 之 id（16 引 TLM HMI Document ＋ 1 引
PDO graphics，共 17；其中 16 者為 TLM），並與 06 輪之對應表交叉：

  - 該 16 leaf 中有幾個同時出現在 06 輪之委派對應中？
  - 重疊者之處置：依 R-VS17 標 BLOCKED，或依 R-VS7(a) 委派？

**此為條文衝突之檢查**：R-VS7(b) 說其畫面層仍屬本 feature，
R-VS7(a) 說畫面行為委派 Comfort。**同一 leaf 若兩者皆適用，
現行條文未定其優先序。** 有重疊即回報，由 Pei 裁。
```
