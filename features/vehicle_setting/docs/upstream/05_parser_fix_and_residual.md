## 2. 不符項目（不自行調和）

### 2.1 驗收錨點 (a)：**11 個鍵值 vs 11 個條目**

`ESS_ENG_ST` 之 `Format` 儲存格原始 repr（自 `inputs/` 讀取，未正規化）：

```
'4 bit signal\n1 = ENS Stopped\n2 = ENS Request Start\n3 = ENS Running\n
 4 = ENS Stop Pending\n5 = ENS Start protection\n6 = ENS Start inhibit\n
 7 = ENS disabled\n8 = ENS_IHB_LATCH\n9 = ENS Starting\nF = SNA'
```

**11 行，其中第 0 行 `4 bit signal` 為位元寬宣告，不含 `=`，非鍵值對。**
故：**條目 11、鍵值對 10。**

下放包之錨點寫「須切得 **11 個鍵值**（`4 bit signal` 行 ＋ 1~9 ＋ `F = SNA`）」
—— 其括號內之列舉即 **11 個條目**，而 `parse_format_cell()` 回傳的是**鍵值對**。
**兩個數字量的是兩件事。**

**不自行調和**：未改解析器使其把 `4 bit signal` 湊成一個鍵值對
（那會造出一個不存在的鍵），亦未逕行改寫錨點。
**兩個數字都量出來報**：條目 **11**（換行確實保留，此即該錨點之實質目的）、
鍵值對 **10**。

> **實質目的已達成**：若壓平，`_split_cell` 只會得到 1 個條目而非 11。
> 錨點所要驗的「壓平則切不出」已被證明。

### 2.2 位元寬宣告是 DR-15 之直接證據（**未預期之發現，見 §5**）

`4 bit signal` 這類行**本身帶資訊**。逐 token 檢視：

| LID | 條目 | bit 宣告 | 鍵值 |
|---|---|---|---|
| `HeatedSeatFL` | 9 | **`2 bit signal (FL_HS_STATSts)`** ＋ **`1 bit signal (FL_HS_STATFailSts)`** | 四階 ＋ Fail 二值 |
| `FL_HS_RQ` | 2 | **無** | `0 Not_Pressed`／`1 Pressed` |
| `FR_HS_RQ`／`FL_VS_RQ_TGW`／`HSW_RQ_TGW` | 2 | **無** | 同上 |

→ **LID 表自身內部一致**：狀態訊號 2 bit 四階、失效 1 bit、**請求訊號二值無階**。
**與基線 DBC 完全相符。** 即 DR-15 之衝突為 **CFTS044 單方對請求訊號賦予階數**，
非 LID／DBC 之間的分歧。**此佐證使 DR-15 之提問更精確**，已補入 `DATA_REQUESTS.md`。
