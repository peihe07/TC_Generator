## 6. 獨立判斷（canon §8.2 §6）

1. **W-166 是本 feature 迄今最有價值的一次檢查，因為它是唯一一個「跑」而非「讀」的驗證。**
   五輪來所有的一致性檢查都是讀產物、讀判準、比對兩個 JSON 欄位；
   **這一次是把宣稱的過程真的執行一遍。** 結果：**鏈不成立。**
   而缺的那一層之所以查得出來，是因為 git 留了 48 輪的 commit ——
   **若那次改動未入庫，這個缺口永遠不可見。**

2. **48 輪那次就地改動，是我做的，而我當時沒有意識到它破壞了什麼。**
   D-3 說「`delivery_disclosure.md` 依 R-VS69 重列」——
   我為了讓揭露表與判準一致，**回頭去改了五個已定版的 JSON**。
   產物因此正確，判準因此通過，**而產生路徑因此斷了一節**。
   **R-VS53 從那一刻起就已經不成立，只是我們到今天才量到。**

3. **W-167 的 10/10 我不認為足以支撐 R-VS6 的全部結論。**
   4.4% 的抽樣，而 R-VS79 立條的理由是「解析層之偏差不可見」——
   **不可見的東西，抽 10 條看不見它，和它不存在，是兩回事。**
   我建議：**L3 應改為全量**。225 條的直讀比對成本很低
   （本輪 10 條的執行時間不到一秒），**沒有理由抽樣。**

4. **§2.3 那兩處下拉，41 輪和 87 包都沒提，是因為沒有人去讀過 sheet6.xml 的 `sqref`。**
   五輪來我們一直在講 x14 的 R 欄，**而 P 欄從第 133 列起也沒有選單** ——
   那是 `Priority`，一個 §9 每輪都在檢查其值域的欄位。
   **檢查驗的是 JSON 裡的值，不是工作簿裡有沒有讓人選對值的機制。**

5. **交付物的實際狀態，講清楚：**
   225 條 TC 內容通過五套機械檢查；
   **R 欄無選單、P 欄與 T–Z 欄自第 133 列起無選單**；
   **11 批 80 條之首版不可重放，且其變更鏈經實跑證實缺一層**；
   **156 條（69%）未經人工覆核**。
   這些不因「八項回掃全數 0」而消失 —— **那八項驗的是條文一致性，不是這四件事。**
