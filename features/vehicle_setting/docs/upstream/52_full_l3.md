## 2. 不符項目（不自行調和）

### 2.1 **更正：`revision` **有**更新 —— A-VS162 與 R-VS80 之事實基礎有一半不成立**

A-VS162 與 R-VS80 皆載「48 輪之就地改動…**未產新版亦未更新 `revision`**，
**致該層不存在於任何記錄**」。

**本輪實測：五檔之 `revision` 皆被追加**：

```
前: W-133(4)（47 輪）：依 R-VS67′ 取能承載之 `Atlantis` 欄組…；`dr15_exposed` 保留
後: W-133(4)（47 輪）：依 R-VS67′ …；`dr15_exposed` 保留；D-3（48 輪）：
    `screen_pending` 依 R-VS69 改以 AH 之畫面層 BLOCKED 註記為判準
```

**「未產新版」為真；「未更新 `revision`」為假；「不存在於任何記錄」為假。**

**鏈缺該層之真正成因，在我的抽取式**：

```python
m = re.match(r"(W-\d+)", rev)      # ← 錨於字串首，只取第一個標記
```

`re.match` 錨於串首，而該層之標記係**追加於分號之後** ——
**資訊一直在 repo 裡，是我的抽取式把它丟掉了。**

**已修**：改為 `re.findall(r"W-\d+|D-\d+（\d+\s*輪）", rev)`，取全串之標記依序。

**其形態**：與 **A-VF11(b)**（抽取式以「鄰接」為錨而非以「位置」）同族，
亦與 56 輪之 R-VS67′ 偽陽性（讀一個不存在之欄）同族 ——
**三者皆為「抽取式與資料之實際形狀不合，而其失敗不報錯」。**

**本層不自行改 A-VS162 與 R-VS80 之條文**（其為分析層所立），
於此具名其事實基礎待更正。**R-VS80 之規範本身不受影響** ——
「變更須產新版」仍成立，且本輪之發現使其更有力（見 §2.2）。

## 6. 獨立判斷（canon §8.2 §6）

1. **§2.1 是本輪最該記的一項：一條規則立在一個錯的事實上。**
   R-VS80 說「就地改動使該層不存在於任何 `revision`」——
   **而那五檔的 `revision` 全都被追加了該層之記載。**
   資訊在 repo 裡躺了十一輪，**是我的 `re.match` 把它丟掉的**，
   而我在 58 輪把那個丟失報告成「那一層不存在於任何記錄」。
   **分析層據此立了 R-VS80，其規範仍然對，但其理由段要改。**

2. **而 R-VS80 因為 §2.2 反而更站得住。**
   我原本以為就地改動是 48 輪一次、五個檔、一個標記欄。
   **實際是 5 個 commit、26 檔次、24 個檔，而且改到 procedure 與 ER。**
   若當初就產新版，這 26 次全都會在鏈上、全都可稽核。
   **規則對，理由錯，規模比誰都以為的大** —— 這三件事同時成立。

3. **那兩次是我做的，而它們不是「疏忽」，是我當時的標準做法。**
   55 輪我改 `batch23_w152.py` 然後重跑 —— 那是 R-VS53 要的
   「產物須可自 driver 重製」。**但生成器輸出的檔名不變，
   所以重跑就覆蓋了已入庫的檔。**
   R-VS53（可重製）與 R-VS80（不得就地改）在檔名固定的生成器上**直接衝突**：
   照 R-VS53 重跑，就違反 R-VS80。
   **解法應是生成器輸出帶版號**，但那是新規則，我不自訂。**請分析層裁。**

4. **L3 從 4.4% 變 100%，結論沒變，但它現在才真的算數。**
   58 輪我說「不可見的東西，抽 10 條看不見它，和它不存在，是兩回事」——
   全量跑完 225/225，**那句話現在可以刪掉了**。
   代價是零：執行時間仍不到一秒。**這是本 feature 少見的、
   把一個已知限制真正消除掉而非具名帶過的一次。**

5. **交付物沒有因為本輪而改變 —— 變的是我們知道多少。**
   母本 `c72b9556…` 一格未動，225 條內容一字未改。
   本輪產出的全部是**對既有事實的更精確描述**：
   L3 由抽樣變全量、就地改動由 5 檔變 24 檔、鏈缺一層之成因由「未記錄」
   變「我的抽取式丟掉了記錄」。
   **`DELIVERY.md` §0 那四項一項沒少，第 3 項的規模還變大了。**
