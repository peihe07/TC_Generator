## 2. 不符項目（不自行調和）

### 2.1 **18 檔次不是「改動」而是「欄位之新增」，且其為下放包逐字所令**

A-VS163 載該 26 檔次之欄位差含 `screen_pending` 165／`dr15_exposed` 24。
**本輪回查其性質：`70b75d0` 之 15 檔次與 `baeb58a` 之 3 檔次，其前版根本沒有該欄。**

```
batch15.json  601d809→70b75d0
   前版有 `screen_pending` 欄? False   後版? True
   新增之欄: ['screen_pending']   移除: 無
```

其依據為 **68 包 D-4 逐字**：

> `generated/` 各批次**增** `screen_pending` 欄（68 包 §2）；

**即：分析層令「各批次增一欄」，而執行層照做就必然是就地改動。**
**這正是 R-VS80「下放包之措辭亦受本條拘束」一句所指之形態，
且其為該句成立之第一個實證。**

**本層之量測法有一個界限**：`ta[k].get(fld) != tb[k].get(fld)` 於
**欄位不存在時回 `None`**，故「新增一欄」與「改一欄之值」在該量測下同形。
**A-VS163 之「165 條 `screen_pending` 被改」因而高估** ——
其 133 條為新增、26 條為重標、6 條為 48 輪之二次重標。

即 **R-VS78** 所規範之形態 —— **本層第三次撞上同一件事。**

**不自行改 A-VS163 之條文**，於此具名其數之構成待更正。

## 6. 獨立判斷（canon §8.2 §6）

1. **§2.1 是本輪最該記的一項：那 18 檔次不是違規，是照令執行。**
   68 包 D-4 逐字令「`generated/` 各批次**增** `screen_pending` 欄」——
   **一個已定版的檔要增一欄，除了就地改沒有別的做法**（其時尚無 R-VS81）。
   R-VS80 說「下放包之措辭亦受本條拘束」，**這 15 檔次就是那句話的實證**，
   而且它是在該條文立出來的**十二輪之前**發生的。
   **A-VS163 把它們算成「本層之工程缺陷」，那個歸屬不對。**

2. **§2.1 也是我第三次撞上 `.get()` 的回退值。**
   56 輪：讀一個不存在的欄 → 28 條偽陽性。
   59 輪：`re.match` 錨於串首 → 丟掉追加的標記。
   本輪：欄位不存在時 `.get()` 回 `None` → **「新增一欄」與「改一欄」在量測下同形**。
   **R-VS78 規範的正是這個形態，而我在它立出來之後又撞了一次** ——
   因為 R-VS78 說的是「首跑前驗欄位存在」，而這次欄位**在其中一版存在、
   另一版不存在**，**兩版比對時該檢查無從施行**。
   建議：**凡兩版比對，先列其欄位集之差**，再談值的差。本輪已如此做（§4 條 3）。

3. **§2.2 那個差 1 的錯誤，活了三輪，而且我每輪都在引用它。**
   58 輪報「鏈長最長 6」、59 輪報「7」、89 包據以問「由 6 層變為幾層」——
   **一個報告內部的矛盾，透過上繳包傳到了下放包的問題裡。**
   表格和摘要句取自同一份資料的兩次計算，而我只看摘要句。

4. **§3 未驗的第二項，我要主動標為代擬之邊緣。**
   `baeb58a` 那三檔的依據，我寫「其時之下放包令各批增該欄」——
   **我沒有真的去 24–26 輪的下放包裡找到那句話**，
   是看到它與 `screen_pending` 同型就推過去了。
   **這跟我 56 輪編出 14 個檔名是同一個動作，只是這次規模小、而且我當場說了。**
   若分析層要那句逐字，我下輪去找；找不到就得改記為「依據未尋得」。

5. **R-VS81 解掉了衝突，但它只對「未來的輸出」生效。**
   現行 24 檔已被就地改，89 包裁定不追改 —— 我同意。
