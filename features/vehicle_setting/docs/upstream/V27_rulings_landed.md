## 2. R-VF74 於首次執行即攔到本層之一個錯 —— 且該錯之形態為新

本條所令之查證，本層**查錯了標的**，詳見 §3 與 A-VF24。
**其為 R-VF74 之最強佐證**：若無本條，該形態根本不會被查；
而有了本條，查了、得 0、判「查無」，**其結論仍為偽**。

即：**R-VF74 使「查」成為義務，但未使「查對」成為義務。**
本層據此提一條文之補充建議，見 §5。

## 4. 本層對本包 §2 之回應

本包 §2 稱「本層之列舉一旦被寫成條文之適用範圍，該範圍即成為上限」。
**本輪之 §3 第 1 項為同一形態之另一面**：
本包 §5 W-VF65 之三項**其措辭亦成為搜尋鍵**，
本層以該措辭逐字搜之而非以其**意圖**搜之。

**二者之共同解**：下放包列舉待查之形態時，
宜同時具名「該形態於**產出**中長什麼樣」，而非只具名其於**條文**中長什麼樣。

## 5. 請裁

**建議 R-VF74 增一款**（本層不自訂，請分析層裁）：

```
查證之標的須為**產出（TC）之書寫式**，非條文之措辭。
以條文措辭為搜尋鍵而得 0 者，其結論為「未查」，不得記為「查無」；
須改以產出側之語彙重搜，或具名「無法構造搜尋鍵」後方得回退。
```

其依據：條文之 `propId = X and value = [Y]` 屬 Android 屬性層，
**TC 本就不寫該層**，故以其為鍵必然得 0 —— 該 0 不含任何資訊。

## 6. 本包是否仍有該驗而未驗者 —— 獨立判斷

**有二項。**

1. **本包 §3 附帶認定第 1 項所問之「二者之對應關係」，本層只答了一半。**
   已答：Part 1 無 Android 屬性層之實例（0 行，屬實）。
   **本輪補查之結果（部分答）**：repo 內之 LID 快取 `data/_lid_argroups.json`
   有 **3021 個鍵，其全為訊號名，無 `propId` 之概念**；
   且 **`PLGAlert_Req` 不在其中**（該快取為 Part 1 Comfort 範圍之欄組）。
   **故以現有之 LID 快取無法建立該對應。**
   **仍未答者**：LID 之**原始工作簿**是否另有 propId 欄 ——
   本層自 `writability_driver.py` 追不到其來源路徑（快取為既有產物，
   其產生腳本不在 `scripts/` 內），**具名為未查，非查無**。
   **其影響**：條文之 `propId = PLGAlert_Req` 與
   TC 之 `TELEMATIC_VEHICLE_SETUP.PLGAlert_Req` 之等同，
   現行係由**訊號名相同**推得，**未經來源證實**。
   **本層判其為真缺口，非形式問題** —— 318 條訊號送出型全數依賴該推定。
   **請裁**：是否須先取得 LID 原始工作簿以證實該等同，或認可「訊號名相同」為據。

2. **R-VF74「二者皆無 → 停手」之分支，本輪從未被觸發，故其未經實測。**
   四種形態皆得先例或有可回退之式。**一個從未執行過之分支，
   其行為與其不存在不可分辨** —— 此為 A-VS106 之同一形態。
   本層無法自證其會停手，具名之。
