# TRACE_MERGE — 併入列之追溯台帳（SW Update）

**R-SU38**：經上游確認「驗證併入他列」者，該列於工作簿**無屬於自己之 TC**，
而 SWE.6 之追溯性要求每一需求列有其覆蓋。
**其解不是替它寫一個 TC**（那正是被判為無驗證點者），**而是記其併入之去向**。

> ### ⚠ **上游未確認前，被併列不得自工作簿缺席**（R-SU38(d)）
>
> 其狀態為 `PENDING`（掛於該列之 TC），**不是「已併入」**。
> **「分析層認為可併」與「上游確認可併」是兩件事。**
>
> 故下表二列目前**仍有 TC 在簿中**（`newR1L-SU-017`），
> 其三欄各掛一 `PENDING: DR-SU3`。**本表現為預備狀態，非既成事實。**

**交付時須附本台帳**（R-SU38(c)）—— 其為追溯矩陣之補件。
**交付面是否認可本記法屬 Tier 3**（R-SU38(e)），提 Pei 裁；未裁前依 (d) 掛 `PENDING`。

## 依據之詳

### `SWE1-FOTA-313`

其 Description 二句拆解後：

1. 「WiFiUpdateService 應**協調** `4907667`–`4907672` 六個錯誤條件之處理」
   → 該六條件之處理即 `315`–`320` 各列，**逐一有其專屬 TC**；
2. 「SWMC 應處理該六條件並向 WiFiUpdateService **回報狀態**」
   → 回報之對象為服務間訊息（R-SU25 之不可觀測面），
   且 `SWE1-FOTA-358`（`Update Status Reporting to SWMC`）為其專屬列。

**兩句拆完，沒有剩下任何有外部表徵且無他列承擔者。餘量為空。**

**曾被考慮而否決之餘量**（記錄，供覆核）：
「多個中斷條件併發時處理錯亂」——
依 **R-SU37 v2(c)** 之檢定二問：
- 問 1（要素是否見於其 Description）：**否** ——`313` 只說協調六條件之處理，未提併發；
- 問 2（是否已由本組他列所擁有）：**是** ——併發屬本組其他列（`321`–`329` 之範圍）。

**故該情形為推想，不得作為 `313` 之驗證點**（PLAYBOOK (35)）。

## 一項未解之交付面問題（隨本表提出）

R-SU38(c) 令交付時附本台帳，惟**現行之追溯矩陣格式未定義「併入」這一種覆蓋**。
其可能之處置有三，**執行層不逕定**：

1. 追溯矩陣中該列填被併入各列之 TC id（一對多）；
2. 該列標為 `Merged`，另附本台帳為佐證；
3. 上游不接受併入 → 被併列須有自己的 TC，**而其驗證點為空** ——
   屆時只剩「寫一個驗不到東西的 TC」與「該需求列不可驗證」二者擇一，
   **二者皆須上游知情**。

**此為 Tier 3 之事項**（R-SU38(e)），提 Pei 裁。
