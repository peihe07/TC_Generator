## 7. 獨立自評（**入 BACKLOG，不立條**）—— §六-6：TC-21 之還原步驟是否可行

**答：我判其不可行，且本 TC 之二次執行設計因此不成立。**

**(甲) 該步驟之內容。** TC-21 procedure 第 3 步：

> Reconfigure the update campaign on the OTA Server to update type Silent
> **and restore the head unit to its pre-update software version**

**(乙) 為何我判不可行 —— 三點，其中第三點是決定性的。**

1. **本 feature 之全部素材中查無「還原／降版」之任何需求或程序。**
   037 之 311 列、CFTS_57、SYSAD 皆無 rollback 至任意版本之機制描述；
   `4907673` 之 Table 4-6 講的是中斷後之續傳，不是降版。
2. **`Rollback Protection` 是一個 Test Set**（framework 第 8 組所涉之
   `Error Code List` 階段之一），其名即**防止**回退 ——
   **一個以防回退為需求之系統，其台架上是否可回退，恰恰不能假設。**
3. **縱使可行，該步驟本身即為一個未經驗證之操作**：
   還原之後 HU 是否回到「與更新前**等價**」之狀態（而非只是版本號相同），
   **無任何需求可據以確認**。而 TC-21 之判決依賴二次執行之**可比性** ——
   **第二次執行之起點若不可確認，二次之差異就不可歸因於更新類型。**

**(丙) 其後果不只是「這一步做不到」。**
TC-21 之驗證單元為「**伺服器所設之類型決定所適用之流程**」，
而該單元**本質上需要至少二次執行** —— 一個 campaign 只有一個類型。
**故問題不在措辭，在設計。**

**(丁) 三個可能之解（執行層不裁）**：

- **(甲解)** 用**兩台 HU**（或同一台之二次乾淨刷機），各配一個類型 ——
  其可行性同樣須台架端確認，**與 T47f 之三項未知同族**；
- **(乙解)** 拆為二個 TC（Regular 一、Silent 一），
  各驗「該類型之流程被套用」，**而「由伺服器決定」這一點改由
  pre_conditions 之差異隱含** —— 惟如此則**驗證單元被稀釋**：
  二個 TC 各自驗的是類型之行為（那屬 `Silent Update` 與 `Update Policy` 二組），
  **而「伺服器決定」本身無 TC**；
- **(丙解)** 掛 `PENDING` 並開 DR 求「更新類型切換之台架程序」。

**(戊) 我的傾向：(丙解)，理由與 batch 2a 同型。**
(乙解) 會使一個真實存在之驗證單元消失於二個較窄之 TC 之間 ——
**那正是 R-SU34 v3(e) 所指「本 TC 是否有屬於其需求單元之驗證點」之反面**：
不是本列沒有點，是**把點拆掉以求可執行**。

**已入 `BACKLOG.md`？否** —— **本項阻斷交付，依 B 檔之檔首規定進待裁表，不進 BACKLOG。**
