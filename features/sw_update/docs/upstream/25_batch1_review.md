### 2.3 ⚠ `I-sibling=0` **對本輪之關鍵問題無發言權**（**下放包未要求，執行層自查**）

該 0 有兩層範圍限制，**任一層都足以使它沉默**：

**(甲) 簿的範圍。** batch01 簿只有 4 列，`175`（`newR1L-SU-001`）在
`sandbox/pilot03`，**二者不同簿，sibling 檢查跨不到**。

故執行層另建**併簿探針**（`scripts/probe_sibling_9.py`，落
`sandbox/probe_sibling9/`，**非交付本非受檢物**）：pilot 5 列 + batch 1 之 4 列
= 9 列寫進同一本再跑 lint ——

```
  行計 A=0 … I=0  I-sibling=0 … U=6  V=0        exit 0
```

**仍為 0。**

**(乙) 判準的範圍 —— 這一層才是真正的原因。** 讀 `lint036.py:633`：

```python
def check_sibling_parens(rows):
    """I-sibling：同 Requirement ID 下多列括號行內容逐字相同。"""
    groups.setdefault((req_id.strip(), content), []).append(...)
```

**分組鍵含 `req_id`。** `175`／`179`／`184` 是**三個不同的 Requirement ID**，
**無論其括號行、Procedure、ER 多麼相同，該檢查在結構上永不觸發。**

> **正確讀法**：`I-sibling=0` 之語意是「**同一需求列底下沒有重複的括號行**」，
> **不是**「本簿無互相重複之 TC」。
> IN §4.3 之「sibling 兩列讀來相同 = FAIL」**其機器化只覆蓋了同 req_id 的那一半**；
> **跨 req_id 的偽通過（R-SU32(c) 所禁者）目前無任何機器檢查覆蓋。**

這正是 R-SU32(c) 已預言的事 —— 條文寫「於 lint 全綠、於 sibling 檢查亦可能
因措辭不同而過關」。**實測顯示比條文所述更弱：不是「可能過關」，是「必然過關」**，
因為它連比都不會比。

## 6. 獨立自評

### 6.1 §七-6 所問：**TC-8（`184`）與 TC-1（`175`）是否也構成 R-SU32(iii)**

**答：是。而且比 `179` 那一例更難察覺。**

**(甲) 先給機器側之事實 —— 逐行比對（`difflib`，非目視）。**

| 欄 | 行數 | **逐字相同之行數** |
|---|---:|---:|
| `test_procedure` | 5 vs 5 | **3** |
| `expected_result` | 5 vs 5 | **3** |

即 **10 行裡有 6 行逐字相同**。相異之 4 行，其相似度為 0.66／0.59／0.71／0.76 ——
**全部是同一件事的改寫**，除了一處：

```
TC-1 ER5: … contains no SW Update prompt and no progress notification
TC-8 ER5: … contains no SW Update prompt, no progress notification and no
          confirmation screen across the check, download and installation phases
```

**(乙) 那處增額，其可觀測性須分兩半看 —— 這是本題的關鍵。**

TC-8 之 ER5 比 TC-1 多了兩樣：

1. **`no confirmation screen`** —— 這一半**可觀測**。
   但它**已由 TC-6（download confirmation）與 TC-7（deployment confirmation）
   逐一驗過**，二者正是本批之前兩列。

2. **`across the check, download and installation phases`** —— 這一半**不可觀測**。
   TC-8 之 Procedure 第 3 步所產生的，是**一段連續錄影**
   （from the availability check until the software version changes），
   **與 TC-1 之錄影是同一段**。
   **該錄影上沒有任何階段界線** —— 靜默更新的定義就是畫面什麼都不顯示，
   於是「check 何時結束、download 何時開始」在畫面上**無任何表徵**。
   測試者拿著這段錄影，**做不出「三階段皆無提示」與「整段皆無提示」之區辨**。

**(丙) 合起來 —— TC-8 相對於已有之三列，其增額驗證點為零。**

`TC-1 ∪ TC-6 ∪ TC-7` 已覆蓋：無 prompt、無 progress notification、
無 download confirmation、無 deployment confirmation。
TC-8 之 ER 是這四項的**聯集**，**加上一個錄影證不了的階段宣稱**。

**故 TC-8 正是 R-SU32(c) 所禁之物的一個變體** —— 條文設想的是
「與鄰列**逐行相同**」，而 TC-8 是「與鄰列**逐行相同或同義改寫**，
其唯一相異處為一句**觀測不到**的措辭」。**後者更難察覺**，
因為 diff 看起來是有差的。

**(丁) 分析層 §五之區分，是措辭上的。**

下放包 §五 為 TC-8 寫的區分理由是「其 ER 第 5 行明列 check／download／
installation 三階段，為本列獨有之驗證點」。**「明列」是真的，「驗證點」不是**
—— 明列於 ER，而 Procedure 產不出能判定它的觀測。

**(戊) 執行層之處置：照原文產出，不改寫，掛在此處待裁。**
