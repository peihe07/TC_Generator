## 8. 獨立自評

### 8.1 §六.6 所問：5 個 TC 之 Procedure 有無在實機上不可執行者

**有，而且是 5 個全部有，成因同一。**

**(甲) 「Read 內部服務狀態」—— 5 個 TC 皆有，共 5 步。**

| TC | 步驟 | 讀取對象 |
|---|---|---|
| `-001` | 2 | the update metadata received by the **WiFi Update Service** |
| `-002` | 2 | the update type received by the **WiFi Update Service** |
| `-003` | 2 | the update type received by the **WiFi Update Service** |
| `-004` | 2 | the update type received by the **update service** |
| `-005` | 3 | the deployment status reported to the **update service** |

`WiFi Update Service` 是**內部軟體元件**，不是使用者可見物。
「Read X received by <內部服務>」要成為台架步驟，需要一條**帶外觀測通道**
（診斷服務、log、DID、vehicle property 讀取工具）。

**本 feature 之實測是：沒有任何已綁定之通道。**

- **DBC —— 不綁**（上繳包 01）：037 之三個 `$FOTA_MASTER.*$` 皆經
  **CarProperty Manager 之 vehicle property 介面**取得，非 CAN frame；
  兩份 `.dbc` 對 `FOTA` 之命中數 **0**
- **LID —— 不綁**：037 無 Logical Identifier 引用

即：規格側**指出了存在一個 vehicle property 介面**，
但**沒有任何綁定之素材說明它在台架上如何被讀取**。

**其中 `-001`／`-002` 更有一層內部矛盾**：該二 TC 之結論正是
**「靜默更新期間 HMI 完全不顯示任何東西」**。
若唯一之觀測面是 HMI，則步驟 2（讀出 update type 為 Silent）
**與步驟 4（螢幕上什麼都沒有）互相排斥** ——
**能讀到它，就表示有一條 HMI 以外的通道；而那條通道未被指名。**

**(乙) `-005` 步驟 2「Wait for the silent update deployment to complete」無時限。**
無逾時值之等待步驟在台架上不可判定「多久算失敗」。
037 與 CFTS 側是否有部署時限之規定，本輪未查（不在 T32 範圍）。

**(丙) `-003` 步驟 3 為 `PENDING`（DR-SU1）—— 已知，非新發現。**

**能誠實說的是**：5 個 TC 之 lint 全綠、Final Step 皆唯一、
欄位紀律皆合，**而它們有 5 步在目前的素材下寫不出台架動作**。
**這正是 lint 查不到的那一層** —— lint 查「這一行寫得合不合格式」，
查不到「這一行做得出來嗎」。

**執行層不改寫**（TC 屬分析層起草），列為待確認 #2／#3。

### 8.2 本輪之方法有無「答不到卻看似答到」之處

**有，在 §3 之「21 項中 18 項全 0」。**

那是本輪最像交付的一格，而它證明的範圍很窄：
**lint 是機械層之格式檢查**。它查到了 TC-3 之 PENDING 說明是中文（T），
卻**查不到** §7.1 所述之五個不可執行步驟 —— 因為那五步在格式上完全合規：
動詞不在禁用表、無情態詞、無 hedge、編號對齊、行尾無句號。

更值得記的是**二者之落點恰好相反**：
lint 抓到的那一列（`-003`）是**已知有 DR 而被刻意掛起**的那列；
lint 沒抓到的那五步散在**全部 5 個 TC**，包含看起來最乾淨的 `-001`。
**若只看 lint 報告，會得到「只有一列有問題」之印象，而實際上是每一列都有。**

### 8.3 一項我做了而下放包未要求的事

**§8.1(甲) 之「內部矛盾」論證 —— 回頭用 TC 自己的結論去驗它自己的步驟。**

T32b 只令跑 lint、T32f 之 §六.6 只問「有無不可執行之步驟」。
逐步讀一遍、指出「Read 內部服務」需要通道，就算答完。

我另做的是**把 TC-1／TC-2 之步驟 2 與步驟 4 對起來看**：
步驟 4 主張「螢幕上不會出現任何東西」，而步驟 2 要求「讀出 update type」。
**這使該 TC 之不可執行性不必依賴外部證據就能成立** ——
不需要去查有沒有診斷通道，光看這兩步就知道它們不能同時只靠 HMI 完成。

**記明此事之理由**：這是一種比「查素材有沒有通道」更強的論證 ——
前者可被一份新素材推翻（找到通道就解決了），
後者指出的是**TC 自身之內部一致性問題**，
它會逼出一個更精確的問題：**「那條通道是什麼，且它在靜默更新期間仍可用嗎」**
—— 而那正是若要發第二筆 DR 時該寫的東西。
