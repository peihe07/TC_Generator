### 1.1 §3.1 `002` 之 `at any point of the session` —— **分析層之造值，確認**

## 二、R-SU43 v2（抄入 RULINGS.md，逐字，append 於 v1 之後）

```
R-SU43 v2（判定核心之他值 —— 「明文」之限定與回查範圍）

v1(c)(d)(e)(f) 維持。(a)(b) 更正並補。

(a) v2 —— **ER 之判定核心，其所斷言之結果，須為該情境下規格所允許之唯一結果。**

    **「允許」限於明文，不含沉默。** 判別之精確表述：
    **「規格對本 TC 所設之情境，有無給出一個使該值為他值之
      **明文許可**、**建議**或**條件**？」**
      三者任一為是 → 失格；三者皆否 → 通過。**沉默不算。**

    三形態（上繳包 33 §6(丙) 實測皆有實例）：
      **明文許可**：`4907477` 之 `SHALL NOT … unless necessary for safety` → **失格**
      **建議**：`4907673` Table 4-6 之 `Complete the deployment`（RECOMMENDED）
        → **失格**（依建議實作者仍合規）
      **沉默**：`4907485` 之 `will display …` 未言「或不顯示」 → **通過**

    **沉默之資格另有一限**（上繳包 33 §6(丁)）：該句須為**直述式且無條件**。
    若其帶條件（如 `… if configured to do so`），
    則「條件不成立」即為一個明文之他值，**隨即失格**。

(b) v2 —— **回查之範圍**（v1 未定，只查錨物件會漏，上繳包 33 §3.2）：

    回查不得限於該 TC 之錨物件，**須及於**：
      1. 同一 037 列之**全部 facet**（例外常在同列之第二句）
      2. 同組之**兄弟列**
      3. 錨物件於 CFTS 中之**相鄰物件**

    理由：**例外與其規則往往是相鄰之二個物件，而錨定只取其一。**
    實例：`002` 之錨 `4907476` 不帶例外子句，例外在相鄰之 `4907477`。

    **本範圍與 R-SU16（兄弟區塊）同構** —— 前者處理「同一件事被拆成相鄰數列」，
    本條處理「規則與其例外被拆成相鄰二列」。

    **範圍之限度須隨結果陳述**：現行範圍所得之「通過」為**上界不是定論**，
    範圍再擴（SYSAD、VF747 等）仍可能減少。
```

## 三、六項裁定

### 3.1 #1 `001`／`002`／`003` 之處置

#### `002`（`176` facet A）—— **先刪造值，再加限定**

**(i) 刪 `at any point of the session`**（§1.1，造值）。
ER 末行改為：
```
4. No update progress notification is displayed on the head unit while no safety-related notification condition applies
```
**(ii) pre_conditions 增一行**
```
3. PENDING: DR-SU1 confirmation that no safety-related notification condition applies during the session
```
**(iii) Procedure 末步同步**
```
4. Check that no update progress notification is displayed on the head unit while no safety-related notification condition applies
```

> **限定子句本身非佔位**（R-SU42 v2 之教訓：佔位不必搬進判定對象）——
> 其所引之前提掛於 Pre-Condition。**`PENDING` 僅 +1 行。**

#### `001`（`175`）—— 同構處置

其判定核心含 `no SW Update prompt and no progress notification`，
例外同為 `4907477`。ER 末行、Procedure 末步各加
`while no safety-related notification condition applies`；
pre_conditions 增同一 `PENDING: DR-SU1` 行。**`PENDING` +1。**

#### `003`（`176` facet B）—— **情態問題併入 DR-SU1，不另改 ER**

`allow` 為**許可**，而 ER 斷言「通知被顯示」**即把許可讀成義務**。

**惟其解不在改寫**：許可型需求之可驗形態為「不存在阻擋」，
而**不存在阻擋無法由單次觀測證明**。

**裁定：併入 DR-SU1，增一問** ——
> `4907477` 使用 `allow`（許可）。請確認：安全條件成立時，
> 系統**是否必須**通知（`shall`），抑或**得不通知**（`may`）。
> 前者本 TC 可驗，後者本列無可觀測之驗證形態。

`003` 之三個 `PENDING` 不變，**`reasoning` 增記情態問題**。
**DR-SU1 落地時須一併答此問**，否則會寫出一個驗證義務而規格只給許可之 TC。
