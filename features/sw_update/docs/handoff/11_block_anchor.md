## 一、上繳包 09 審查判定

**收。反向探測之設計是本輪關鍵。**

### 1.1 以反向探測區辨「0 命中」之真偽 —— 採認為方法範例

式B／式C／式D 皆 0 命中，執行層未止於報 0，而以更寬鬆之裸字串探測
（`listed` 0、`as follows` 0、`section` 0、`table` 0、`refer to` 0、`see` 0）
證明該三式之零為**語料真的沒有**，非 regex 太嚴；
且**明言六式不因本節而修改**（改式即為看著結果轉旋鈕）。

**證明「零是真的零」與報「零」是兩件事。**

### 1.2 §2.4 兩條漏網 —— 採認，其中一條之診斷特別重要

> 「`defined in` + 名詞」之語形本身**不足以判別**，判別靠的是其後之名詞
> 是否指涉規格物件 —— **而該判別不是語形問題。**

此句正確界定了語形掃描之能力上限，並直接支撐 §二之 (c) 群裁定。

### 1.3 §7.2 自評 —— 採認為本輪主教訓

「聯集 4/311（1.3%）」讀起來像「全母體只有 1.3% 是統攝型」，
而它實際只說「六式語形命中 1.3%」；隱式統攝在語形上與一般需求無異，
**既不在分子也不會被察覺，該百分比對它完全無感**。
執行層自陳「至於語形不可見者有多少，本輪答不到」——正確。

### 1.4 §4.2 與 §7.3 —— 主動預防誤讀，採認

「全母體 13.5% vs 物件佔比 2.9%」未控制長度混淆，
**不構成虛高之證據，亦不構成無虛高之證據**；執行層將此數連同
「這不構成證據」一起寫出，以防日後被單獨引用。此作法應維持。

## 二、裁定

### 2.1 (c) 群為空 —— 准

`SWE1-FOTA-343`（`vehicle conditions specified in the deployment
configuration file`）與 `SWE1-FOTA-382`（`source firmware version specified
in the differential update package`）所指涉者為**執行期產物**
（部署組態檔、差分更新包），非規格中之需求物件。
**二者不是統攝型需求**，(c) 群為空。

全母體之統攝型需求（語形可見者）為 `SWE1-FOTA-313`、`SWE1-FOTA-327` 二列，
**且二者皆已是自證錨** —— 即語形可見之統攝型，其錨定問題已由 R-SU15(b) 全解。

`SWE1-FOTA-128`（`below mentioned parameters`）**未裁**：其指涉對象
（「below mentioned」所指者）須見其後續列方能判定，材料不足。列入 T24a。

```
R-SU15 v2（統攝型需求 —— 增訂普查之能力界線與盲區偵測器）

v1 (a)–(d) 全部維持。v1 (e)「全母體普查」之落地結果與界線更正如下。

(e) v2 —— **語形普查之結果與其界線**：

    已實證之漏網：語序倒置（`below mentioned`）、
    式F 計數門檻（`{3,}` 對兩個 id 之列舉不敏感）。

    一律標為「疑似盲區」送分析層人裁，不論其語形。
    十分位之界（上繳包 08 §3 實測為 0.229）隨語料版本重算，不得沿用舊值。
    **本偵測器為召回之保險，非統攝型之判定** —— 低分之成因可能是
    統攝型、可能是規格無對應、可能是描述缺陷（下放包 11 §3.2 之 `319`）。
    分類屬人裁。

沿革：v1 見下放包 10 §四；(e) 之落地與 (f) 之增訂依據上繳包 09 §2、§7.1。
```

### 3.1 ⚠ 本輪最重要之發現：**兄弟區塊**

1. **自證**：`313` 之 Description 逐字列出 `4907667`–`4907672` 六個 id，

正解皆不在前 5）。**若無區塊結構，此二列無從錨定。**

### 3.2 `SWE1-FOTA-319` 之召回失敗有可指認之成因 —— 037 描述缺字

其 Description 為：
> The WiFiUpdateService shall coordinate the handling of **condition** during
> OTA server communication, flashing, or software component update…

`the handling of condition` —— **條件之名稱脫落**。其 Requirement Title
為 `Power Loss Handling`，對位物件為 `5. Loss of power(battery disconnect)`。
**037 之描述漏了「power loss」四字，文本路遂無詞可共。**

此為**上游文件之缺陷**，非本管線之缺陷。**不改 037、不臆補**；
記錄於 §四 T24d 之台帳，於撰寫該列 TC 時 `test_item` 上半仍
verbatim 抄其原文（含缺字），錨由區塊定，並於 `reasoning` 記明。

### 3.3 `SWE1-FOTA-292` 之疑似召回失敗 —— 待驗

該列（`manage the configured network priority and select the appropriate
network`）之前 5 候選皆為「建立連線／選網」類（4.10.2／4.6／4.6.1／8.1），
而 CFTS `4907460`（4.7.3）之內容為
> The OTA client SHOULD support **configurable network priorities** in order
> to limit data costs for download sessions…

**字面更貼近，卻不在前 5。** 其 Heading 為 `291 Bearer selection:`，
與「網路優先序」同義。**疑為召回失敗，但分析層無其排名資料，不逕裁。**

## 四、R-SU16（新條，抄入 RULINGS.md，逐字）

```
R-SU16（兄弟區塊錨定 —— 第三條真獨立路徑）

實證（下放包 11 §3.1）：037 之 `SWE1-FOTA-315`–`320` 六列與 CFTS
`4907667`–`4907672` 六個列舉項逐位對應。其中 `319`／`320` 之正解
**不在文本路之前 5 候選內**，僅能由區塊結構推得。

裁定：

(a) **定義**：CFTS 中以編號列舉（`1.` `2.` `3.` …）呈現之一組相鄰需求物件
    為**列舉區塊**；037 中連續之一組列若逐位對應該區塊之各項，
    則此對應關係為**兄弟區塊錨定**。

(b) **獨立性**：本路之輸入為「區塊邊界」與「列序」，
    **不使用文本相似度**，故與路徑 A 真正獨立
    —— 與 R-SU13 v2 支柱 2（序位一致性）不同，後者以 A 之首選為輸入。
    **本條為 R-SU13 v2 之第四支柱。**

(c) **區塊邊界之來源，依可信度排序**：
    1. **自證**：037 某列逐字列出該區塊之全部 id（如 `313`）—— 最強
    2. CFTS 文件結構：同一母章下連續編號之列舉項
    3. 037 側之連續列具共同語形（如同一動詞骨架 + 不同條件名）
    僅有 (c)3 而無 (c)1／(c)2 者，**不足以定區塊**。

(d) **對位之檢定**：區塊內須有**至少二列**之文本路首選即其對位物件，
    方得以區塊推定其餘各列之錨。實證中 `315`–`318` 四列滿足此條，
    故 `319`／`320` 之推定成立。滿足者不足二列時，全區塊送人裁。

(e) **本路之錨得覆蓋文本路之首選**：`319`／`320` 之文本路首選
    （`4907380`／`4907279`）與其正解不同章，而區塊錨為正解。
    **衝突時區塊錨優先**，並記其三證於 `reasoning`。

(f) **全母體之區塊普查**須執行，不得只處理已發現之一塊。
```
