## 三、R-SU29（新條，抄入 RULINGS.md，逐字）—— 105 列之處置

```
R-SU29（無觀測面之列之處置）

現況（上繳包 19～21 實測）：
- 126 列之 `Requirement Description` 未提及任何外部可觀測面
- 其中 105 列之 `Verification Criteria` **亦未**提及
- 三源素材查無任何可作觀測通道者（adb／logcat／dumpsys／debug／shell 皆 0）
- 而 037 自身將該 105 列之 **85% 標為含 `System Test`**

裁定：

(a) **不整批處置，不預先放棄。**
    依據：pilot v2 已證明「需求本文未提及外部面之列，其行為仍可能有
    可觀測後果」（`SWE1-FOTA-175` 全文無 `version` 一詞，而其驗證面
    取版本號之前後變化）。**語形判定不得作為放棄該列之依據**
    （上繳包 20 §7.1(乙2)：126 為上界，非事實）。

(b) **105 列隨其 Test Set 之撰寫批次逐列處理**：
    撰寫該列之 TC 時，依 R-SU25(c) 求其外部可觀測後果；
    取得者照常撰寫，並於 `reasoning` 記明該後果之推得依據。

(c) **取不到者掛 `PENDING` 並增列入 DR-SU2 之滾動清單**，
    不阻斷同批次之其他列。DR-SU2 之清單隨批次增列，
    每包附其現況（列數、所屬 Test Set）。

(d) **母體不因本條縮減**（R-SU3 之 311 不變）。
    若日後 DR-SU2 無解而 `PENDING` 累積至無法交付，
    **母體之縮減屬 Tier 3，提 Pei 裁，分析層不逕裁**。

(e) **禁止之作法**：不得為使該列「可寫」而杜撰觀測面
    （如自行指定 log tag、自行假設診斷 DID、自行發明服務介面）——
    此為 §8.4.1 之造值，且其偽裝性極高（讀者無從分辨杜撰與實測）。
```

### 3.1 DR-SU2 之開立

**DR-SU2 之標的與理由（本輪之關鍵改變）**：

先前之乙路（發 DR 求觀測通道）其立論薄弱 ——
「我們找不到通道」對上游而言是我方之困難，非其文件之缺陷。

**本輪之實測給了它一個文件內在不一致之依據**：

> 037 自身將該 105 列之 85% 標為含 **`System Test`**，
> 而其 `Verification Criteria` 未指出任何外部可觀測面。
> **文件說要做系統測，卻沒說系統測時要看哪裡。**

此為**上游文件之內在不一致**，屬正當且明確之 DR 標的。

| 欄 | 值 |
|---|---|
| 事項 | 105 列（內部服務主體且 VC 亦無外部面者）之系統測觀測面 |
| 理由 | 037 將其 85% 標為含 `System Test`，而 `Verification Criteria` 未指出可觀測面；三源素材亦查無任何觀測通道 |
| 請求 | 該 105 列於系統測層級之觀測手段（log tag／診斷 DID／服務介面／HMI 間接後果），或確認其不由 SWE.6 覆蓋 |
| 初始清單 | **`Telematics Client` 5 列（`363`–`367`）** —— 需求本文與 VC 皆無外部面，且 `366`／`367` 之 VC 檢查對象仍為內部（「the OTA server is queried」「the received session request is forwarded」） |
| 性質 | **滾動清單**，隨撰寫批次增列 |
| Urgency | High |
