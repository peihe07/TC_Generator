## 一、上繳包 23 審查判定

**收。§7.1 是本輪最該被記住的一段，且它推翻了一個尚未被說出口的推論。**

### 1.1 §7.1 —— pilot 之選樣避開了兩個難類

實測：pilot 之 4 列（`175`／`176`／`177`／`183`）**無一屬 126 內部列**；
而 `Silent Update` 9 列中唯一之 105 列（`179`）**恰好落在 batch 1**。

**其意涵須明說**：pilot v2／v3 之「5 個 TC 寫得出來、lint 20/21 全 0」
**只證明非內部列寫得出來**。126 列與 105 列之寫法**至今無一例經驗證**。

下放包 18 §4.1 選 `Silent Update` 為 pilot，其依據為
「Layer 3 有 GT 支持、含 HMI 與 Service 兩型」——
**該依據未含「是否含內部列」之維度**，故選樣之避開為**分析層之疏漏**，
非執行層之取樣。§二 R-SU31 立條。

### 1.2 §T37a —— 停止條件未觸發，裁定成立

35 本已交付簿於 `AB`–`AG` 六欄**皆空**，R-SU28 v3 三之語意推斷獲實測佐證。
**35 本之樣本量遠超所令之範圍**，執行層自行擴大掃描，正確。

### 1.3 §4.1 —— 最後 5 欄中 3 欄同源，是本輪之解題線索

036 之 `C`（`Requirement or Design ID (Polarion)`）之值來源即
SYS1 之 `ID`／`_polarion`；`vehicle_category` 於該欄實填 `NRL-171043`，
與 SYS1 之 `NRL-168414` 同源。

**此使 5 欄之未定收斂為 2 個問題**：
(i) `C` 欄之值如何取得（且**本 feature 之 037 無 HMI Source ID 欄**，
    與 vehicle_category 之取法可能不同）
(ii) `E` 欄之角色

### 1.4 §T37b 之附帶所見 —— R-SU27(a) 於非內部列確實生效

`SWE1-FOTA-175` 之 VC 末句：
> Ensure the SW Update HMI is not triggered for progress indications,
> update prompts, or customer-facing interaction during Silent Update execution.

**此即 pilot v2 所採之觀測面，而 v2 起草時分析層尚未讀過該欄。**
二者獨立得到同一觀測面 —— **R-SU27(a) 之「候選來源」地位於非內部列上
獲一次交叉佐證**（雖為事後）。

反之 `179` 之 VC 四句**全部為內部**（SWMC 與 WiFi Update Service 之間之
DD metadata 傳遞、分析、請求生成），與其 105 列之分類一致。

## 二、R-SU31（新條，抄入 RULINGS.md，逐字）

```
R-SU31（pilot 之代表性與其結論之適用範圍）

實測（上繳包 23 §7.1）：pilot 之 4 列（`175`／`176`／`177`／`183`）
**無一屬 126 內部列**，亦無一屬 105 列。

裁定：

(a) **pilot v2／v3 之結論，其適用範圍限於非內部列。**
    「5 個 TC 寫得出可執行之步驟」「lint 20/21 全 0」等結果，
    **不得外推至 126 列或 105 列** —— 該二類之寫法至今**無一例經驗證**。

(b) **選樣依據須含難度維度**：日後選 pilot 或首批時，其依據除
    Layer 3 之 GT 支持、HMI／Service 之分面外，
    **須明列「是否含已知之難類」及其列數**。
    下放包 18 §4.1 之選樣依據未含此維度，為**分析層之疏漏**。

(c) **batch 1 之意義因此改變**：`SWE1-FOTA-179` 為本 feature
    **首個進入撰寫之 105 列**。其處理結果 —— 取得外部後果而照常撰寫，
    或取不到而掛 `PENDING` —— **才是 105 列可寫性之首例證據**。
    該列之處理過程須逐步記明，不得只記結論。

(d) **通則**：一批樣本「全部通過」之意義，取決於該批**涵蓋了哪些類**。
    未涵蓋之類，其通過率為**未知**，不是**高**。
```
