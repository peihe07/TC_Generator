### 1.1 `.gitignore` 內既有之理由（逐字）

**關於 `sysad_sections.json`（第 3 項爭點已被回答）**：

> Carry customer prose rather than derived structure — same policy as inputs/.
> `sysad_sections.json` bleeds SYSAD paragraph body text into its heading field;
> the `er_*` pair embeds the workbook's Expected Result / Procedure text verbatim.

**這與包內的推理方向一致但結論更精細**：包內以「四份為同類文件之結構萃取，
一致性上應同 policy」推論四份應一起處理；`.gitignore` 則已依**各檔實際內容**
分開判定 —— 三份只帶 id 與標題，`sysad` 那份把段落正文帶進了 heading 欄。

實測佐證：`sysad_sections.json` 之 heading 值確含正文，例如
`"203554": ["4.1.1", "章節目的 Purpose本節旨在說明整體系統架構設計，包括 Head Unit (HU) 內部主要模組構成、與行動裝置…"]`。

**另三份被保留追蹤的理由亦已逐字寫明**：

> The remaining `data/*_sections.json` ARE tracked on purpose (as Home's
> `spec_id_to_outline.tsv` and sxm/amfm's `stla_to_cfts.tsv` are): they are the
> traceability lookups every `spec_reference` is linted against, they carry ids
> and heading names rather than requirement text, and a diff on one is the
> signal that the spec export moved underneath us.

**關於 `pcts_ui/`**：

> PCTS Verifier uiautomator dumps: 320 KB of single-line XML regenerated by
> re-dumping the app. No diff value, and nothing in them is human-authored.

> **執行層意見**：此理由與包內 §4.1 #2 之論述**在事實上衝突**，且衝突點可查證。
> `.gitignore` 說「re-dumping the app 即可再生」；包內說「不可再生（需實機）」。
> **兩者都對，但講的是不同條件下的再生**：在有實機且該 app 版本仍可安裝時可再生，
> 在沒有實機時不可。R-P11 之證據綁定依賴的是**取證當下**的 dump，其
> `pcts_evidence.json` 記錄了裝置與 apk 建號（Pixel 10 / Android 16 /
> `5.1-prod.922397802`）—— **該組合日後未必可重現**。
> 此點需 Pei 裁定，執行層不主張。

**關於 `batches/`**：

> `batches/` is excluded, and not because it is regenerable — re-running the
> Step 2 scripts does not reproduce the verdicts. It is excluded because each
> row embeds the workbook's Pre-conditions and Test Procedure text verbatim as
> a before/after pair, which is the same content the root-level `output/` rule
> and `inputs/` keep out. **The audit value lives in `_meta` plus the row /
> tc_id / changed fields; emitting those without the prose is the fix if the
> trail ever needs to be tracked.**

**`.gitignore` 已經寫出了解法。** 包內 §4.1 #3 主張「改為只排除中間檔而保留 batch
記錄」，與此解法方向相同 —— 產出一份**去除 prose 的稽核軌跡**（保留 `_meta` +
`row` / `tc_id` / `verdict` / `reason` / `changed`，去除 `before` / `after` 全文）。

**執行層建議**：此為可執行且無政策衝突之處置，惟需授權新增產物（例如
`data/batch_audit_trail.json`）。本包未執行。

## 2. 交付檔本身不受 git 追蹤

```
features/projection/inputs/  →  .gitignore:2  (inputs/)
git ls-files features/projection/inputs/  →  0
```

**交付檔 `b16debb7…` 不在版本歷史中**，僅存在於工作樹。

這是既有政策的正確結果（客戶原始檔不入庫），但意味著：

- tag 之 annotation 記錄 SHA256 是**唯一**的交付版本綁定手段
- 若工作樹遺失，交付檔無法自 repo 復原
- `git tag` 所標記的 commit **不包含交付物本身**，只包含產生它的腳本與治理記錄

**須於 tag annotation 中明載此點**，否則日後 checkout 該 tag 會得到一個沒有交付檔
的樹。
