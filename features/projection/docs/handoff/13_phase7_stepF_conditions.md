## 1. A-PJ67｜Test Item 判準衝突 —— 裁為讀法 A（依 done region）

執行層之傾向正確，裁定採納。

> **R-P81｜補列之 `Test Item` 依 done region 慣例，canon §4.3 於本欄不適用**
>
> 本 feature 之 `Test Item` 欄採 **done region 慣例**：需求敘述逐字，長度不受 canon §4.3 之 2–14 字拘束，且**得含 `shall` 等 modal**（§4.3 一般禁止之）。
>
> **依據**：
> 1. profile §1 `[OVERRIDE]` 明定本 feature 之風格權威為 workbook 自身之 done region。canon 明文「feature profile 之 cited override 勝於通則」——**權威鏈上的明文勝過通則**
> 2. 實測 558 列：最小 11 字、中位數 41 字、最大 143 字，符合 2–14 字者 **4/558（0%）**。改寫 7 條補列將使其成為全簿唯一之短標題形式
> 3. D-6 之目的為使補列與既有列**不可區分**；讀法 B 會使補列在該欄看起來像另一份文件，與 D-6 之目的相反
> 4. `Test Item` 不承載追溯——追溯在 `Requirement or Design ID`
>
> **範圍限定**：本條僅豁免 `Test Item` 欄之長度與 modal 限制，**不豁免該欄之其他要求**（不得編造、須反映該 leaf 之需求內容）。canon §4.3 於本 feature 之其他欄位、以及其他 feature 之 `Test Item` 欄，仍全部適用。
>
> **R-P79 之 D-6 判準更正**：自由文字欄之 `Test Item` 判準由「符合 canon §4.3 之三種形狀與 2–14 字」改為「**與 done region 慣例一致：反映該 leaf 之需求敘述，長度落在既有 558 列之分布內（11–143 字）**」。

執行層停在此處而不自行擇一，是本包 §0 設計奏效的實例——**若裁為讀法 B，7 條重寫、D-6 與複本 W 流程重跑，交付檔仍只寫一次。**

## 4. A-PJ66｜列身分欄改為推導式（第二次踩同一坑）

執行層之處置正確且必要，但仍應再一般化一層。

> **R-P84｜列身分欄為推導式，非列舉**
> D-3 之列身分雜湊欄位定義為：
> ```
> IDENTITY_COLS = 34 個凍結欄 − 全部授權例外欄
> ```
> **不得以列舉維護**（現為 `{Expected Result, Remarks, Test Case Author}`）。任何新增之凍結欄窄口授權，**自動**排除於列身分之外。
>
> **依據**：A-PJ57（ER 窄口）與 A-PJ66（Remarks 窄口）為同一缺陷之兩次發生。首次修正寫成「排除 ER 這個特例」，故第二次仍踩。`Test Case Author` 之 40 列補值尚未寫入而已先排除，是**唯一一個在造成 FAIL 之前就被攔下的**——因為執行層這次改成了通則。
>
> **通則**：授權變更之欄位天然不可作為身分之一部分。身分定義須由「凍結欄」與「授權例外」兩份清單**推導**，兩者皆已存在於 `lint_defs`，不需第三份清單。

## 5. Q-3｜`Test Vehicle(Bench)` 3 列須查內容

> **R-P85｜以統計代替語意之禁止（本次適用）**
> `Test Vehicle(Bench)` 既有 3 列非空未查內容，即依「多數為空」判 PASS。**與 M-3（`Input Test Data` 沿用多數值）同型**——canon §5a 第九條之自我適用範圍，執行層已正確識別。
>
> **作業**：
> 1. 讀出該 3 列之內容與其所屬 TC，判定其填寫慣例（例如「需特定台架方能執行者填入台架名稱」）
> 2. 依該慣例判定補列 7 條是否有應填者——**特別是 `NR1L-PROJ-566`（227，需客戶專屬 APP）**，若慣例為「需特定資源者填入該資源」，則該列應填而非留空

> **通則**：欄位之填寫慣例須由**非空樣本之內容**判定，不得由空／非空之比例判定。少數非空樣本往往正是承載慣例者。
