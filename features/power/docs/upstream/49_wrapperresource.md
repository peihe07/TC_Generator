## 二、B2 / G226 —— 獨立重跑：**二份皆位元組相同**，惟路徑缺二步

`features/power/scripts/rerun_wrapper_convert.py`。

**⚠ 工具差異須明載**：分析層用 `olefile 0.47`，**本機未安裝**。
為免為一次比對而引入新依賴（**新依賴之版本差異本身即為變因**），
執行層**以標準庫自行解析 OLE2 compound file**（FAT/DIFAT → 目錄鏈 → mini/常規串流）。
二者所得位元組相同，**即證該切出不依賴特定套件**（A-PW316）。

### R-P317 之路徑，實測須補二步（A-PW315）

（甲）`\*\objdata` 之內容**並非直接為 OLE2** —— 其前有 **OLE1 包裝**
（`01 05 00 00 02 00 00 00 11 00 00 00` ＋ `Visio.Drawing.11\0` ＋ 保留欄位 ＋ 長度），
**OLE2 標頭自 offset 41 起**。

（乙）自 WMF 簽章切出後**須依 WMF 標頭所載之大小截斷**：

```python
declared = struct.unpack_from("<I", blob, i + 6)[0] * 2   # WMF 標頭 offset 6，單位 word
wmf = blob[i:i + declared] if 0 < declared <= len(blob) - i else blob[i:]
```

**並陳各版（R-P182）**：`O829` 首次重跑得 **1,570,790** bytes（多 26），
比對後確認**前 1,570,764 bytes 與分析層所產完全相同**，
多出者為 `OlePres000` 之 stream 填充（含 `NANI` 標記），
而 **1,570,764 正是 WMF 標頭所載之大小**。補（乙）後即位元組相同。
`O1584` 無填充，故首次即相同。

### ⚠ §K 第 1 項之疑慮未發生，惟其理由須明載

§K 慮「路徑本身有誤，則重跑會一致地錯」。**本次未發生** ——
惟其成立之理由**不是路徑無誤**，而是**執行層未照抄路徑而逐步驗證中間產物**：
若照抄「自 offset 40 切出」而不驗其長度，**即會得到多 26 bytes 之檔而不自知**，
且該檔**仍可開啟且看似完整**（A-PW314 —— 與 A-PW280 單向差集同型之第四例）。
