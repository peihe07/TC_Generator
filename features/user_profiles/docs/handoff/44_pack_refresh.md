## 一、AA-1（process defect）review pack 與語料不同步

分析層讀 `40_review_pack_24a.md` 時實測：

- `TC-142`（`041-03`）步驟 2：`Press Yes on popup PU_0129`
- `TC-140`／`141` 步驟 2：`Press Yes on popup PU0626`

而 **41 輪 §2 之 RD #8 處置**明文：五條之確認步驟一律改為
`Press Yes on each confirmation popup PU0626/PU_0129`。

**成因**：`24a`／`24b` 產於 40 輪，RD #8 修正與 `popup_guard` 之 20 條修正
皆在其後。**review pack 是靜態轉錄，不隨重生成更新。**

42 輪已具名「重生成會使 `audit_pending` 之 digest 不符」，
**但無人提及 review pack 亦會因此過期** —— 而分析層正以它作覆核依據。

**這是覆核依據之正確性問題，不是格式問題**：我可能正在對一份已被修好的
內容開缺陷單，或反過來，把已修的版本當成未修而放過。

### 處置

1. **`build_review_pack.py` 於檔首寫入產生時之語料指紋**
   （各條受檢六欄之 digest 或其 `generated/` 檔之 sha256 ＋ 產生輪次）
2. **加一支檢查**：pack 之指紋與當前語料不符 → **報「pack 已過期」並拒絕採信**
   （同 `audit_pending` 之 digest 機制，但方向相反：那個防「改了不重判」，
   這個防「判了舊的」）
3. **重出第五、六批之四份 pack**（`24a`／`24b`／`33a`／`33b`），
   並列出**自其原產生輪次以來有變動之條目清單**，
   使分析層知道哪幾條要重讀、哪幾條不必

## 二、已讀 7 條之覆核結果（`139`–`145`）

**缺陷 0。** 三處值得記：

1. **`TC-140` 取 memory seat 2 而非 seat 1** ——
   「一個永遠落到 Driver 1 之實作，在 seat 1 之設置下與正確實作不可分辨」。
   **選能分辨的設置，不選最順手的設置。**
2. **`TC-144` 之被拖者刻意取非現用之 profile** ——
   拖現用者則「未被啟用」恆真，該斷言即無判別力。
   ER4 併驗「不得啟用」正是為擋「長按即啟用並且順便可拖」之實作。
3. **`TC-145` 之 username 長度刻意不同** ——
   等長時置中與靠左在多數字型下差異極小，且重疊不會發生。
   **前提之作用是使斷言可觀察**，同 `TC-115` 之螢幕尺寸。

**惟此 7 條之覆核結果，須待 §一之變動清單確認其未被 41 輪修正動過方為有效。**

## 三、43 輪三項獨立判斷之採納

1. **「某情形會使某閘轉紅」之斷言須指名驗過它的方向性案例**（§7-1）——
   指不出來者改寫為「推測」。**成因是「未決」段與「方向性案例」段
   之間沒有任何機制要求彼此一致** —— 立為上繳格式之要求。
2. **G-C 之 `why` 欄視為必填**（§7-2）——
   `lint.popup_ids` 與 `done_region.style_authority` 之所以比 `author_value` 好，
   差別在於前兩者**寫了為什麼**。
3. **「先去別的 feature 的交付件裡找一次」**（§7-3）——
   T:Z 被送成裁示題，而查的成本是一支唯讀腳本、三十秒。
   立為常規：**遇「無先例」之判斷，先查他 feature 之交付件，再論裁示。**
