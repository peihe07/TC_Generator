# 43 下放包 — 宣告與生效之分離、掃描存活之證據、覆核收尾

**本包無裁決條文。** 42 輪上繳**核可**。

## 一、採納三項獨立判斷

### G-C：`feature.yaml` 之「宣告」與「生效」須分得開（42 輪 §7-1）

`author_value: "PeiPYHsu"`、`tc_ref_id_value: "NEW"` 為 Comfort 之 yaml 所宣告，
而 Comfort 之交付件該兩欄是空的；我方 yaml 沿用同一寫法。

> **一個沒有被任何程式讀取的設定值，會一直看起來像是決定過的。**

**作業**：`feature.yaml` 之 `write_back` 段加 `applied: true|false` 欄位
（或把未採用者移入註解），使兩者在檔案裡分得開。
**Comfort 之 yaml 不動**（他 feature，R-U24／R-U30）；
其現象登記為跨 feature note，待 Comfort 開輪次。

### G-D：`audit_pending` 之報表須同時列被抑制之條數（42 輪 §7-2）

其顧慮成立：**一個永遠空的清單與一個壞掉的清單，輸出相同**。

**兩層並用**：
1. 報表固定輸出被抑制之條數與其分組（本輪已如此）
2. **分析層之讀法**：「抑制 43 條」是**掃描仍活著的證據**，不是可以略過的意思。
   若某輪該數字**歸零而語料未縮**，須先查掃描本身。

記入 profile 之方法節。

### G-E：可測範圍已到底 —— 品質由人讀承擔（42 輪 §7-4）

30–41 輪每輪皆有缺陷產出；本輪三支新程式一條 TC 都沒動。

> **那不是品質變好的證明，是可測範圍到底的訊號。**

自此**第五、六批 55 條之人工覆核為品質判斷之主要承擔者**，
不得因「16 支閘全綠」而縮減其深度。
