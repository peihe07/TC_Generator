### 2.3 量測 caveat（一處誤報，具名）

### 2.4 Comfort 之 7 條長什麼樣 —— **用途也不同**

全部 7 條皆為「**這條沒有被涵蓋**」之聲明，形式有二：

- `[BLOCKED-NON-HMI]` / `[BLOCKED-SPEC]` ＋
  `No test case in this delivery covers …`（4 條）
- 「該條款以 hard controls 集合為對象，混合型控制之車輛上……
  **cannot be determined from the Comfort HMI specification alone**」（3 條）

**即：Comfort 之 remarks 只在「未涵蓋／不可判定」時出現。**
本 feature 之 remarks 是**每條之設計理由**（為何這樣切、前提為何如此設）。

**兩者不是同一種欄位用法** —— 這比「有沒有內部指涉」更根本。

## 8. 獨立判斷

1. **48 輪那句「已 grep 17 支確認無其他同型」，其證據當時是無效的（§0.1）。**
   結論碰巧是對的，但**用來支持它的方法抓不到它自己要找的 bug**。
   這比錯誤本身更值得記：**一個查核步驟報「0 命中」時，
   要先問它對已知的那一個命中會不會叫。**
   本輪之 DF-2 就是照這個問題設計的 —— 它先證明自己抓得到 `TC-082`，
   再去掃其他的。**建議立為常規：凡「全面查核」之回報，
   須附「本查核對已知案例會轉紅」之實測。**

2. **§2 之查證推翻的不只是「有沒有內部指涉」，是 remarks 這個欄位的用法。**
   我原本以為爭點是「要不要把 `§8.4.1` 拿掉」。
   實測後才看到：**Comfort 之 remarks 只在「沒被涵蓋」時出現，466 列寫 7 條。**
   我方 143 條寫的是每條的設計理由 —— **那是另一種欄位。**
   **若不先查，這一輪會變成「逐條把中文改成英文」，而問題根本不在那裡。**
   G-H（先查他 feature 交付件）第二次證明其價值，而這次它改變的是問題本身。
