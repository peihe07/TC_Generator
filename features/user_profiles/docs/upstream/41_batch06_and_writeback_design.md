def build_edits(records):

## 7. 獨立判斷

1. **「十六條」實際上是二十條，而多出來的四條比原來的十六條更值得注意。**
   那四條（`022`／`024`／`025`／`059-03`）之 pre-condition
   **早就寫了「B 之 welcome popup 為開啟」** —— 也就是說，
   **當初寫的人看見了這個 popup 並做了決定**，只是決定寫在中文前提裡。
   X-1 判它們「未處理」，判錯了；而它判對的那十六條，
   當初寫的人**根本沒看見**。同一個掃描結果裡混著兩種東西，
   而數字（22 處待判）看不出差別。
   **待判清單之價值在逐條讀，不在總數** —— 這是本輪最實在的一課。

2. **PU0588 那兩處誤報活了六輪，是因為「待判」給了它們庇護。**
   紅的東西會被修，綠的東西沒人看，**而待判的東西每輪被抄進上繳一次**。
   R-G9 說「誤報之閘活不過三輪」，但那條規則是為**紅**寫的。
   建議把它擴到待判：**同一條待判連續三輪判為「不成立」者，
   須改判準或除役，不得續留**。

3. **動詞詞表這件事，真正的教訓不是「動詞」。**
   任何以**枚舉**為判準的閘 —— 詞表、PU id 清單、節號清單、狀態值清單 ——
   都有同一個盲區：`--self-test` 驗的是它認識的輸入。
   本 feature 現有 `KNOWN_PU`（現測）、`STATE_VALUES`（寫死四個）、
   `UI_LOCATORS`（寫死兩個）、`DESIGN_METHODS`（現測九條）。
   **其中兩個是寫死的，而它們沒有 VB-2 那樣的對照。**
   建議下輪把 `STATE_VALUES` 與 `UI_LOCATORS` 也接上同型之對照。

4. **全覆蓋達成了，但「180 / 180」這個數字要小心讀。**
   它說的是**037 之每個 leaf 都有一條 TC**，不是「每個 leaf 都驗完了」。
   本批就有四處在 remarks 裡具名「本條不保證」的留白
   （§3.4 之四項）。**覆蓋率是分母的性質，不是分子的品質。**

5. **寫回之五項未決裡，第 1 項（車型欄）是唯一會擋住交付的。**
   其餘四項都有一個安全的預設（不填、留空、沿用 Comfort）。
   而 T:Z 七欄**沒有安全的預設**：填了是編造，不填則該七欄不在 DV 涵蓋內，
   而 §5.4 之涵蓋檢查會紅。**建議優先取得該項之依據。**
