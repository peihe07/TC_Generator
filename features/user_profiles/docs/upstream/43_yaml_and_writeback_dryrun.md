## 1. 作業 1 —— G-C：宣告與生效分得開

### 1.1 `feature.yaml` 之新形

`write_back` 段凡「值 ＋ 是否生效」成對之項目改為子映射：

```yaml
  author_value:
    value: "PeiPYHsu"
    applied: false
    why: "Comfort 交付件之 AA 欄實測為空（466 列）。且此為在交付件上以 Pei
      之名署名 —— 留空可補，署錯名不可。"
```

四項：`author_value`／`tc_ref_id_value`／`vehicle_columns`（皆 `applied: false`）、
`row_order`（`applied: true`，值 `req_id`）。**宣告一律不刪** ——
它是一段有來歷的決定，刪掉就看不出曾經決定過什麼。

### 1.2 **它不只是寫法，是一道閘**

`scripts/write_back.py` 新增 `yaml_params()`，**只讀 `applied: true` 者**；
並新增 **WB-0**：`applied: false` 之項，其對應欄須確實沒被寫入。

方向性案例兩條：注入「`author_value` 為 `applied: false` 而 AA 欄被寫」→ **紅**；
同一份產物改判 `applied: true` → **綠**。
**這就是 G-C 之機械化** —— 42 輪之前，那個值躺在 yaml 裡沒有任何程式讀它。

**WB-0 首版慢到跑不完，值得記**：v1 用
`load_workbook(read_only=True)` 再逐格 `ws["AA10"]` ——
read-only 之工作表不支援隨機存取，十個案例由數秒變成逾兩分鐘。
**檢查沒錯，取值途徑錯了**；v2 直接掃 sheet XML。

### 1.3 comfort 之現象 → **N-XF02**（跨 feature note，唯讀）

登記於本 feature 之 `ANOMALIES.md`，**comfort 一個檔都沒動**（R-U24／R-U30）。
內含 §4 之 T:Z 實測表。**不建議追改其已交付之檔**：
交付件那兩欄為空是**與其程式一致的**，不一致的是 yaml 之記載。

## 7. 獨立判斷

1. **§0.1 那個錯誤是怎麼活兩輪的，比錯誤本身重要。**
   我在 41 輪寫下「不填會紅」，那是**推論**；42 輪跑出來的第 ① 案是綠的，
   那是**實測**。兩者並排放了一整輪，而我在 42 輪的上繳裡
   **同時寫了「7/7 PASS」與「不填則 WB-5 會紅」** —— 沒有把它們對起來。
   **成因是：那句話寫在「未決」段，而測試結果寫在「方向性案例」段，
   兩段沒有任何機制要求彼此一致。**
   建議：凡上繳中出現「某情形會使某閘轉紅」之斷言，
   **須指名是哪一個方向性案例驗過它**；指不出來的，改寫為「推測」。

2. **G-C 揭露的形態比 yaml 大。**
   「宣告了而沒有程式讀」不只發生在 `feature.yaml`。
   本 feature 現存同形態者至少還有兩處：
   `feature.yaml` 之 `lint.popup_ids`（20 個，而 `lint_tcs` 已改為現測 21 個，
   自陳「該值不動，差異已具名上報」）、
   `done_region.style_authority`（BLANK 之下無 done region 可保護）。
   **兩者都有記載說明其為何不生效，這比 `author_value` 好** ——
   差別在於前兩者**寫了為什麼**。
   建議把 G-C 之 `why` 欄視為必填而非選填。

3. **T:Z 之答案很可能是「留空」，而那會使我 42 輪的第 3 項獨立判斷落空。**
   我當時說「即使拿到依據也無法逐條對應」，據以建議改寫提問。
   **現在看來提問本身可能不必要** —— Comfort 已經用 466 列回答了。
   這不是壞事，但值得記：**我把一個「查一下就知道」的問題送成了裁示題**，
   而查的成本是一支唯讀腳本、三十秒。
   **下次遇到「無先例」之判斷，先去別的 feature 的交付件裡找一次。**

4. **55 條人讀開始之前，有一件事只有現在做才有用。**
   G-E 說品質改由人讀承擔。而人讀會產生的修正，
   其落地方式是**重生成**（41 輪之 20 條 popup 修正即如此）。
   **重生成會改動 TC 之受檢六欄，於是 `audit_pending` 之 digest 會不符，
   那 43 條會整批回到待判清單。** 那是設計如此，不是故障 ——
   但若分析層在讀 55 條的同一輪看到「待判 43 條」重新出現，
   容易誤讀為退步。**先在此具名。**
