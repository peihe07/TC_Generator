## 1. L-1 —— **採 (a)**：立 profile 例外，與閘同生

### 1.1 所擇與理由

**採 (a)。** 9.1.1 之 spec 原文即為

> `8.4" will show the username in the Edit Username line like “Edit username: [username]”`

(b) 之改寫會改掉 spec 之逐字內容，而 §8.4.1 禁止改寫 ——
**TC-018 之 ER 要斷言的正是「那一行長什麼樣子」**，
把 placeholder 拆成散文，斷言的對象就不再是原文那個形式。

**惟 22 包之警語照收**：「立一個沒有邊界的例外等於沒有規則」。
故例外**與閘同生**，兩者不得分離。條文入 `DECISIONS.md` **D-UP22-01**。

### 1.2 G19 —— **不是禁令，是對照**

| | |
|---|---|
| 判準 | 每個方括號 token 須在該 TC **所引之節**（或其 must_carry）之原文內逐字找得到 |
| 找不到 | 轉紅（自擬） |
| 受檢欄位 | `tc_title`／`test_item`／`pre_conditions`／`input_test_data`／`test_procedure`／`expected_result`／`remarks` |

依據為 canon §11「Exception (profile-scoped)」之逐字：
`lint validates retained tokens against the cited source row instead of
banning them` —— **本閘之形式即該句所指者**。

### 1.3 方向性案例（**5 / 5**）—— 其中一條是本組的重點

| 案例 | 期望 |
|---|---|
| procedure 以方括號標 UI 標籤 `[Media]`（自擬）| 紅 |
| `[username]` 逐字引自 9.1.1（**TC-018 之實際形狀**）| 綠 |
| **同一 token `[username]`，但引 9.1（其原文無此 token）** | **紅** |
| `tc_title` 含 §4.3 之 placeholder 語法 `[Outcome] when [trigger]` | 紅 |
| remarks 照錄 11.4 原文之 `[This whole note is not applicable for R1 H]` | 綠 |

**第三條是這組的重點**：同一個 token、只換被引之節就必須轉紅 ——
它守的是「**對照的是來源，不是一張 token 白名單**」。
若日後有人把本閘簡化成「`[username]` 一律放行」，
紅向前兩條仍全過，**只有這一條會倒**。

### 1.4 一項記載限制（R-G11）

canon §11 之例外原文為 **「when the *feature profile* says so」**，
而本 feature **沒有** `docs/runtime/profiles/FW036_R1L_UserProfiles_Profile.md`
（Power／Home／Comfort 等八個 feature 皆有）。本條遂落在 `DECISIONS.md`。

**兩者不是同一件事**：profile 檔是 canon 明指之載體，`DECISIONS.md` 是 feature 自裁之登記。
**故本輪不宣稱「已依 canon §11 之形式立例外」** —— 是否補建該 profile 檔，待裁。

## 2. L-2 —— 兩者**不同語意**；且缺口是**兩個**，不是一個

### 2.1 核對結果：**不同**

| | 條件 | 對象 |
|---|---|---|
| 9.2 條件 2 | `does not support **the connected profile feature**` | Connected Profile 選項／資訊 **＋** Stellantis Connected Account 按鈕 |
| 11.3 第二句 | `does not support **connectivity**` | Connected Account **line item** |

**不等價之證明不需外部資料**：9.2 自身把「區域無 `<Brand>` app」與條件 2
**並列為兩個獨立條件**。若「不支援該功能」只等於「無連網」，
**「區域無 app」這一條件就無處安放** —— 一台有連網之車，在無 app 之區域仍無該功能。
反向佐證：6.4.1（NOPR3.1）以 `not equipped with connectivity` 述另一個行為，
可見 spec 對「連網」有其一貫且較窄之用法。

**兩者所隱藏之對象也不同**（9.2 併含 Connected Profile 之選項／資訊）——
即使條件相同，11.3 之 TC 也不可能代測 9.2 之那一半。

### 2.2 **連帶發現：這是一組互指之委派**

22 包點名的是 9.2 這一側。照同一把尺量另一側，發現 11.3 也在委派：

| 條 | 其記載 | 實際 |
|---|---|---|
| `TC-020`（9.2）| reasoning：條件 2「由 **11.3** 承擔」| 11.3 沒有承擔 |
| `TC-040`（11.3）| remarks：第二句「由 **9.2** 承擔」| 9.2 沒有承擔 |

**兩條各自把那一側推給對方，而雙方所指的並非同一件事 —— 兩個缺口同時存在。**

**它比單向指錯更難發現**：單向指錯至少有一份記載是空的；
**互指之委派兩份記載都看起來已交代**，且兩份都通得過現行 G17／G18
（引用欄形態正確、字面值溯得到源）——
**覆蓋稽核之分子分母都不會動，缺口在文字裡而不在數字裡**。

## 3. L-3 —— 判準 V-1，及其**可測之「理由不得適用於已配者」**

### 3.1 條文（入 `DECISIONS.md` D-UP22-02）

> 凡 spec 有**明文之變體覆寫註記**，其所涉字面值出現於某條 TC 之 ER 者，
> **須配該變體之對造**；不配者須具名理由，**且該理由須不適用於已配者**。

### 3.2 觸發要件是「明文覆寫」，不是「另有一種配置」

**這一句是判準的全部重量所在。** 若把觸發要件寫成「ER 內容隨配置而異」，
則 `(if applicable)` 之 Navigation、8.4 吋螢幕、有無連網全部要配 ——
**判準會擴張到不可能執行，然後被整個放棄**。

故觸發母體取 `data/pdf_starred_notes.tsv` 之 `kind == 變體覆寫註記`：
**spec 自己標出來的覆寫，現為 4 條，可逐條點名，新增時閘會紅。**

### 3.3 全批掃描結果 —— 4 個 axis，**原本只配了 1 個**

| axis | 正向 | 對造 | 22 包點名？ |
|---|---|---|---|
| p17 / Table CPA2 整張表不適用（R1 High）| `013` | `044` ✅ 原已配 | — |
| p14 / Table EDPR1 之帳號 label（R1 High）| `017` | **`074` 本輪補** | ✅ |
| p16 / Table PIP1 之 Connected Account 列描述（R1 High）| `039` | **`075` 本輪補** | ❌ **本輪掃出** |
| p17 / Connected Navigation 列（China market）| `013` | **`076` 本輪補** | ❌ **本輪掃出** |

**後兩個是照 22 包所要求之「全批同型者一併掃出」得到的。**
`039` 以「非 R1 High」為前提、`013` 以「非中國市場」為前提 ——
**兩條都把覆寫排除在外，於是覆寫本身無人測**，
與 22 包對 `017` 的觀察是同一個形狀。

**`074` 之方向值得單獨記一筆**：22 包指出 `017` 把**變體**設為前提，
於是 **base variant（非 R1 High，多數車輛）之清單順序反而未被測** ——
`074` 補的正是那一側。

### 3.4 不配對造者：`020`／`077`，理由 `absence-only`

其 ER 為「該按鈕**不顯示**」之缺席斷言 —— label 的形式不影響判定（J-7）。

**而 22 包要求的是「該理由須不適用於已配者」。本輪把這句話做成述詞，由閘實測**：

- 述詞 `absence_only(tc, literal)`：ER 中每一個提到該字面值之**子句**都帶否定詞
- 閘 4 逐條驗：該述詞對**不配者為真**，且對**同一 axis 之已配者為假**

`017`／`074` 斷言的是「清單第四項寫著哪一個 label」—— 述詞為假。**理由不適用，成立。**

### 3.5 **這個閘首跑就抓出兩處錯 —— 都是我的述詞錯**

| # | 現象 | 成因 |
|---|---|---|
| 1 | 閘報「`absence-only` 同樣適用於已配之 `074`」| 述詞以**句**為單位，而 `074` 那一長句裡的 `Resume Setup (only if **not** complete)` 讓整句被讀成否定 —— **一個在場斷言被判成缺席斷言**。改切**子句**（併切逗號） |
| 2 | 閘報「`020` 之述詞不成立」| `literal` 寫死 `Stellantis Account`，而 9.2 本文寫 `Stellantis Connected Account`、R1 High 側寫 `Connected Account` —— **同一 axis 之兩側本來就是不同字串**。改以正則涵蓋各側 |

**閘沒壞，是我寫的述詞壞了。** 兩者的輸出形狀相同（都是「紅」），
分得開只因為它**同時驗兩個方向** —— 述詞對不配者為真、對已配者為假。
只驗其中一向，這兩處都會被讀成「判準成立」。

**此三者仍可能各有覆蓋缺口** —— 例如 **9.1.1 之另一側（大螢幕上 username
與 avatar 顯示於清單左側）現行語料無人驗**。
但那是**取樣範圍**之問題，不是變體對造之問題；**混為一談會使兩者都查不清**。
