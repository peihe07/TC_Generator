## 7. 獨立判斷

1. **`feature.yaml` 宣告了交付件並不帶的東西，而兩個 feature 都是（§1.5）。**
   `author_value: "PeiPYHsu"`、`tc_ref_id_value: "NEW"` ——
   Comfort 的 yaml 這樣寫，它的交付件那兩欄是空的；我方的 yaml 也這樣寫。
   **一個沒有被任何程式讀取的設定值，會一直看起來像是決定過的。**
   建議：`feature.yaml` 之 `write_back` 段加一個 `applied` 欄位，
   或把未採用者移入註解 —— **讓「宣告」與「生效」在檔案裡分得開**。

2. **G-A 之真正效果要到下一輪才看得見，而它可能是負的。**
   本輪 43 條全部登記為 `judged-closed`，於是下輪之待判清單**會是空的**。
   一個永遠空的清單與一個壞掉的清單，輸出相同 ——
   **那正是 21 輪為 `audit_consistency` 加 `--self-test` 的理由**。
   digest 機制擋得住「TC 被改而不重判」，**擋不住「掃描本身壞了」**。
   建議下輪起，`audit_pending` 之報表**同時列出被抑制之條數**
   （本輪已如此輸出：`Q-1：13 條 …`），而分析層讀它時
   **應該把「抑制 43 條」當成掃描仍活著的證據**，不是可以不看的意思。

3. **未決 1 拖住的不只是交付。**
   T:Z 是七個欄位，而它們決定的是**這份交付件對哪些車型有效** ——
   那不是格式問題，是**測試範圍的宣告**。

   （只提螢幕尺寸、有無記憶座椅、有無連網、R1 High）。
   **也就是說：即使拿到 T:Z 的依據，我方也無法逐條判斷哪一條適用哪個車型** ——
   除非那個依據是「全部適用」或「依變體條件推得」。
   **建議向 Pei 提出時一併說明這點**，否則得到的可能是一份我方用不上的答案。

4. **本輪三支新程式都是「守著別的東西」的程式，一條 TC 都沒動。**
   `audit_pending` 守待判、`audit_enums` 守兩張清單、`write_back` 守母本。
   這在交付前是對的順序 —— **但它也意味著：現在擋在交付前面的，
   已經不是我方做不到的事，而是我方不知道的事**（未決 1）。
   從 30 輪到 41 輪，每一輪都找得到缺陷；本輪找不到了。
