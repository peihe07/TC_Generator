## 1. 作業 1 —— AA-1 之三項處置

### 1.1 指紋之範圍 ＝ **pack 實際轉錄的東西**

不取 `audit_pending` 之六欄（那是為待判掃描而定的），
而取 **pack 自己印出來的每一個欄位**：`tc_title`／`pre_conditions`／
`input_test_data`／`test_procedure`／`expected_result`／
`specification_reference`／`design_method`／`priority`／`priority_basis`／
`remarks`，加上 `reasoning`、`source_clause`（spec 原文）、`leaf_desc_037`。

**判準**：若 pack 印的沒變，它就沒過期；若 pack 沒印的變了（例如 `keywords`），
它不影響覆核。**兩支工具之 digest 範圍不同，是因為它們防的是不同的事。**

### 1.2 過期檢查：**不符即拒絕採信**

```
python3 scripts/build_review_pack.py --verify docs/upstream/44_review_pack_24a.md
→ 44_review_pack_24a.md：相符 11 條，不符 0 條
```

**與 `audit_pending` 之 digest 方向相反**：
那個防「改了不重判」，這個防「判了舊的」。

**無指紋表者一律判過期**（非「無法判斷」）——
40／41 輪之四份即屬此類，`--verify` 對它們回傳不符並以非零狀態碼結束。

### 1.3 四個方向性案例

| 向 | 案例 | 結果 |
|---|---|---|
| 正常 | 剛產生之 pack | 綠 |
| 注入 | 某條之指紋與語料不符 | **紅 — 拒絕採信** |
| 注入 | 整段指紋表被移除（＝指紋機制之前產生者） | **紅 — 一律視為過期** |
| 護欄 | `changes()` 對剛產生之 pack | 無變動 |

### 1.4 重出之四份，與舊四份之處置

**重出**：`44_review_pack_24a.md`（11 條）／`24b`（11）／`33a`（17）／`33b`（16）——
共 55 條，四份 `--verify` 皆為 **相符 N 條、不符 0 條**。
每份檔首載明其**取代**之舊檔。

**舊四份保留不刪**，於標題下加警語（同 R-2 之先例）：

> ⚠ 本檔已於 44 輪重出取代 → `44_review_pack_XXX.md`。
> 本檔為靜態轉錄，不隨重生成更新；其產生後語料有變動 **N 條**。
> **不得以本檔作覆核依據**。原文以下保留不刪
> （**記錄分析層當時讀到的是什麼**）。

**刪掉就看不出「當時讀到的是什麼」** —— 而 AA-1 這種缺陷，
下次追查時要的正是那個。

### 1.5 **變動清單如何得出：不用 git**

「git 一律不執行」，故不以 `git show` 取舊版。
**舊值就在那份檔案裡** —— `--changes` 解析舊 pack 之每一個條目區塊，
逐欄與現況重新渲染之值比對，**報到欄位層級**（不只報「變了」）。

## 5. 獨立判斷

1. **AA-1 是我方之缺陷，而它被找到的方式值得記：分析層是在「用」的時候發現的。**
   我在 42 輪具名了「重生成會使 `audit_pending` 之 digest 不符」，
   **在同一段裡沒有想到 review pack 也是一份靜態轉錄**——
   而那兩者的關係，我在 43 輪 §7-4 甚至又寫了一次
   （「重生成會改動受檢六欄，那 43 條會整批回列」）。
   **我對「重生成會使 X 過期」這件事想了兩輪，兩輪都只想到 X = 待判登記表。**
   成因：待判登記表是我寫的，review pack 也是我產的，
   **但只有前者是「檢查」，後者是「輸出」** —— 我把時效性當成檢查的性質，
   而它其實是**任何靜態轉錄**的性質。
   建議：凡本 feature 產出而供他人據以判斷之靜態檔（現有：四份 pack、
   `26_rd_queries` 系列、`34_provenance5`），**一律比照加指紋**。
   本輪只做了 pack —— **其餘兩類尚未做，具名於此。**

2. **「相符 11 條，不符 0 條」這個輸出，下一輪就會開始說謊 —— 除非有人跑它。**
   指紋機制之價值全在**覆核前真的跑一次 `--verify`**。
   而它不像其他 16 支閘會在我方每輪的例行檢查裡被跑到 ——
   **它要在分析層那一側被跑**。
   建議：把 `--verify` 之執行寫進覆核之起手式，
   或由我方在每輪上繳時附上四份 pack 之當前 `--verify` 結果
   （本輪已附，見 §1.4）。**後者較可靠，因為它不依賴另一層記得做一件事。**

3. **T:Z 從「唯一擋交付者」到「不擋」，只用了一支唯讀腳本。**
   §7.4 立為常規是對的，但我想補一句它的邊界：
   **Comfort 之先例之所以能用，是因為兩個 feature 用的是同一份表單母本。**
   若他 feature 用的是別的表單，其交付件之填法**不構成先例**，只是參考。
   查之前先確認母本同一 —— 這一句沒寫進 §7.4，**因為它是我現在才想到的**，
   建議下輪補入。

4. **已覆核 141 / 189，而其中 7 條是分析層讀的，134 條是更早輪次讀的。**
   G-E 說品質改由人讀承擔。以本輪之速度（一輪 7 條），
   餘 48 條需約七輪。**若要縮短，可考慮把「無變動」之條目
   （本輪確認 `24b`／`33a`／`33b` 共 44 條自產生以來一字未動）
   之覆核與生成輪次脫鉤** —— 它們自 40／41 輪起就是現在這個樣子，
   **不是等到現在才穩定的**。
