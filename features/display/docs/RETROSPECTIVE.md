# RETROSPECTIVE —— Display 前十六輪之流程檢討

- 日期：2026-08-25
- 作者：分析層（Claude Project），應 Pei 指示
- 性質：檢討與矯正規則。矯正規則（R-G28–R-G31）之抄錄入台帳
  由下放包 17 步驟 1 執行。
- 基準事實：Display 為 **8 條需求**之 feature，十六輪後 TC 產出為 **0**。

## 一、輪次之去向（誠實記帳）

| 去向 | 輪 | 佔比 |
|---|---|---|
| 素材取得與驗明（含三次「檔名對而內容不答」） | 01, 04, 05, 部分 15/16 | ~4 |
| **分析層之誤及其善後** | 02, 03, 06, 07, 08 | **~5** |
| 對 TC 有直接推進（覆蓋、值域、Q2/Q3 材料） | 03(後半), 05, 09, 10 | ~3 |
| **鷹架品質工作（對 TC 零推進）** | 11, 12, 13, 14 | **~4** |

**約六輪為分析層之誤所耗，約四輪花在鷹架自身的品質上。**
八條需求之 feature 承受了為 627 條設計的流程強度。

## 二、五個模式（每個附再犯判準）

### 模式一：未讀碼／未讀檔就立論，且把錯誤前提提交裁決

實例：Q5。分析層從 01 輪認定「sniffer 認不出 037」是 `recon.py`
跑不動之因，五輪未讀 `recon.py` 原始碼，據此給 Pei A/B/C 三選項 ——
**三個皆不解阻塞**。Pei 裁了 B，B 無效，又花一輪定位真因（一行寫死
的分頁名）加一輪修正。同型：02 輪之檔名搜尋（未下鑽 `ASW-R2/`）、
「Display 無 sys1_export」（實有）。

**再犯判準**：提交 Tier 2 選單時，任一選項未經「採之則阻塞消失」
之讀碼或實測驗證。→ R-G28

### 模式二：鷹架品質工作自我增殖

「未驗項」機制本身有效（它抓到會說謊的警示、綠燈查錯對象等真缺陷），
但**缺一個過濾器**：11–14 輪的未驗項幾乎全是鷹架自身的品質問題
（sidecar 會過期、守衛未被呼叫、映射未逐字），逐項展開為次輪步驟，
每輪再產生新的未驗項。結果是四輪、十餘條條文、零條 TC。

那些條文（R-G23–R-G27）對後面七本工作簿有真實價值 ——
**問題不是做了，是記在 Display 的工期上、且逐輪連鎖地做**。

**再犯判準**：下放包之步驟中，「不影響交付物正確性」者佔多數。→ R-G29

### 模式三：供給側思維

PROXI 之 keyword／heading／ETM 三種分類嘗試共耗三輪，全部失敗，
才改為需求驅動（R-DM33）。失敗的不是判準，是方向：
在不知道 TC 需要什麼之前，去分類 446 列供給。

同型風險至今仍在：SYS2 80 列全母體覆蓋表、SYSAD 分派全表 ——
其中對 8 條 TC 真正有用的是 16 個候選列與值域，其餘是揭露義務
（一次性產出即可），不是持續維護的對照。

**再犯判準**：任何「對全母體逐列分類／填欄」之步驟，而其消費者
（哪一條 TC、哪一項揭露）說不出來。→ R-G30

### 模式四：待裁跨輪與輪次粒度

縮寫錨一案執行層連問三輪（04/05/06），分析層拖至 06 輪才裁。
反向亦有：可並行之小步驟被拆成獨立輪次。八條需求的 feature，
每一次下放／上繳往返都應換到明確的推進。

**再犯判準**：執行層之同一問題出現於連續兩包之「未驗項」而無裁示。
→ 併入 R-G31 之斷路器。

### 模式五：流程強度與規模脫鉤

Display（8 leaves）沿用了 vehicle_setting（627 leaves）尺度的全套：
全母體覆蓋表、參考庫九項綁定、逐輪抄錄核對、四層交叉檢查。
其中綁定與核對之**單次成本低**，可保留；全母體對照與逐輪連鎖之
鷹架稽核**成本隨輪次成長**，小 feature 承受不起。

**再犯判準**：開案時未依 leaf 數選流程檔位。→ R-G30

   與本檢討無涉。

## 四、矯正規則（全文，待抄錄）

```
R-G28（裁決選單須先驗證其能解題 —— 全域）
向 Pei 提交 Tier 2 選單前，須：
(a) 把阻塞定位到具體之檔案與行（或具體之缺件），定位須來自
    讀碼／讀檔／實測，不得來自推定；
(b) 對每一選項回答「採此選項後，該阻塞是否消失」，答案之依據同 (a)。
未能滿足者，提交之物不是選單，是猜測 —— 裁了也不解題，
且消耗的是 Pei 之裁決與兩層之往返。

實例：Q5 之 A/B/C 三選項皆建立在未讀 recon.py 之前提上，
三者皆不解阻塞（真因為 recon.py:568 一行）。Pei 裁 B，B 無效。
```

```
R-G29（未驗項分流：交付正確性 vs 鷹架品質 —— 全域）
上繳包之「未驗項」由分析層分流為兩類：
  A 類 —— 影響交付物（TC／揭露表／DECISIONS）之正確性：
          次一下放包內處理。
  B 類 —— 鷹架自身之品質（工具、守衛、台帳、映射稽核）：
          記入 feature 之 BACKLOG.md，不逐輪展開；
          於交付後、或 Pei 指定之整備期批次處理。
例外：B 類項若再犯會直接污染交付物（如會說謊的守衛正在被
交付流程依賴），得升 A 類，須註明升類理由。

下放包不得因「上輪自陳了它」而自動把 B 類展開為當輪步驟 ——
自陳之義務在誠實，不在立即處置。
```

```
R-G30（流程檔位與 feature 規模成比例 —— 全域）
開案（Phase 0）時依 037 之 leaf 數選檔位，記入 DECISIONS.md：

  輕量（leaf ≤ 20）：intake → recon → DECISIONS → framework → pilot。
    不做任何全母體對照表（覆蓋、參數、分派）；上游素材之取用
    一律需求驅動（R-DM33 之一般化）：TC 需要什麼，查什麼。
    揭露義務以一次性量測滿足，不建持續維護之對照。
  標準（20 < leaf ≤ 150）：現行流程。
  重量（leaf > 150）：現行流程＋批次分段（vehicle_setting 模式）。

檔位可因實情升檔（須記理由）；不得無理由降檔。
Display 補記為輕量檔位（本條生效前已按標準檔位走，不回溯重做）。
```

```
R-G31（推進聲明與斷路器 —— 全域）
每一下放包檔頭須有一行：
  「本包對交付物之推進：<具體物>」或「無（理由：…）」。
連續兩包為「無」者，第三包不得發出 —— 分析層須先向 Pei 報告
現況並取得走向指示。

同斷路器適用於待裁：執行層之同一 Tier 2 問題出現於連續兩包
之未驗項而無裁示者，分析層次包必須裁畢或明列不裁之理由與裁期。

理由：十六輪中有四輪（11–14）對交付物零推進而無人叫停 ——
不是因為誰失職，是因為沒有任何機制要求把「零推進」說出口。
```
