## 零、本提案初版之兩處錯誤與其更正（2026-08-25）

初版（下放包 08 §5）之三梯次表有兩處錯：

1. **`ETM` 列數 50 為索引錯位所致。** 我以
   `{i+1: g[i-1][ui]}` 建 PROXI 列號對照表，把每一列之 `Used by` 值
   接到了下一列。正確索引（`{i: g[i-1][ui]}`）之實測為 **100 列**
   （於有 PROXI 定義之 177 列中）。
2. **「互斥且窮盡：69 + 117 + 269 = 446」之算式不成立** ——
   三數實際相加為 **455**。成因是第一梯次之 keyword 條件會納入
   *沒有* PROXI 定義之列，而那些列同時被算進第三梯次。
   **梯次自始就不互斥，而我在表下斷言它互斥。**

更正後之互斥分割（已驗 `lid_row` 唯一，四類相加 = 446）：

| 類 | 判準 | 列數 |
|---|---|---|
| A | 有 PROXI 定義 且（`Used by` 含 ETM ∪ keyword 相鄰） | **107** |
| B | 有 PROXI 定義 且 兩者皆否 | **70** |
| C | 無 PROXI 定義 但 keyword 相鄰 | **9** |
| D | 無 PROXI 定義 且 keyword 未命中 | **260** |
| | 合計 | **446** |

**但 A 類之判準本身已由步驟 5 之實測否定，見 §零之二。**

### 零之二、`ETM` 判準之鑑別力 —— 實測為零，**停止條件 25 觸發**

「與顯示相關」無逐字錨可判（R-DM13／停止條件 14），故改測可測者：
ETM 群內之 keyword 命中率 vs 群外之基準率。

| 群 | 列數 | keyword 命中 | 命中率 |
|---|---|---|---|
| `Used by` 含 ETM | 100 | 8 | **8.0%** |
| `Used by` 不含 ETM | 77 | 7 | **9.1%** |
| 倍率 | | | **0.88x** |

**ETM 群之命中率略低於群外。** ETM 群之內容以音訊／天線／氛圍燈等
與顯示無關者為主（`AM_FM1_Antenna_Type`／`AMPPresent`／

依下放包 09 §六第 25 條：**ETM 之 100 列中與顯示相關者遠少於半數，
第一梯次判準不成立，停並回報，不得逕行改判準續做。**

本提案之 §二起以下各節**暫停適用**，待分析層裁示新判準。
唯一未受影響者為 keyword 相鄰之 23 列（其中 14 列有 PROXI 定義、
9 列無），該線索自始標為「僅揭露、非錨」。

## 一、待排之母體是什麼

`data/proxi_candidates.tsv` 之 446 列（LID `Proxi & Configuration`
之全部資料列）。依 R-DM23，其 `related_leaf` 為空之 445 列語意為
**(2) 本輪未追查** —— 不是「已查證與本 feature 無關」。

現況（逐字量測，非估計）：

| 項 | 列數 |
|---|---|
| 已有 `related_leaf` | **1**（r170 `RVC_SK_PRSNT`，`glossary_phrase_norm`） |
| 於 PROXI `Format` 逐字查得定義 | 177 |
| 其 PROXI 列之 `Used by NODE(VFXXX)` 含 `ETM` | ~~50~~ → **100**（見 §零） |
| keyword 相鄰（`DISP`／`DCSD`／`RVC`／`Camera`／`Display`／`Touch`／`Screen`） | 23 |
| 上兩者之交集 | ~~4~~ → **7** |
| 上兩者之聯集 | ~~**69**~~ → **116**（含無定義者；互斥分割見 §零） |

`ETM` 之意義：本 feature 三個顯示訊號在 BHCAN2 中之發送節點即 `ETM`
（A-DM14）。**這是相關性之線索，不是判準** —— 一個參數被 ETM 使用
不表示它與顯示有關，ETM 也管別的事。

## 二、提案之順序（三梯次）—— **§零之二已使本節之第一梯次判準失效，暫停適用**

| 梯次 | 判準（逐字、可機器產生） | 列數 | 理由 |
|---|---|---|---|
| **第一梯次** | keyword 相鄰 **或** `Used by` 含 `ETM` | **69** | 兩條線索各自獨立；取聯集而非交集（交集僅 4 列，取交集會漏掉 65 列） |
| **第二梯次** | 有 PROXI 定義但不在第一梯次 | 117 | 值域已知，追查成本低；但無任何相關性線索 |
| **第三梯次** | 於 PROXI `Format` 查無定義 | **269** | 連值域都取不到，追查它需要先解決「它在哪裡被定義」 |

三梯次互斥且窮盡：69 + 117 + 269 = 446。

> 第三梯次之 269 列不等於 `anchor_kind = none` 之 269 列 —— 兩者恰好同數
> 是巧合嗎？**不是**：`anchor_kind` 之 `none` 條件即「無 leaf 錨、無
> cfts_usage、無 PROXI 定義」，而前兩者在 446 列中幾乎不出現，故兩集合
> 實際重合。此處記明以免日後被當成兩個獨立事實引用。

## 三、停止點之提案

追查應在下列任一條件成立時停止該梯次，**而非追完為止**：

1. **DR-DM7 到齊**（本專案之 VF 代碼或已填值之 PROXI 實例檔）——
   `Used by NODE(VFXXX)` 即可用於篩選，母體可望大幅收斂。
   **此時應重新分梯，不是接著往下追。**
2. **同一梯次連續 20 列無任何逐字錨**（沿用 R-DM13 之「loop-until-dry」
   精神）→ 該梯次視為乾涸，記其已追列號後轉下一梯次。
3. **出現需要非逐字判斷才能連上之候選** → 依停止條件 14 標無錨，
   不得猜；若同一梯次累計 3 筆以上如此，停並回報（該梯次之判準可能
   不適用）。
