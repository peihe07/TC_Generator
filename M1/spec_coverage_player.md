## ③ 高信心 SPEC-only 缺口(11 條,逐條判定)

### 群組 A — 進度條 / 時間顯示行為(7 條)→ **確認真缺**
鐵證:需求母體中「time format / elapsed / total time」= **0 個需求**,「Songs Found」= **0 個需求**。進度條雖有 10 個需求「提到」,但全是 PC1.1 把 Progress Bar 列進 Play Controls 的**樣板句**,**沒有任何需求定義進度條的實際行為**。

- `PC6.1` — 裝置支援 position jumping 時,進度條可操作(slider 跳轉)
- `PC6.1.1` — Slider 移動並指示 elapsed time
- `PC6.6` — USB 插入時於 elapsed 區顯示 '<n> Songs Found'
- `PC6.8` — 移除整個進度條(slider+bar)的條件
- `PC6.8.1.1` — (該情況下)維持 current/total time 資訊
- `PC6.8.2.1` — (該情況下)連 current/total time 也移除
- `PC6.8.3` — 曲目中途進度條/scrubber 顯示狀態不應改變

> 補充:`PC6.4`(時間格式 HH:MM:SS)被歸在桶②(內文假覆蓋),實則也是同群的缺口。整個 **PC6.x 進度條/時間家族基本上沒被拆成需求**。

### 群組 B — Shuffle 清單時序(2 條)→ **確認真缺**
鐵證:「re-shuffle / shuffled list」= **0 個需求**。Shuffle 需求(PLA-010)只覆蓋 On/Off 切換,沒有清單時序行為。

- `PC5.2.1` — 洗牌清單在當前曲目播完前不播放
- `PC5.2.2` — 到清單尾端不重新洗牌

### 群組 C — 邊界 / 條件(2 條)→ **部分覆蓋,語意待確認**
- `PC4.7` — 「Repeat Off 不支援時不應呈現該選項」。最近需求 PLA-033(Repeat Off State UI)有 Off 概念,但**沒有「不支援時不呈現」的條件邏輯** → 可能部分缺。**(與 §2 Repeat Off 議題相關)**
- `PC2.2.1` — 放開 FF/Rewind 按鈕後續播。FF/Rewind 需求 PLA-025/026 有 6 條,可能已覆蓋「放開續播」→ 需確認。

## ② 待語意確認(26 條,擇要)
這桶是 token 相近但無引用,**含假覆蓋**。低分可疑者(很可能其實也是缺口):
- `PC1`(Play Controls 適用來源清單)、`PC2`(Skip 切換曲目)、`PC1.2`(Tune knob 切曲)、`PC3.2/3.2.1`(暫停圖示/resume 操作)、`PC2.2.2`(FF 到頭停止)、`PC6.8.2`(無法顯示資訊時)。
- 這些建議用一次 LLM 批次語意確認(便宜),逐條判「真覆蓋 / 真缺口」。

## 對生成的意義(回到標準)

這 11(+ PC6.4,實為 12)條是「**生成 TC 時必須主動考慮、即使沒有對應需求**」的行為——正是 `TC_generation_standard.md` §2 兩層覆蓋模型裡 L2 要補的。

**建議動作**
1. 進度條/時間顯示(群組 A)+ Shuffle 時序(群組 B):**直接補測項**,並回填成 domain pack 的 boundary(它們是穩定的 SPEC 行為)。
2. PC4.7 / PC2.2.1(群組 C):與 Repeat Off 議題一起,對 SPEC 細讀確認。
3. 桶②的 26 條:跑一次 LLM 批次語意確認,把「真覆蓋」濾掉、剩下的併入缺口清單。
4. 把 L2 SPEC 覆蓋做成與 L1 並列的 KPI,Gate 同時看兩層。
